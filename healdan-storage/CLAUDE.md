# healdan-storage

Guidance for storage backends. It was moved out of the root `CLAUDE.md`, so that it loads only when Claude works on files here. The root file still applies, and its "Where the rest lives" lists the other files like this one.

- **`healdan-storage`** keeps each Store's files on a storage backend of its own, a local or NFS folder or an S3 bucket (JPF id `healdan-storage`, which requires `healdan-core`; spec `docs/superpowers/specs/2026-11-01-s3-storage-backends-design.md`). Its code is under `com.logicaldoc.healdan.storage`, which `HealdanContext`'s scan finds. The Developer Guide's How Healdan Extends LogicalDOC page has how it plugs into CE. The docs are the Admin Guide's Storage Backends section (`site/content/admin/storage-backends/`), Stores and Healdan Settings pages; the Install manual's Cloud Storage, Backup and Restore, Host Folders, What Runs, Configuration, Upgrading, Troubleshooting and Known Limitations pages; and the Developer Guide's How Healdan Extends LogicalDOC, API (`503 storage-unreachable`), Tests, Continuous Integration and Building from Source pages. Its build, test and Docker facts are in the root `CLAUDE.md`'s "Build and test", in `docker/CLAUDE.md`, and under "Tests" below.
  - `HealdanStorage` is CE's one `store` bean through the `store=` key (`ConfigPlan.HEALDAN_KEYS` in Docker), and never a Spring component, which would make a second instance, `healdanStorage`, on `FSStore` servers too, that `Context.get(HealdanStorage.class)` finds before CE's (`Store.get()` and CE's `@Resource` look `store` up by name). Its `init()` reads no table, as Spring calls it before Flyway has run. On `FSStore` the module's other beans, its download filter and its seeds do nothing, and the Storage tab refuses every change.
  - `hd_storage_file` (JDBC, `StoredFiles`) has a row per file, keyed by doc id and resource name. Backend 0 is staging, which has no `hd_storage_backend` row, and 1 is Original (`store.1.dir`). Each write gives the row a new random 64-bit `hd_write`, never a counter, which the mover's commit and the read cache's entries check. `exists`, `size` and `listResources` answer from the rows, and a file with no row is read from Original's folder. The mover lists only rows with `hd_waiting` set, so whatever leaves a file off its Store's backend sets it (`recordWrite`, `moved`, `setStore`, the recording seed, and `storeBackendChanged`, which every Store switch calls, including one back to Original, which deletes the Store's `hd_storage_store` row), and the nightly check mends one that drifted. Its SQL follows the rules under the root `CLAUDE.md`'s "Persistence"; its plan's Global Constraints (`docs/superpowers/plans/2026-11-03-s3-storage-backends.md`) gave them for MariaDB and PostgreSQL both, before `on conflict` replaced their `Savepoints.insertIfAbsent`.
  - One lock per file (`FileLocks`, striped in the JVM): saves and deletes hold it while they write a file's bytes and row, the mover for its commit, and the purge while it checks and deletes a held copy. Nobody holds two. The mover and the purge, once they hold one, write nothing while an open transaction has written that file's rows (`writtenByOpenTransaction`), and leave the file for a later pass. Healdan runs one node; a cluster would need a lock in the database.
  - A local hold (and staging's) moves the copy under `.held/` at once, while its `hd_storage_held` row and the delete of its `hd_storage_file` row are the caller's transaction's. `HoldRollback` puts it back on a rollback, holding its lock, before `FileLocks`' marks clear (their order is `HoldRollback.ORDER + 1`), so the mover and the purge never find the row back before the copy. It replaces a file in the place only when nobody else has written or deleted the file since the hold (`FileLocks.marksMade` and `marksHere`), so the file is the transaction's own write; otherwise the copy stays. A copy left under `.held/` waits for the purge's next run, which puts back any local held copy whose row reads it from there rather than delete it. A hold whose row can't be written puts its copy back at once. A delete that finds a file under `.held/` and not in its place holds that copy again.
  - Staging, the read cache and the key files are `-Dhealdan.storageStaging`, `-Dhealdan.storageCache` and `-Dhealdan.storageKeys`; without them, `staging/` and `cache/` beside `store.1.dir`, and `healdan-storage-keys/` beside `SecretBox`'s key. Staging can't be, hold or sit inside Original's folder or the key files', nor the cache any of those three (`Staging.apart`, by path, links not followed). A backend added or edited can't overlap them, the configuration folder or another backend (`BackendDrafts.checkPlace`): folders by path and with links followed, and S3 buckets and prefixes within one S3 service (every AWS host is one, any other endpoint its host and port).
  - An encrypted backend's key is `backend-<id>.key`, 32 bytes, mode 600 in a folder of mode 700, never in the database: lose it and the recovery key, and its files can't be read. Every backend has a marker naming this install (`storage.installId`) and the backend, `.healdan-backend` in a folder or `<prefix>.healdan-backend` in a bucket; one missing or another's fails the backend, so an unmounted share is never written to, and the recording seed stops startup rather than mark an Original with no marker and no file while `ld_document` has documents not deleted. An encrypted backend's `.healdan-check` must decrypt under the key file at start, at the first write to a backend not yet checked, and on Test.
  - The hooks in `healdan-core`: `HealdanStartup.start()` calls each `HealdanStartListener`, and `StorageStartup` then starts the checks, the mover, the retests, the purge, the alert and the nightly check (tests call `run()`, which calls none); `HealdanHooksImpl.afterFolderRestore` calls each `FolderTreeListener`, as CE's folder restore tells no listener; the seeds join `SeedRunner.ORDER` by name, a name with no bean skipped; and `StorageUnreachableException` (`healdan-core`'s `util`) is an outage, which `healdan-api` answers `503 storage-unreachable` and `PreviewWorker` waits out without spending a try.
  - The Admin app reads and changes storage through `healdan-core`'s port `StorageAdministration` (`com.logicaldoc.healdan.admin.storage`, plain records in `StorageRecords`: no S3 secret, only whether one is stored; the access key ID, which an edit shows; a recovery key only in an encrypted add's `AddedBackend` and `showRecoveryKey`'s answer, each recorded as a showing; an endpoint as scheme, host and port), which `StorageAdministrationImpl` (`storage.web`) implements with a method for each of `StorageAdmin`'s operations, plus `backend(id)`, `backends()` (every backend as `backend(id)` gives it, and the files with no Store, from one overview) and `exists(id)` (counting no file), so a request reads the overview once at most, `on()` and `settings()` (counting no file, for the settings' routes) and `limits()`, over `StorageAdmin` unchanged, so the tab's rules and sentences are the port's. Each change, and `showRecoveryKey`, first refuses anyone but an administrator (`FilingRules.isAdmin`, `ONLY_ADMINS`), then, while storage backends are off, every change with a sentence of its own (`OFF`), as the Admin app has no Storage tab to name. `BackendDetail.storesInTrash` names the Stores in the Trash on a backend (deleted or removed; with no backend of their own, Original's; never the Templates Store), whose files stay there for their restore, and `remove`, but of Original, and a `save` that changes the bucket, prefix or path refuse while there's one, naming each with the way out (restore, another backend, delete again), before `StorageAdmin`, which would name it by id. A `save` whose draft leaves an S3 endpoint null keeps the row's (`whole`), as `BackendDetail` gives an endpoint only in part, so `PATCH /v1/admin/backends/{id}` sends the port none it wasn't sent. A missing secret key file is `SecretKeyMissingProblem` (`sealed()`, the values sealed with it), and `newKey` is the tab's question answered. `healdan-core` and `healdan-api` can't depend on `healdan-storage`, so it's found by type (`Context.get().getBeansOfType`), as `HealdanStartListener`s are (spec §9.7; `StorageAdministrationImplTest`; `OverviewPort`, in `healdan-core`'s test-jar, a fake whose every method but `overview()` fails).
    - Each change that succeeded is recorded straight after it (`AdminEvents.recordAfter`, area `STORAGE`): `backend.added`, `backend.changed`, `backend.removed`, `backend.recovery-key-shown`, `-confirmed` and `-entered`, `store.backend-changed`, `storage.stuck-retried` and `storage.settings-changed`, aimed at a `backend`, a `store`, or `storage` with no id (the settings, the files with no Store). What changed is read from the rows before and after, an access key or secret as `Change.secret()` and a recovery key never; an encrypted add records `backend.added` and `backend.recovery-key-shown`; a read, and a change that changes nothing (a retry with nothing stuck too), record nothing.
  - `storage-hide-stores` hides CE's Stores screen (menu 105), which could change `store.1.dir`. `DownloadErrorFilter` holds a CE download's first 1,024 bytes, so an outage met before they're sent gets a `503` page (or `/convertpdf`'s placeholder), not an empty `200`.

## Tests

- `healdan-storage`'s tests extend `AbstractStorageTestCase` (on `AbstractHealdanTestCase`), which runs CE through `HealdanStorage`: it writes `healdan-core`'s test `context.properties` again as `context-storage.properties` with `store` swapped (its `baseConfigResource()`, which the base class writes again as `pg-context-storage.properties`), and registers the module's `plugin.xml`. Staging, the cache, the key files and the secret key are under `target/`. Storage is tested in three layers: `MemoryBackend` (faults on demand; `s3Like` acts as a bucket) and `LocalBackend` under `target/`, with `BackendContract` run on each backend; `FakeS3`, a JDK HTTP and HTTPS server in the tests that answers `S3Backend`'s calls and refuses what S3 refuses (`S3BackendTest`); and Garage on the smoke stack (step 5f). No test makes a real start, so tests call `Mover.runOnce()` and the like themselves; `StorageStartupTest` starts the timers with their waits shortened.
