# healdan-core

Guidance for provider sign-in, email, the Trash and the Admin app's records, all in `healdan-core`, with the routes and screens on top of them in `healdan-api` and `healdan-web`. It was moved out of the root `CLAUDE.md`, so that it loads only when Claude works on files here. The root file still applies, and its "Where the rest lives" lists the other files like this one.

- **Sign-in through a provider** (M4, OpenID Connect; spec `docs/superpowers/specs/2026-11-01-m4-oidc-sign-in-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.signin`, with its pages in `healdan-api`'s `SignInResource` at `/api/signin/`. The docs are the Install manual's Sign-In Providers section (`site/content/install/sign-in/`), the Admin Guide's Healdan Settings page and the Developer Guide's API page.
  - Providers' settings are `signin.*` rows in `hd_setting` (`SignInProviders`, which validates everything before it writes). A link is the provider's id and the identity, with no issuer, so the identity claim and the issuer (but for a trailing slash) can't change while the provider has linked accounts (R21, R33), and the identity claim can't be one people can change: `email`, `preferred_username`, `upn`, `unique_name`, `name` or `nickname` (R34). Refusals reach the GUI as HTML, so they name a provider by its id, never its label. The group map is `hd_signin_group`. Links between accounts and identities are `hd_signin_identity` rows, kept as records once unlinked; `hd_linkkey` and `hd_linkuser` are set only while linked, so the unique indexes allow one link in use per identity and per account.
  - `SecretBox` seals client secrets, helpers' refresh tokens and storage backends' S3 secrets (AES-256-GCM) under a key file at `-Dhealdan.secretKey`, which `docker/setenv.sh` puts in the conf volume and the modules' tests put under `target/` (`healdan-storage`'s under `target/conf/`, the configuration folder no local backend may share). Losing it means entering the secrets again, helpers signing in again, and S3 backends failing until their secrets are entered. Once anything stored is sealed, only an admin who types a secret and confirms a new key makes one (`sealWithNewKey`): a client secret on the Sign-In tab, or an S3 secret on the Storage tab. Any other seal fails (`KeyMissingException`), so a key file missing for a while loses nothing. Keys are made under `healdan-secret.key.lock`, so two servers sharing the folder make one.
  - A linked account has `UserSource.OIDC` (stored as 3, appended so the others keep their numbers; `UserSourceTest` pins them), no password and no impersonators. `ProviderPasswordListener` refuses either with an `AuthenticationException`, the only veto `HibernateUserDAO` passes on: it logs and swallows a user listener's `PersistenceException`. CE's user delete runs no user listener at all.
  - Linking an account, or making a linked one a provider account again, deletes its LogicalDOC API keys and, after the commit, closes every open CE session of the account on this node, every one it opened as another account, and every session its keys opened (`SignInAccounts`, R31, through `admin.people.PersonSessions.close`, which the Admin app's Disable, Reset Password and Sign Out Everywhere share). Unlinking gives the account a temporary password from `TemporaryPasswords`, which New User and Reset Password share (`SignInAdmin`). The web page can still make a key for it, which `HealdanThrottle` refuses at sign-in on every route.
  - A provider sign-in opens its CE session through the whole chain with a one-time `hd_signin_` key (`SignIns`, `SignInAuthenticator`), on M2's pattern; `HealdanTokenAuthenticator` leaves those keys alone. The helper gets a 60-second one-time code for its device token instead, and a helper start whose PKCE challenge another sign-in still has, waiting or with a code, is refused as `expired`.
  - `/api/signin/` is pages, not JSON API: `openapi.yaml`, `RouteCoverageTest` and `Contract` leave it out, as `/api/addin/`. `PublicAddress` (`healdan-core`'s `web` package) gives the server's public address to both and to the Sign-In tab.
  - Provider calls go through Nimbus (`ProviderClient`), which builds the requests and reads the answers, sent by the JDK's `HttpClient` with the JVM's trust store and HTTP proxy properties (a SOCKS proxy is refused, as the client would skip it), never LogicalDOC's proxy settings, and only over HTTPS unless `HEALDAN_SIGNIN_ALLOW_HTTP=true`, which only the sign-in overlay sets. Each call's whole answer must come within 10 seconds (a refresh's 20) and weigh at most 1 MiB (the keys 50 KB). A discovery document that couldn't be fetched is remembered for 30 seconds per provider, and every use fails at once meanwhile; `forget`, which saving a provider calls, clears it.
  - Of the provider's answers, only `invalid_grant` revokes a helper at its re-check (`ProviderRecheck`, from `TokenFilter`); an outage never does. The gate refusing the account, the account no longer linked to that provider (R19), and a refresh token that won't open revoke too. Revoking clears the token's sealed refresh token, whose column V7 widened (R35).
- **Email** (M5; spec `docs/superpowers/specs/2026-11-03-m5-email-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.email` and `healdan-api`'s `EmailResource` (`POST /api/v1/emails/inspect`, `POST /api/v1/emails`, `GET /api/v1/emails`; in `openapi.yaml`). The docs are the User Guide's Filing Email from Outlook and Emails (Once in Each Matter), the Install manual's Office Integration (deploying `outlook-manifest.xml`), Known Limitations and Upgrading (emails filed before M5), and the Developer Guide's API (Filing Email), Desktop Clients and How Healdan Extends LogicalDOC (`hd_email` and the worker) pages.
  - The Message-ID is the `emailmessageid` property (`ATTR_EMAILMESSAGEID`, the `profile-message-id` seed), which `EmailDocumentListener` reads on every route: the header without brackets or whitespace, at most 998 characters, NUL as a space and each character beyond the Basic Multilingual Plane as U+FFFD (`MessageIds`; PostgreSQL would keep an emoji, but the helper's `MessageIds` does the same to the character, and `hd_email` is indexed by the result), an `.msg`'s from its `PR_INTERNET_MESSAGE_ID` stream, which `EmailFields` reads with POI (CE's `EMail` has none). A check-in replaces the property and the row with the new version's, or takes them away when it's no message. `hd_email` (V8, `hd_docid`, `hd_messageid`, a SHA-256 hash; no matter column, since `MatterLocator.locate` finds each copy's matter afresh) is the index, and the attribute isn't the truth: CE's screens can edit it. Rows for documents deleted for good stay; every lookup joins `ld_document` and skips deleted documents and aliases.
  - `EmailIndexWorker` fills both for emails already in Healdan, with a cursor (`email.index.cursor`) and `email.index` = `done` in `hd_setting`. It runs from its cursor at every start; to run it again from the start delete both and restart.
  - A matter holds a message once (`OncePerMatter`): `OncePerMatterListener` (`healdanOncePerMatter`, position 135, after the email fields at 130 and before the doc # at 140) refuses new email documents and stores that move a document into another matter (never a move within its matter), and `HealdanHooksImpl` covers the routes that write before a listener (moves, restores, folder copies and merges). It refuses with `AlreadyFiledException`, a `HealdanRuleException`, which `ProblemMapper` answers as `409 already-filed` with the copy as `document`. Only copies the caller can read count; no user means every copy counts.
  - There's no lock on `hd_matter`: a lock held across a folder copy's later `DocumentManager` waits deadlocks with any upload. The rule serialises on `DocumentManager`'s monitor, inside which each `create` and `moveToFolder` runs its listeners and, when no outer transaction is open, commits, so its check (with a fresh look at READ_COMMITTED for a transaction begun before the call) sees every filing that went through the monitor before it. `OncePerMatterConcurrencyTest` fails without it. Folder copies and merges (one transaction of several stores), folder moves and restores, and a direct `DocumentDAO.store` or `DocumentManager.update` that moves a document don't go through it, so one of them at the same moment as an upload of the same message into the same matter can still leave two copies. A cluster would need a lock again.
  - `EmailFiling` (with `Filer`, the filing of one document taken out of `DocumentResource.create`) files the email, its ticked attachments (`MessageParts` decides which are attachments and which inline; attachments take the email's sent properties) and their `attachment` links, each document in its own transaction and undone by compensation on a failure. `MessageLocks` holds a JVM lock per matter and Message-ID, which `Filer` takes too for an email filed on its own, so a repeat waits for the first filing, 30 seconds at most, then `409 filing-in-progress`. Filing needs WRITE on the folder, as `POST /v1/documents` does.
  - `EmailFiling.link`, which the filing and Save to Matter (`MessageResource`) both link with, reads each link's row back from `ld_link` and stores a new link while it isn't there (`CheckoutResource.TRIES`), then fails the filing, which is undone. CE's link DAO stores the link and writes both documents' count of links in one transaction, and another thread's write of either document in that moment, such as the Indexer's, fails that write in a flush CE's DAO swallows, so the transaction rolls back at its commit, unseen and unlogged (the smoke test's step 9, 2026-11-21; `MessageResourceTest`'s saves past the Indexer's write). The undo's delete of a link (`unlink`) is read back the same way, as CE's DAO counts the links again in that transaction and a lost delete left the email the count of a link it no longer had (`#testAFailureAfterTheLinkTakesTheLinkBackPastABackgroundWrite`), and `link` refuses inside a transaction, where its read-back would count a row not yet committed. Any write through a CE DAO whose `flush()` can meet a newer record version can be lost this way: read back what it stored.
  - Never log subjects, addresses, attachment names or message contents at info or above; Message-IDs at debug only.
- **The Trash** (M6 §16; spec `docs/superpowers/specs/2026-11-16-folders-and-trash-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.trash`, with `healdan-api`'s `TrashResource` (`/v1/trash`) and `FolderChanges` (`FolderResource`'s folder delete, move and `contents`), and the User app's `views/TrashView.tsx` (`/app/trash`) and `organising/` (folder moves and deletes, the cross-matter question, Undo). The docs are the Admin Guide's The Trash and Removed Items page, the User Guide's The Trash and Copying, Moving and Deleting, and the Developer Guide's API, The Web App and How Healdan Extends LogicalDOC.
  - The tree rules hold on every route, admins needing none of the permissions. A folder move needs Move on every live folder and document in it, hidden ones included, and Add where it goes: `PermissionRules.checkMoveTree` from `RulesFolderListener`, and `HealdanTreeChecks.movedTrees` (through `HealdanRpcChecks` for the Classic Interface) before `FolderServiceImpl.move` and `SoapFolderService.move` write, so a Classic merge's subfolders need it too. `beforeFolderDeleteTree` runs `checkFolderDelete` and `checkDeleteTree`, then `TrashRules.checkDeletable`, which refuses a live document inside that is checked out or immutable, admins' too, and only then records the item, so a person without Delete inside learns nothing of what's there. A non-admin restores a folder only from the Trash (`ld_deleted` 1), a live one refused as well as a removed one (`checkFolderRestore`).
  - The Classic Interface's three removal RPCs (`deleteFromTrash` twice, `emptyTrash`) ask the `removeFromTrash` and `emptyTrash` hooks first (`TrashRemoval`), so a folder's removal takes its contents and is recorded. A restore, on every route, sets a restored document `TO_INDEX` (`TrashDocumentListener` on `RESTORED`), as CE's restore never re-indexed.
  - Every delete, on every route, is one item in `hd_trash` (V11) with a member in `hd_trash_member` for each folder and document it took, deleted, removed, restored or destroyed. `TrashRecorder` records a tree in `beforeFolderDeleteTree`, a document from `TrashDocumentListener` (position 170) and a folder deleted alone from `TrashFolderListener` (140), in the delete's transaction; a member already deleted in an item records nothing. CMIS records first and commits each row on its own, so `afterFolderDeleteTree` (`TrashRecorder.settle`) drops what it didn't take.
  - A restore brings back only its item's members (`TrashRestore`, through `folderRestoreScope`); one a restore leaves behind, its folder not live, moves to the item holding that folder, or to an item of its own. A member removed on its own leaves its item for one of its own (`TrashRecorder.splitOff`), so Removed lists every removed member.
  - `TrashDestroyer` destroys what was removed more than `trash.removedDays` before (1 to 365, 30 by default), nightly at 02:47 server time (`TrashStartup`), each document in its own transaction, as `_system`, which the `trash-system-destroy` seed gives Destroy Documents. A document's member is written destroyed before CE's destroy runs, so nothing but the commit follows `healdan-storage`'s hold of its file, which a rollback wouldn't undo; the item's folders and aliases then go in one transaction, and one the job can't take yet (a row still in it, a folder taking its security from it, a live alias) stays removed for the next night. `trash-record-existing` makes items of what was deleted before the Trash. Tests call `runOnce` themselves; `TrashTestHooks`, in `healdan-core`'s test-jar, fails a destroy for other modules' tests.
  - The API refuses a Store's Trash item (`409 refused`, "A Store is restored from Deleted Stores on the Admin app's Stores page, or in the Classic Interface."), which only an admin's delete makes, in the Admin app (`DELETE /v1/admin/stores/{id}`) or the Classic Interface, as CE puts a Store back under the root whatever is asked: it's restored by `POST /v1/admin/stores/{id}/restore` (`StoreService.restore`, through `TrashRestore` with the root as the place), or the Classic Interface's Trash. A matter's own folder and a Store are never moved or deleted by the User app, nor destroyed by the job.
  - In the app, folder rows select with documents (a plain click still opens a folder; Shift, Command, the arrow keys, Space and a right-click select), a drag's `ROWS_TYPE` payload carries folders with their kind and level, and every delete's toast has Undo (`@healdan/ui`'s `toastWithAction`, 10 s, F6 reaches it), which restores the items the delete answered with.
- **The Admin app's records** (spec `docs/superpowers/specs/2026-11-18-admin-app-design.md` §8.1 to §8.8, §9.3 to §9.6) are `healdan-core`'s `com.logicaldoc.healdan.admin` and the packages under it; the docs are the Developer Guide's How Healdan Extends LogicalDOC, API (The Admin App's Routes) and Tests pages, and the Admin Guide's The Admin App, Clients and Matters, Workspace Templates, Top-Level Folders (the Workspace Editor), Permissions (Who Can Use This Folder), Stores, Users and Groups, and the Monitoring section (`site/content/admin/monitoring/`). No test makes a real start, so tests call `ErrorWriter.drainOnce()` and `UsageSummary.refreshNow()` themselves, and `DashboardService.forget()` before a fresh `read()`.
  - `hd_admin_event` (V12) is the administration record: when, who (id and username), from where (`AdminContext`, which `AdminFilter` sets to the request's address; none outside an admin request, as from the Classic Interface), the `AdminArea`, the action (`client.renamed`), the target's kind, id and name, and a JSON detail of the changed fields, `{"before":…,"after":…}` in name order, a secret's `{"secret":true}` (`AdminEvent.Change.secret()`) with no value. `AdminEvents.record` writes in the caller's transaction, so a failed record fails the change; `recordAfter`, for a change that isn't one transaction, writes after it in a savepoint, never throws, and logs a failure at error naming the action and the target's kind and id, never a value. `ClientService` and `MatterService` (`@Transactional`) record their creates and edits themselves, so the Classic Interface's and the seeds' client and matter changes are recorded too; a create records every field it set, an edit only what changed, an owner as `Full Name (username)` (`PersonNames.of`, each name trimmed, and the username alone when both are blank, as `dave`, not twice; a deleted owner under the username CE gave the account at its delete), and an edit that changes nothing isn't recorded. The admin routes record the rest: `matter.moved` (the Store before and after, in the move's transaction), `matter.deleted` and `folder.access-applied` (`recordAfter`), and `folder.access-changed` (in the save's or Follow Parent's transaction: `follows`, the followed folder's path from its workspace's top folder, and a change per changed row keyed `group Partners`/`user jdoe`, valued with the flags in `Permission` order, null for no row); a folder's target name is that path. A Store's are `STORES`'s, in `StoreService`'s transactions: `store.created` (its name and a `read` change per row), `store.access-changed` (`follows` when it followed, and a change per changed row, named as a folder's) and `store.renamed` (the name before and after), and after the change, from the routes, `store.deleted` and `store.restored` (`recordAfter`). A workspace's folders and the templates (`MATTERS`) record inside their transactions `folder.created` (`name`, `in`), `folder.renamed`, `folder.moved` (`in`), `folder.properties-changed` (each own value that changed, by the property's name, null for inheriting), `search-folder.created` (name, `in` and the rule), `search-folder.rule-changed` (the rule's members that changed), `template.created` (`name`, `copyOf`) and `template.renamed`, and after the delete `folder.deleted` and `template.deleted` (`recordAfter`); a template's target name is its name.
  - `MatterAdmin.check(Draft, actor)` (`admin.matters`, `POST /v1/admin/matters/check`) says what `MatterService.create` would refuse in New Matter's form, every `Draft` member nullable, each code looked for only once its members are given (`MatterCheck.CODES` order), with `MatterService`'s and `MatterNumbering.checkAvailable`'s own checks and sentences, P1 per template folder top down (`PermissionRules.prospective` against `AclMath.effective(parent)`, aliases skipped as the copy skips them) and P2 on the workspace's ACL as the create makes it (`AclMath.effective(template)` plus the owner's own group with every permission, through `PermissionRules.p2Failures`, which `checkP2` uses). It writes nothing; admins only. `IndexCounts.failedIn` and `PreviewJobs.countGivenUpIn` count a matter's (`GET /v1/admin/matters/{id}`).
  - `FolderAccessService` (`admin.access`, with `AccessLevel`, `AccessRow`, `AccessGrant`, `FolderAccess`): `workspaceFolder(id)` is the admin routes' scope, which it takes from `WorkspaceAdmin.workspaceFolder`, the one copy (a live matter's own folder or a template's top folder and what's in them; null, so `404`, for a Store, the Templates Store, the root, Default, an alias, a folder in the Trash or a search folder directly in the Templates Store). `read` lists `AclMath.effective`'s rows, so none that grants nothing, a person named by `PersonNames` and a group whose `ld_group` row is gone by `GroupNames` (`Group <id>`). `save` (exact flags, by group or a person's own group) refuses a deleted group or person (but a deleted group the folder already grants something may stay, so a save needn't take away what's there), `guest` or a read-only person's own group beyond Read Only's five, but for the owner's row on a matter's own folder (P2-R20), and on that folder an owner's row left out or below Full Access. A read-only owner's row is then stored as what a read-only person's row holds (Read, Download, Preview, Print, Email, Subscription and Store, read back as `custom`), so `folder.access-changed` records each row as stored, not as sent; below the matter's own folder the owner's row is capped as anyone's. The cap binds only what a row adds to what the folder grants that group now, so a row kept as it is passes, such as a read-only owner's that Set Own Permissions takes over from the folder it followed. It checks P1 (inside a matter) and P2 (its own folder) with `PermissionRules`' methods before writing, as `HibernateFolderDAO.store` logs a listener's veto at error, which `ErrorCapture` would count; then `FolderDAO.store` with `FolderEvent.PERMISSION`, so `PermissionsFolderListener` narrows below. In a template P1 and P2 aren't checked as it's edited. `followParent` is `updateSecurityRef`, refused on a matter's own folder. Nothing changed, nothing written or recorded. `save`, `followParent` and `applyToSubfolders` refuse anyone but an administrator first ("Only an administrator can change who can use a workspace's folder."), as the other admin services do. Every admin write that can roll back calls `CacheEvictor.evictFoldersOnRollback` before its DAO write, as the second-level cache isn't transactional: `save` and `followParent`, `StoreService`'s `create` and `setAccess`, `FolderChanges.moveMatter`, `WorkspaceAdmin`, `TemplateAdmin` and `MatterService`.
  - `applyToSubfolders` is CE's `FolderDAO.applySecurityToTree`, in its own transaction, after Healdan's hook (`PermissionRules.checkApplyToTree`, which in a Store and its matters, the Templates Store and its templates, and from the root lets an admin through and needs anyone else to have SECURITY on every folder below with its own rows, the Trash's included; only admins reach the admin route, so there it always passes and `canApplyToSubfolders` is a live folder below): every folder and search folder below, at every level, the Trash's included, loses its own rows and follows what the folder follows; nothing moves, and the folder is untouched. A restricted folder below is opened up (`FolderAccessServiceTest#testApplyToSubfoldersOpensUpARestrictedFolderBelow`).
  - `WorkspaceAdmin` (`admin.workspace`, with `WorkspaceNode`): `workspaceFolder` is the admin routes' one scope, which `FolderAccessService` and `healdan-api`'s `WorkspaceRequests.folder` use; `tree` reads the workspace once (`StoredRows.descendants`), aliases left out, hidden ones kept, folders then search folders by name ignoring case. `createFolder`, `rename` and `move` refuse first, each a `HealdanRuleException` with its sentence, so a refusal writes nothing: the workspace's top folder (its matter's or template's routes change it), a name any live folder in the folder has ignoring case (hidden, alias or search folder too, as CE's `setUniqueName` would rename), a move out of the workspace (a matter's folder moves to another matter in the User app; a template's, `OTHER_TEMPLATE`, "A folder in a template moves only within that template."), into a search folder or into its own tree, a checked-out document in a moving tree; then CE's DAO, so the filing rules, P1's narrowing and the values passed down decide as on every route, and a backstop refuses a name CE changed anyway. `properties` is `ProfileView.forFolder(folder, topId)` (inheritance walks up to the workspace's top folder), Client and Matter left out; `setProperties` stores with `FolderEvent.CHANGED`, nothing that wouldn't change the folder's own values. Search folders through `SearchFolderService`, the name checked first. Deletes aren't its: `FolderChanges.deleteWorkspaceFolder` and `deleteTemplate`. Admins only.
  - `TemplateAdmin` (`admin.workspace`, with `TemplateInfo`, `TemplateProblem`): `list` (by name ignoring case; folders counted without aliases; live matters made from each in one grouped query), `create` (empty, following the Templates Store; or a copy through `TemplateCopier` in the create's transaction, as a `SEARCH_FOLDER` operation so it may make search folders, the copy's top re-pointed with `updateSecurityRef` when the source's follows), `rename`, both refusing a name another folder in the Templates Store has, ignoring case, and `problems`: `wider-than-parent` per folder or search folder in the tree's order (`AclMath.effective` against its parent's, which also catches one still following a folder above its parent), and `store-unreadable` per live Store and group (`PermissionRules.p2Failures` on the template's ACL, owner left aside), Stores and then groups by name; a group named by `GroupNames` (`MatterAdmin`'s rule).
  - `StoreService` (`admin.stores`, `StoreAccess`): `stores()`, `store(id)` (a live Store by `MatterLocator`, else null, so `404`), `isStore(id)` (live or in the Trash), `fixedFolder(id, change)` (Default's, the Templates Store's and the root's sentences) and `access(id)` (`CAN_SEE` for Read alone, `CUSTOM` otherwise). `rename(storeId, name, actor)` (`@Transactional`) takes `create`'s name rules leaving the Store out, its own name changing nothing, a case change a rename, and records `store.renamed`. `restore(storeId, actor, session)` takes the Store's Trash item (`trashItem`, deleted or removed; else `NOT_IN_TRASH`), checks its name free under the root as `create` does, then `TrashRestore.restore(item, rootId, …)`; its caller records. `deleted(tenantId)` lists the Stores in the Trash in one query (`DeletedStore`: item, state, matters still in it, who deleted it, when removed). All refuse anyone but an administrator first (`ONLY_ADMINS`). `create` makes the workspace under the root with its own rows, a Read row per group, and records it, in one transaction, so a failed record leaves no folder. `setAccess` gives each listed group Read, keeping its other flags, drops every other row, and stores once with `FolderEvent.PERMISSION`; before that it calls `PermissionRules.checkStoreP2(storeId, acl)`, P2 for the Store's live matters' own folders (those that follow the Store skipped; the Trash's checked at restore by `checkRestore`) against the rows as they'd be, in a few queries chunked by 500 ids, the owner's own group passing while the owner could read the Store, refusing only a group the change shuts out (P2 holding now and failing after), so a matter that already let in more stops no other change. Nothing changed, nothing written or recorded.
  - `UserAdministration` and `GroupAdministration` (`admin.people`, spec §8.7) are the people's reads and changes, on CE's `UserDAO` and `GroupDAO`, none of its RPC services, so `TokenUserListener`, `ThrottleUserListener` and `EveryoneUserListener` run as on every route. A person is an account of the reader's tenant, not deleted, not SYSTEM (never changed here: `SYSTEM_ACCOUNT`); a READONLY one is only in its own group and `guest` (`READ_ONLY_GROUPS`), and New User makes DEFAULT accounts only. A group is live, DEFAULT, the tenant's and not `_user_`; `admin`, `guest`, `publisher` and Everyone are fixed. The Users list reads everything once (`PeopleReads`), then filters, sorts and pages in Java. Last Sign-In is `ld_lastlogin` once the history has an `event.user.login` (every new CE session writes both, a device token's after its bound session timed out) or `ld_lastlogin` is later than `ld_creation` (CE's `history.events` can leave the row out), else null. Each change runs its own `TransactionTemplate` and throws `IllegalStateException` inside a caller's, so a guarded change commits before it lets go of its lock and what follows a commit (`PersonSessions`, the email, `recordAfter`) follows a real one. The order: `ONLY_ADMINS` (and `YOUR_ACCOUNT_DISABLED`, for every change, inside its lock where it holds one); not a person or group; `IllegalArgumentException` (`groupIds`); the fields (`admin.FieldRefusal`: `required`, `too-long`, `invalid`, `taken`, `not-editable`, in the form's order); `NO_GROUP`; the no-op, answered as it is and unrecorded (`refusals` null for it); then the rules, each a `HealdanRuleException` whose sentence is a public constant.
    - The guards (`DISABLE_ADMIN`, `DISABLE_YOURSELF`, `ADMIN_STAYS`, `LEAVE_ADMIN_YOURSELF`, `LAST_ADMIN`): a disable, or any membership change (`memberships`: `setGroups`, a group's member add and remove), holds `UserAdministration.ADMIN_CHANGES`, refuses first a caller whose stored account isn't enabled now (`requireEnabledAdmin`, read by JDBC past the second-level cache: `YOUR_ACCOUNT_DISABLED`, so of two administrators disabling each other the second meets it, and `LAST_ADMIN` stays for a caller the count leaves out, such as a seed's, and as the backstop after the write), counts the enabled administrators (enabled, not deleted, not SYSTEM, in `admin`) after its write and commits before letting go. ## Tests

- The Monitoring tests' seams are in `healdan-core`'s test-jar. `LogTestHooks` sets `LogFiles`' `configuration` (`useNewFolder`: the test `log.xml`, a small configuration of the shipped kind with `DMS`, a task's log, CMIS rolling with `fileIndex="min"`, the `_WEB` copies and additive and non-additive loggers, its root in a folder of the test's own under `target/`; `useConfiguration`) and `opener` (`refuseToOpen`, `shrinkAfterOpening`, `keepOpened`), and `reset()` puts both back and deletes the folder; Log4j itself reads `log4j2.xml` in the tests, so nothing but the tests writes those files, and a module whose tests read the Server Log needs `healdan-api`'s copy of `log.xml`. `DocumentViewsTestHooks` stops (`stopTime`) and moves (`passTime`) the views' clock and fails their writes (`failWrites`). `JobsTestHooks.list(task)` lists a task of the tests' own after CE's through `Jobs.tasks`, such as `HeldTask`, run by CE's `Task.run`, which waits for `release()` and can be held before its run begins (`holdTheStart`, `letStart`). `AuditFeed`'s `scanPerSource`, `sent` (each statement a page sends, window ends included) and `paged` (each page's cursor, which `AuditTestHooks` uses to fail a page or act at one) and `JobControl`'s `saver` are seams on the beans. A test that changes Index Optimizer's schedule or enabled flag puts it back, and one that switches scheduled tasks off sets the run level's aspect in memory only and puts it back. `AuditFeedTest` checks the plans on PostgreSQL itself: each source's unfiltered first page reads its table's key backwards with no sort (2,000 rows a table, sequential scans off), and each index-served read, with the value among the oldest 1% of 40,000 rows a table, removes by its filters no more than the window and the value's own rows (`explain (analyze)` of every statement the `sent` seam saw), under a forced generic plan too.
- Provider sign-in tests run against `FakeProvider`, a JDK HTTP server in `healdan-core`'s test-jar that serves discovery, keys and a token endpoint and signs its ID tokens with Nimbus. `SignInTestHooks`, in the same test-jar, allows plain HTTP, sets the TLS provider calls trust (`FakeProvider.trust()` uses it) and moves the clocks of pending sign-ins, one-time codes and the re-check; `FakeProvider.close()` resets it.
