# healdan-api

Guidance for Healdan's JSON API. It was moved out of the root `CLAUDE.md`, so that it loads only when Claude works on files here. The root file still applies, and its "Where the rest lives" lists the other files like this one.

- The rules and records the routes sit on (sign-in, email, the Trash, the Admin app's services) are in `healdan-core/CLAUDE.md`, and the apps that call the API in `healdan-web/CLAUDE.md`.
- **`healdan-api`** is Healdan's JSON API, the HTTP layer at `/api/*` (JPF id `healdan-api`, which requires `healdan-core`; M2's spec is `docs/superpowers/specs/2026-10-23-m2-api-foundation-design.md`). Its code is under `com.logicaldoc.healdan.api`, and `HealdanContext`'s scan finds its beans, so it has no `@PluginContext` of its own. Domain code (tokens, read models) stays in `healdan-core`. The docs site's Developer Guide has a page for API clients (`site/content/developer/api.md`).
  - `ApiServlet` (`@WebServlet("/api/*")`) runs a CXF JAX-RS server on its own `ExtensionManagerBus`, not CXF's Spring bus, which would expose every `/services/rest` server under `/api/rest` too. Its resources are the Spring beans in the package that carry `@Path`.
  - `/api/**` is `security="none"` in `context-security.xml`: the API's `TokenFilter` signs requests in from `Authorization: Bearer hd_…` device tokens, or, when a request has no Bearer `Authorization` header, from the browser's CE web session on `WebSessionRoute`'s rule (M6 spec §8.1): `Sec-Fetch-Site: same-origin`; an `Origin`, when sent, that is the public address's or the request's own; `X-Healdan-Client: web` on `POST`, `PATCH`, `PUT` and `DELETE`, in any case, the method being the request's own (CXF's `_method` and `X-HTTP-Method-Override` stay off, which `WebSessionRouteTest` pins); and the CE session id only from the HTTP session's `sid` attribute. Never from a `sid` parameter or header, the `ldoc-sid` cookie, Basic or `X-API-KEY`. A same-origin request that breaks the rule is `403 web-session-refused`, and no open session `401`. `AppServlet` asks `WebSessionRoute` for the session and its user too, so a page load the API would refuse goes to sign-in.
  - On the web session `Caller.token()` is null, which the device-hold code (`DeviceHolds`, `ApiViews.heldHere`) takes as no device, so a resource that reads the token checks for null. It signs out with `DELETE /v1/session`, and a token with `DELETE /v1/auth/tokens/current`.
  - Device tokens work only at `/api`. `HealdanTokenAuthenticator` accepts one only inside `ApiTokens.openSession`, which hands CE's chain a one-time key, and refuses every other `hd_` key but the `hd_signin_` ones, which it leaves to `SignInAuthenticator` (M4), so CE's routes (`loginApiKey`, `X-API-KEY`, Basic) never take a token. Letting a token in elsewhere, such as WebDAV, needs a narrow allowance there.
  - `healdan-api/src/main/resources/healdan/api/openapi.yaml` (OpenAPI 3.1, served at `/api/v1/openapi.yaml`, browsable at `/api/docs/`) is hand-written and is the contract: `ApiTestCase` checks every response a test gets against it (only a test-only route under `/api/v1/test/` can skip it, with `ApiCall.withoutContract()`, for an answer no client reads), and `RouteCoverageTest` fails when the routes and the files differ. A new endpoint goes into it in the same change. A list schema built with `allOf` needs `unevaluatedProperties: false` (see `Page`).
  - Errors are RFC 9457 problems with stable `code`s (`ApiProblem`); unreadable means `404`, as in the old UI.
  - **The admin API** (`/api/v1/admin`, the Admin app's; spec `docs/superpowers/specs/2026-11-18-admin-app-design.md` §9.1, §9.2) is `com.logicaldoc.healdan.api.admin`. Every resource class there carries `@AdminRoute(area)` (`healdan-core`'s `AdminArea`), and only those do: `AdminRoutesTest` fails on a route under `/v1/admin` whose class lacks it, that is `@Public` or that locates a sub-resource, and on the annotation outside `/v1/admin`. `AdminFilter` (an `ApiServer` provider after `TokenFilter`) answers a device token `403 web-session-only` and anyone `AdminAccess.allowed(user, area)` refuses `403 admins-only` (members of `admin`, in every area, for now; asked at every request); no session is still `TokenFilter`'s `401`. It fails closed: a route declared under `/v1/admin` whose class lacks the annotation is logged at error and `403 admins-only` to everyone, judged by the declared path (`RoutePaths.declared`), never the request's, which can carry matrix parameters. A request it lets through has its address in `AdminContext`, which `ApiServlet` clears with the caller, once the answer is written.
  - Its contract is `healdan-api/src/main/resources/healdan/api/openapi-admin.yaml`, not served over HTTP; `openapi.yaml` lists no admin route. `Contract` checks every answer under `/api/v1/admin` against it, and `RouteCoverageTest` compares the routes with both files and fails on a `/v1/admin` path in `openapi.yaml` or another in the admin file. `$ref` can't cross the files, so it repeats `Page`, `FieldError` and the `Problem` response, and `Problem` with fewer members, which `OpenApiFileTest` keeps the same as the first file's but for their words. `npm run generate` writes its types to `packages/api/src/admin-schema.d.ts` (not committed), exported as `adminPaths` and `adminComponents`.
  - Its changes are checked in one order, and a refusal changes nothing: `400` for the body, `404` for the path (and `GET /v1/admin/matters/next-number`'s `clientId` and `GET /v1/admin/stores/{id}/backend`'s `backendId`), `422 validation` (missing or blank `required`, `not-editable`, and what a route names, such as an access row's `invalid` or `duplicate`, or the missing `values` of `PUT /v1/admin/folders/{id}/properties`, after its `404`), then `409 refused` with the rule's sentence in `detail`, an id in a body that names nothing included. No other problem code is new but the Storage routes' two: `503 storage-unavailable` (no storage port, after `400` and before anything else) and `409 secret-key-missing` (with `sealed`).
    - `AdminClientsResource`, `AdminMattersResource` and `AdminFolderAccessResource` are all `MATTERS`, `AdminStoresResource` (rooted at exactly `/v1/admin/stores`) is `STORES`, and `AdminUsersResource` (`/v1/admin/users`) and `AdminGroupsResource` (`/v1/admin/groups`: live `ld_type = 0` groups of the caller's tenant, no `_user_` ones) are `PEOPLE`. The storage routes are three `STORAGE` classes, so a route's area is its record's: `AdminStoreStorageResource`, rooted at exactly `/v1/admin/stores` beside `AdminStoresResource` (a Store's backend, its switch with `switchPreview` first, its stuck files and their retry), `AdminBackendsResource` (`/v1/admin/backends`) and `AdminStorageResource` (`/v1/admin/storage`: the settings, and the files with no Store, `stuck(0)`/`retry(0, …)`).
    - The People routes (spec §8.7) sit on `healdan-core`'s `admin.people` services, which check every change's fields and rules and record it themselves; the routes record nothing and open no transaction, as each change runs its own. `PeopleRequests.run` answers a service's `FieldRefusal` `422 validation` (its fields in the form's order), an `IllegalArgumentException` `400 bad-request` (logged at error: the routes check what a service would find malformed first, so one is a fault), and leaves a `HealdanRuleException` to `ProblemMapper`'s `409 refused`. `checkGroupIds` (a null or a repeated id) and a `PATCH` member's type are `400` before the path's `404` (`isPerson`, `isGroup`, cheap); a `PATCH` fills its left-out members from the person or group as read and sends the whole draft. A person's path id is `[0-9]+`, a group's `-?[0-9]+`, as CE's `publisher` is -10000 (`GroupPath` and the Users list's `groupId` have no `minimum`). A system, deleted or other tenant's account is `404` on every `/users/{id}` path and as a member's `{userId}`; a `_user_`, deleted or other tenant's group on every `/groups/{id}` path. `GET /users/options` and `GET /users/{id}/checkouts` are beyond spec §10; the Admin app's Release is the public `DELETE /v1/documents/{n}/checkout`. A temporary password is only in `CreatedUser` and `TemporaryPassword`, when it wasn't emailed, and their `toString()` (`PeopleView`) leaves it out (`AdminUsersResourceTest#testNoAnswerRecordOrLogHoldsATemporaryPassword`, with CE's own generator, as a fixed list repeats).
    - The storage routes ask `StoragePort` (a `@Component`) for `healdan-core`'s port, through a seam tests set to a fake and put back (`volatile Supplier<List<StorageAdministration>> ports`; `FakeStoragePort` in `healdan-api`'s tests). None is `503 storage-unavailable` (`require()`), and the Stores routes answer a Store's `backend` and `pending` null instead. `StoragePort.run` answers the port's `SecretKeyMissingProblem` `409 secret-key-missing` with `detail` and `sealed`, and leaves its other refusals (`HealdanRuleException`s with the Storage tab's sentences, or the port's own) to `ProblemMapper`'s `409 refused`. A backend in the path the port doesn't give is `404`, any while storage backends are off. They check a form (`400`, `422`, the settings' `out-of-range` against `limits()`) before the port, and record nothing: the port records every storage change. Only the add's `AddedBackend` and Show Recovery Key's answer hold a recovery key; no answer holds an S3 secret (`AdminBackendsResourceTest#testNoAnswerRecordOrLogHoldsASecret`).
    - A Store's routes: `GET /v1/admin/stores` answers `StoreInfo` rows (`StoreInfos`: live matters in one grouped query, figures from `UsageSummary`, readers from `StoreService.access`, backend and pending from one port overview, null without it, while off, or when the overview can't be read, which is logged at warn by class only), for the menus and the Stores list alike. `PATCH` (`name` alone) and `DELETE /stores/{id}` answer Default, the Templates Store and the root `409 refused`, a sentence each (`StoreService.fixedFolder`), before a rename's own name counts, and anything else that isn't a live Store `404`; `GET /stores/{id}` answers all three `404`. The delete is `FolderChanges.deleteStore`, beside `deleteMatter` (`deleteForAdmin`: the tree's Delete, `refuseCheckedOut`, `trashTree`), one Trash item with the Store and its matters, answering `DeletedFolder`; the Store's files stay on its backend while it's in the Trash, for its restore, so the backend's `storesInTrash` names it; `GET /stores/deleted` lists the Stores in the Trash, deleted or removed; `POST /stores/{id}/restore` (the Store's folder id, no body) is `404` only for an id that names no Store, live or deleted, and `409 refused` for a live one. `store.deleted` and `store.restored` are recorded with `recordAfter`. `POST /stores` takes `backendId` (Original when absent), checked through the port before the create and given after it (`setStoreBackend`, its own transaction); a switch that fails in between, only in a race, leaves the Store on Original, `201`, logged at warn, with Original as the answer's `backendId` (`Store` answers `id`, `name` and `backendId`), so New Store says it was made on Original. `deleteStore` holds the Store's own folder lock, as `moveMatter` and New Matter's route do, so no matter is moved or made in a Store on its way to the Trash.
    - A Store's create, rename and restore hold the root's folder lock (`FolderChanges.withFolderLocks` on the root's id, taken in the resource around the service's transaction), so two of them can't give one name twice under the root (`AdminStoresResourceTest#testTwoCreatesOfOneName`, `#testTheRootsLock`).
    - The two lists read their matching rows in one query, then sort and page in Java (ties by number ascending whatever the `order`, nulls last both ways), the figures from `UsageSummary`, null with `figuresAt` until the first summary; but the Matters list sorted by number, its own order, which SQL pages (a count and a page), so a page reads only its own matters. A create that loses a race for its number (a unique index's SQLState 23505) goes through `NumberRaces`, which asks the number's check again so the answer is the used number's `409`.
    - A matter's move and delete are `FolderChanges.moveMatter` and `deleteMatter`, `move` and `delete` without the matter's-own-folder refusal, their refusals (`checked-out`, `immutable`, `name-taken`, …) answered `409 refused` with the same sentence and no `holds`. They, `deleteWorkspaceFolder`, `deleteTemplate` and `deleteStore` refuse anyone but an administrator first, `403 admins-only` (`ADMINS_ONLY`), as their routes already do, since every admin service checks for itself; `moveMatter` refuses a non-Store and any folder in the Store with the matter's folder's name, ignoring case, hidden ones too, never renaming it.
    - Every `/v1/admin/folders/{id}` route needs a class rooted at exactly `@Path("/v1/admin/folders")`, the id in its methods' paths: CXF matches methods only within the root classes whose path equals the best match's, or `PATCH /v1/admin/folders/5` reaches only one class and answers `405`. Each finds its folder through `WorkspaceRequests.folder(id)`, which is `WorkspaceAdmin.workspaceFolder`'s scope and its `404`, `AdminFolderAccessResource` too.
    - The workspace and template routes are four more `MATTERS` classes, each at its own exact root: `AdminWorkspaceResource` (`/v1/admin/workspaces`, the tree), `AdminFoldersResource` (`/v1/admin/folders`, beside the access routes: New Folder, rename, move, delete, the values, New Search Folder), `AdminSearchFoldersResource` (a search folder's rule; it's renamed only through `PATCH /v1/admin/folders/{id}`, so a body with `name` is `400`) and `AdminTemplatesResource`. A move's body `folderId` naming no workspace folder is `409 refused`.
    - Names go through `FolderRenames.name`, search folders' too, which refuses what Healdan doesn't keep in a name rather than let the name be changed. A change that gives a folder a name holds the lock of the folder the name goes into (`FolderChanges.withFolderLocks`, the public routes' locks, in id order: a rename its parent's, a create the folder it's made in, a move both parents', a template's create or rename the Templates Store's) and checks inside it that the folder hasn't moved meanwhile, so two changes at once can't give one name twice in a folder: the locks are what keep the names apart.
    - A folder's delete is `FolderChanges.deleteWorkspaceFolder` and a template's `deleteTemplate`: `deleteMatter`'s checks and Trash, each refusing for itself what its route doesn't take (`404` for a folder outside the workspace scope, or anything but a template's own folder; `409 refused` for a workspace's top folder through the folder route), and answering the Trash item (`DeletedFolder`). `/v1/trash/{id}/restore` answers a template's item, or a template's folder's, `409 place-gone`, as it restores into a Store only; the Classic Interface's Trash and its Deleted folders report restore them, into the folder open or chosen (spec §11).
    - The Monitoring routes (spec §8.8) are four `MONITORING` classes, each at its own exact root: `AdminErrorsResource` (`/v1/admin/errors`, over `ErrorStore` and `ErrorReview`), `AdminLogsResource` (`/v1/admin/logs`, over `LogFiles`), `AdminAuditResource` (`/v1/admin/audit`, a page and `export`, over `AuditFeed` and `AuditCsv`) and `AdminJobsResource` (`/v1/admin/jobs`, over `Jobs` and `JobControl`). `MonitoringView`, `AuditView` and `BackgroundJobView` hold the contract's records and cut a URL's user name and password (`UrlCredentials.cut`) from a fault's message and stack and a job's error. The services check their caller and record what they change; the routes record nothing, and no read, download or export is recorded. A malformed parameter (a window, an area, an `unresolved` that isn't exactly `true` or `false`, a position, a cursor, a zone, an id or doc # that isn't a whole number from 0 up, a day not of the years 0001 to 9999 written as `2026-11-22`) is `400` before a path's `404`; a schedule's fields `422` (a `mode` of any other value or type `invalid`, a wrong type for `intervalSeconds` or `cron` `400`); what a job doesn't allow now `409 refused` with `JobControl`'s sentence; an unknown job `404`, its name not echoed. The log's download and the export are `StreamingOutput`s, both `no-store`, whose files are checked (`LogFiles.zip` opens and closes each, `LogZip.writeTo` opens them again) or filters prepared and first page read (`AuditFeed.prepare`, `AuditCsv.open`) before the first byte, and a `HEAD` of either reads no file and no row. An unreadable log file is `UncheckedIOException`, `ProblemMapper`'s one error line and `500`.
