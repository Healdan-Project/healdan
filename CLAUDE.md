# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo, Healdan (`Healdan-Project/healdan` on GitHub), is a hard fork of LogicalDOC Community Edition (LGPLv3), a Java document management system. It started from 9.3.1 and follows upstream's releases; the root POM's version is the one it's on. It's detached from GitHub's fork network. The plan is to take it in its own direction (a new UI, bespoke features, replacements for features LogicalDOC sells as paid extras) while still merging upstream core and security fixes.

- Upstream is `https://github.com/logicaldoc/community.git`. A fresh clone needs `git remote add upstream <that url>`.
- Sync upstream by merging `upstream/master` into a dedicated branch and opening a PR to `master`. Merge, never squash or rebase, so the shared history stays intact; the repository allows only merge commits. Keep sync PRs free of feature work.
  - Existing databases never get LogicalDOC's schema changes (see "Docker"). When a sync changes LogicalDOC's tables, in a `logicaldoc-*` module's `sql/` scripts or in the columns an entity maps, add the SQL an existing PostgreSQL database needs, with a check, to the Install manual's Changes to LogicalDOC's Tables (`site/content/install/upgrading.md`) in the sync PR, a merge fix like the icons. Write it as that section says, fed to `psql` as the app's role in a heredoc inside the section (`docker compose exec -T db sh -c 'psql -U "$HEALDAN_DB_USER" -d "$HEALDAN_DB_NAME"' <<'SQL'` … `SQL`), the shape `docker/tests/test-init.sh`'s section 3c finds and runs; it lists none yet. While the move from MariaDB exists, a sync that adds, drops or renames a table or a column in LogicalDOC's scripts also fails CI's Move test: hold it and ask the owner (see the database bullet below).
- Healdan's own modules (`healdan-*`) follow upstream's version: their POM parent and `plugin.xml` version match the root POM's. A module left behind makes Maven look for stock LogicalDOC jars, which the build no longer fetches: it fails with `Non-resolvable parent POM … Could not find artifact com.logicaldoc:logicaldoc:pom:<old version>`. Bump the module instead.
  - When a clean sync merge brings a LogicalDOC release bump, `.github/scripts/upstream-sync.sh` adds a "Follow upstream to <version>" commit. After a conflicted merge it doesn't, so whoever resolves the conflicts bumps them too.
- Upstream changes `logicaldoc-core` and `logicaldoc-gui` the most. To keep syncs cheap, put new work in new plugin modules and avoid editing upstream files where possible.
- Upstream sometimes ships POMs that fail Maven validation (for example, a duplicate dependency). If CI fails within a minute, check POM errors, the icon check, the doc-links check, the hosts check, the Maven repository check, the database driver check and the web licence check (next bullets) first.
- The GUI bundles Font Awesome Free 6, but upstream writes the GUI against Font Awesome Pro. Pro styles (`fal`, `fa-light`, `fa-thin`, …) and Pro-only icon names compile fine and only show up at runtime, as blinking missing-icon placeholders.
  - `.github/scripts/check-fontawesome-icons.py` catches them. It runs first in `build-logicaldoc.yml`, and `build` must pass before a PR can merge. Run it locally with `python3 .github/scripts/check-fontawesome-icons.py`.
  - When it flags lines an upstream sync brought in, swap them for Free icons in the sync PR itself. That's a merge fix, not feature work.
- Nothing links to LogicalDOC's docs (docs, wiki, help or forums.logicaldoc.com). `.github/scripts/check-logicaldoc-doc-links.py` runs next to the icon check and fails `build` on one, naming the file and line. When a sync brings one in, point it at docs.healdan.com in the sync PR, a merge fix like the icons. Its `ALLOWED` list holds the few exact lines Healdan leaves alone, each with its reason (the `SystemInfo` defaults `HealdanSystemInfo` replaces). The docs site's pages are checked by `check-site-sources.py` instead, which allows no such link.
- Healdan never contacts LogicalDOC's servers (no statistics, registration, licence or news calls). `.github/scripts/check-logicaldoc-hosts.py` runs after the doc-links check and fails `build` on any host, URL or email address at logicaldoc.com, .it, .net or .org, naming the file and line. It skips tests, prose, the docs site and the SOAP, CMIS and WebDAV XML namespaces. When a sync brings one in, remove the call in the sync PR, a merge fix like the icons. Its `ALLOWED` list holds the exact lines nothing contacts, each with its reason.
- Builds get the artifacts only LogicalDOC's Maven repository has from Healdan's copies at `https://maven.healdan.com/` (repository `Healdan-Project/maven`), through a mirror of the `logicaldoc` repository in `docker/maven-settings.xml`. JAI, betelio, ksoap2 and Oracle's JDBC driver aren't among them: their licences don't allow hosting them, or they have none, so the build drops JAI, betelio and Oracle's driver, and leaves `logicaldoc-webserviceclient`, ksoap2's only user, out. `.github/scripts/check-maven-repositories.py` runs after the hosts check and fails `build` when a POM or the settings file points a repository at a LogicalDOC host the mirror doesn't cover.
  - Upstream's parent POM also declares two retired repositories: `java.net` (`maven.java.net`, whose certificate chain no longer validates) and `sourceforge` (`oss.sonatype.org`, Sonatype's retired OSSRH, which answers 404). Nothing comes from either, but Maven asks every repository for each version range's metadata, so a second mirror in the settings file, `retired-repositories`, sends both to Maven Central (§12 of the design spec). The check also fails `build` on a repository on either host under an id no mirror to Central or to Healdan's copies covers; when a sync brings one, add its id to that mirror's `mirrorOf` in the sync PR, a merge fix like the icons.
  - When a sync bumps one of those artifacts or brings a new one, the build fails with `Could not find artifact … in healdan`. In the sync PR, as a merge fix, check its licence allows hosting it, run `python3 import-artifact.py <group>:<artifact>:<version> --project … --licence …` in a checkout of `Healdan-Project/maven`, push, and re-run CI once `python3 import-artifact.py --verify https://maven.healdan.com/` passes. One whose licence doesn't allow hosting is dropped instead, as JAI was. A missing `com.logicaldoc:*` artifact is never imported: it means a module or version was left behind, so bump it. When the old GWT UI retires, its GWT libraries leave the build too (§3.1 of `docs/superpowers/specs/2026-10-29-healdan-maven-repository-design.md`).
- Healdan runs on PostgreSQL 18 only, and supports only open-source databases (Healdan-Project/healdan#110; the design is `docs/superpowers/specs/2026-11-18-postgresql-design.md`, the plan `docs/superpowers/plans/2026-11-18-postgresql.md`, and the facts `docs/reference/postgresql-recon.md`). Its own Java tests run on PostgreSQL 18 too, and upstream's on HSQLDB (see "Tests"). `HealdanMigrator` refuses any other database at start: MariaDB with a message that names the Install manual's Moving from MariaDB to PostgreSQL, and anything else, MySQL and HSQLDB included, with `Healdan's tables support PostgreSQL only; found …`. MySQL isn't supported and won't be added. Oracle and SQL Server are gone: the WAR ships neither driver and the setup wizard doesn't offer them (`docs/superpowers/specs/2026-11-01-open-source-databases-design.md`). CE's code paths for them (`isOracle()`, `isSQLServer()` and the branches they guard) and upstream's `.oracle` and `.mssql` SQL variants stay, as they never run and removing them would cost every sync (upstream edits core's schema files most months, and a deleted file would conflict each time). The wizard, which the container never runs, starts on PostgreSQL and still offers MariaDB and MySQL, and the WAR still ships MySQL's driver, though Healdan refuses to start on either (owner, 2026-11-01).
  - An install made on MariaDB moves its data across once with `move-from-mariadb`, a command in the image (`docker/tools/src/MoveFromMariaDb.java` and the `Move*` classes beside it; see "Docker"), from a source at `mariadb-final`, a tag made as the switch merges (the plan's Task 23), on the commit of `master` it merges onto, the last that runs on MariaDB, as the Install manual's Moving from MariaDB to PostgreSQL (`site/content/install/moving-from-mariadb.md`) gives it. MariaDB's driver stays in the WAR for it. Both stay until the owner says otherwise, about a month after the owner's server has moved (PostgreSQL spec §9.7); the removal (the plan's Task 26) deletes the command, `compose.move.yaml`, `test-move.sh` and its fixture, drops MariaDB's driver from the WAR (an upstream POM edit) and adds it to `check-database-drivers.py`.
  - Until then, an upstream sync that adds, drops or renames a table or a column in CE's scripts breaks the move or its test: the move makes CE's tables with the current scripts and refuses a table or column its MariaDB source lacks (`MovePlan`), and the test's check of the report fails on one only the source has, so the Move test, a step of the required `Test (amd64)`, fails and the sync can't merge as it is. Hold such a sync and ask the owner (the plan's Open Points for the Owner Before the Merge). Healdan's own migrations aren't affected: the move takes Healdan's tables to version 13 (`TARGET_VERSION`), the one that pairs with its version-12 source, and no further, and the app's first start applies any later one to the moved rows, as on any upgrade.
  - `.github/scripts/check-database-drivers.py` runs after the Maven repository check and fails `build` on a POM dependency on Oracle's or SQL Server's JDBC driver, or a tracked file naming one of their driver classes, naming the file and line. It skips tests, prose and the docs site. When a sync brings one in, take it out in the sync PR, a merge fix like the icons.
- The User app's npm packages ship in a page Healdan serves, so their licences matter. `.github/scripts/check-web-licences.py` runs after the database driver check and fails `build` on a package in `healdan-web/web/package-lock.json` that the app ships (no `dev: true`) with a licence outside MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC and 0BSD, or with none, or a development-only one outside those and BlueOak-1.0.0, CC0-1.0, CC-BY-4.0, Python-2.0 and Unlicense. It names the package and its licence. Its `ALLOWED` list holds the reviewed exceptions, each with the licence reviewed and its reason; an entry whose package the lockfile now gives another licence fails, and so does one the lockfile no longer has. `scripts/notices.mjs` writes the notices of what ships into `apps/user/dist/notices.txt`, and fails on a shipped package with no licence file, and on a `DECLARED_ONLY` entry (a reviewed package that declares its licence without a file) that the app no longer ships without one.
- `README.md` opens with Healdan's notice that it's a modified version of LogicalDOC CE, which the LGPL asks for, then its Status section (experimental, no warranty, use at your own risk), then points to the docs site. It's Healdan's own now: when a sync brings an edit to upstream's README, keep Healdan's. `Build_this_Sources.md` and `docker/README.md` are short pointers to the site.
  - The docs site's home page and the Install manual's first page carry the same status notice. Change all three together.
  - `GPL-3.0.txt` is the GPLv3, which the LGPL in `LICENSE` incorporates. It isn't named `COPYING`, because GitHub would then stop detecting the repository's licence as LGPL-3.0.

## Roadmap

- `docs/ROADMAP.md` holds Healdan's direction: who it's for, the glossary, the milestone order, and what's decided versus open for each milestone. Read it before starting feature work.
  - Healdan's *Store* and *Workspace* don't mean what LogicalDOC's `Store` and workspace mean. See its glossary.
  - Each milestone gets a design spec in `docs/superpowers/specs/` before anyone builds it. Update the milestone's status in the roadmap as it moves.
  - Superpowers' brainstorming, writing-plans, subagent-driven-development and executing-plans skills are for milestone-sized work, the kind that gets a spec. Work directly on fixes, reviews, docs edits, upstream syncs and other small changes: those skills' questions, plan documents and per-task subagents take far longer than such a change needs.
- `docs/reference/logicaldoc-ce-capability-map.md` records what CE already has, what's only hidden by GUI feature gates, what's half built and what's missing, with file paths. Check it before re-researching.

## Build and test

You need JDK 25 and Maven 3.9+, Docker for the `healdan-*` modules' test database (below), and on x86-64 a processor with AVX2 (x86-64-v3): `healdan-web`'s build runs Vite 8, whose Rolldown binary dies with `Illegal instruction` (exit 132) without it, as it does on a VM with QEMU's default processor type (the Install manual's Troubleshooting has the fix; `-Dhealdan.web.skip=true` skips that build). The JDK is the one the `Dockerfile`'s `MAVEN_IMAGE` and `TOMCAT_IMAGE` name; CI's `build` check reads it from there and fails if the two differ. `source.level` in `logicaldoc-parent/pom.xml` sets the Java language level, and the GWT client compiles at source level 17. Some dependencies aren't on Maven Central. They come from Healdan's copies at `https://maven.healdan.com/` and from `https://repo.terracotta.org/maven2`, which `docker/maven-settings.xml` lists. CI and the Docker build copy it to `~/.m2/settings.xml`; copy it there for local builds.

```bash
mvn -B -ntp -DskipTests install                          # full reactor build (what the Docker image runs)
mvn -B -ntp -pl logicaldoc-webapp -am -DskipTests package # deployable WAR -> logicaldoc-webapp/target/*.war
mvn -pl logicaldoc-core test                              # one module's tests (sibling modules must be installed first)
mvn -pl logicaldoc-core test -Dtest=DocumentManagerTest   # one test class
mvn -pl logicaldoc-core test -Dtest='DocumentManagerTest#testCopyToFolder' # one method
docker/tests/test-db.sh start                             # the PostgreSQL 18 healdan-*'s tests run on, at 127.0.0.1:5432 (`stop` removes it)
mvn -pl healdan-core test -Dtest=FilingRulesTest          # Healdan's tests, or one class of them
mvn -pl healdan-core -DskipTests install                  # healdan-core with its test-jar, which healdan-api's tests need
mvn -pl healdan-api test -Dtest=FolderResourceTest        # the API's tests, or one class of them
mvn -pl healdan-storage test                              # the storage module's tests (needs healdan-core installed with its test-jar, as healdan-api's do)
mvn -pl healdan-web test -Dhealdan.web.skip=true          # the web module's servlet tests, without the Node build (needs healdan-core installed with its test-jar too)
dotnet test clients/helper/Healdan.Helper.sln             # the desktop helper's tests (.NET 10 SDK; global.json pins it)
dotnet test clients/helper/Healdan.Helper.sln --filter "Category=MacKeychain" # the real macOS keychain, by hand on a Mac
HEALDAN_MAC_OFFICE=1 dotnet test clients/helper/Healdan.Helper.sln --filter "Category=MacOffice" # the real Word, Excel and PowerPoint, by hand on a Mac with Office (they open windows)
python3 -m unittest discover -s clients/libreoffice/tests -v # the LibreOffice extension's tests (standard library only)
node --test 'clients/office/test/*.test.js'               # the Office add-in's logic (Node 22+, nothing to install; Node 21+ takes the argument as a file pattern, so a folder fails)
cd healdan-web/web && npm ci --ignore-scripts             # the web apps' packages (Node 24, `.nvmrc`; Maven's build downloads its own into healdan-web/target/)
cd healdan-web/web && npm run generate                    # the apps' API types, from healdan-api's openapi.yaml and openapi-admin.yaml
cd healdan-web/web && npm run typecheck                   # tsc over the packages (tsc -p .), then each app as a program of its own
cd healdan-web/web && npm run lint                        # ESLint
cd healdan-web/web && npm test                            # the apps' and packages' Vitest tests and Node's runner for scripts/
cd healdan-web/web && npm run build                       # generate and typecheck, then Vite's builds into apps/user/dist/ and apps/admin/dist/
mvn -pl healdan-web -am -DskipTests package -Dhealdan.web.skip=true -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true # healdan-web without the Node build (its jar then holds no app) or the GWT compile
clients/libreoffice/build.sh                              # the LibreOffice extension, packaged as clients/libreoffice/healdan.oxt (reproducible)
dotnet run --project clients/helper/tools/IconRender      # the extension's toolbar images and icon, from the helper's icons (by hand, on a Mac)
clients/helper/packaging/mac/package.sh 1.2.3             # Healdan Helper.app and its .dmg, on a Mac; signed only with SIGN_IDENTITY set
clients/helper/packaging/linux/package.sh 1.2.3 amd64     # the Ubuntu 26.04 .deb (or arm64) in packaging/linux/out/; needs no signing
HEALDAN_HELPER_DEV_ROOT=/tmp/hh dotnet run --project clients/helper/Healdan.Helper # a Debug helper with its files and keychain entry apart; no links or .oxt, and no notifications on a Mac (on Linux they go through notify-send)
python3 docker/demo/build.py                              # the demo firm's files, from docker/demo/sources/ (needs a built image)
```

- `logicaldoc-parent` is a reactor module, and the root POM inherits from it, so dependency and plugin versions live there.
- `logicaldoc-gui` runs a GWT compile for each GWT module (frontend, login, setup), which is slow. Skip it with `-Dgwt.skipCompilation=true` when you aren't touching the UI; the module's Java still compiles, which `healdan-core` needs.
  - Up to `test` that's enough. For `package` or `install`, add `-Dmaven.antrun.skip=true` and `-pl '!logicaldoc-webapp'`, as CI's `build` check does. The GUI's antrun step fails without the GWT output, and skipping antrun leaves every plugin zip unfinished, so the WAR built from them is broken.
- `healdan-web` builds the User app and the Admin app (`healdan-web/web`, an npm workspace) through `frontend-maven-plugin`, which downloads Node into `healdan-web/target/` (the version in `.nvmrc`, which the POM names too: change both, as `scripts/workspace.test.mjs` fails until they match) and runs `npm ci --ignore-scripts` and `npm run build` in `generate-resources`; `maven-resources-plugin` then copies `apps/user/dist/` into the jar's `healdan/app/user`, which `AppServlet` serves, and (`copy-admin-app`) `apps/admin/dist/` into `healdan/app/admin`, which `AdminAppServlet` serves. `-Dhealdan.web.skip=true` skips Node, and each copy then does nothing when its `dist/` doesn't exist, so the jar holds no app and `/app/` answers 503, as `/admin/` does an administrator. CI's `build` check passes it everywhere; the `Web` check and the Docker build do the Node build (the Dockerfile keeps npm's cache in a mount).
  - The workspace's `.npmrc` sets `ignore-scripts` and `save-exact`, so a developer's own `npm install` runs no package's install script either and pins what it adds (`scripts/workspace.test.mjs` checks both).
- Spring-based tests fail in `setUp` unless `~/logicaldoc-dev.properties` exists. An empty file works; CI creates one.
- The `healdan-*` modules' tests need a PostgreSQL 18 server; upstream modules' tests don't (they run on HSQLDB in memory). `docker/tests/test-db.sh start` runs `postgres:18` as the container `healdan-test-db` on the Docker network `healdan-test` (made if missing), published on `127.0.0.1` at 5432 or `HEALDAN_TEST_DB_PORT`, user `healdan` (a superuser) and password `healdan-test`, its data on a tmpfs, with `fsync`, `synchronous_commit` and `full_page_writes` off and 300 connections, and the password hashed with one SCRAM iteration (`-c scram_iterations=1` to initdb, which hashes it), as each test opens about 40 connections and PostgreSQL's 4,096 iterations were most of what one cost; a server started before `start` passed the setting keeps its old hash until it's stopped and started. It waits for `pg_isready` over TCP and prints the URL for the host and for a container; run while it's up, it says so and exits 0. `stop` removes the container, and with it the databases and templates a killed run left. It removes the server for every run using it, so don't stop it while another run's tests may still be going.
  - The tests read `HEALDAN_TEST_DB_URL` (the server's JDBC URL without a database, by default `jdbc:postgresql://localhost:5432/`), `HEALDAN_TEST_DB_USER` (`healdan`) and `HEALDAN_TEST_DB_PASSWORD` (`healdan-test`), whose defaults reach the server `start` runs. With another `HEALDAN_TEST_DB_PORT`, set the URL `start` prints. Maven in a container joins `--network healdan-test` with `HEALDAN_TEST_DB_URL=jdbc:postgresql://healdan-test-db:5432/`.
  - With no server, each test fails in `setUp` with `Healdan's tests need a PostgreSQL. Start one with: docker/tests/test-db.sh start`.
- `healdan-core`'s, `healdan-api`'s, `healdan-storage`'s and `healdan-web`'s tests run against the installed jars of the modules they use. After changing `logicaldoc-core`, `logicaldoc-webapp` or `logicaldoc-gui`, re-install that module (`-pl <module> -DskipTests -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true install`) before running them.
- `healdan-api`'s, `healdan-storage`'s and `healdan-web`'s tests also need `healdan-core` installed, test-jar included: they reuse its `AbstractHealdanTestCase`, fixtures and test `context.properties`. Re-install it after changing `healdan-core`.
  - `-DskipTests` still compiles tests, so it builds and installs that test-jar. `-Dmaven.test.skip=true` doesn't, and their `with-tests` profiles then leave the test-jar dependency out, so the build works but `healdan-api`'s, `healdan-storage`'s and `healdan-web`'s tests can't run until `healdan-core` is installed with `-DskipTests`.
- `master` takes changes only through pull requests. Its ruleset, `master: require CI`, requires `build`, `Test (amd64)`, `Test (arm64)`, `Clients` and `Web` (not strict: a branch needn't be up to date), blocks force pushes and deletion, and has no bypass, so it binds the owner's account and every session using it. Issue Healdan-Project/healdan#9 has the reasons.
- CI's `build` check compiles every module except the WAR, skipping the GWT compile, and runs Healdan's tests in parallel shards. The Docker image CI does the GWT compile and the WAR. Upstream modules' other tests don't run in CI.
  - The tests are every test class in a `healdan-*` module (found without a list) and the upstream tests named in the workflow's `UPSTREAM_TESTS`, which cover Healdan's edits to upstream code. Add a test class there when a change edits upstream code. A name no upstream module has fails the check.
  - The `checks` job runs the quick checks, then `.github/scripts/test-shards.py` splits the tests into shards of about five minutes (at most eight). Each class weighs its time in the newest successful run, which the `test-times` job caches, or 3 s per `@Test` until it has one. Each `Tests (n of N)` job installs the modules, without javadoc or plugin zips, and runs its share. The `build` job, the check master requires, passes when they all did, or when a docs-only pull request skipped them.
  - Each `Tests (n of N)` job has a `postgres:18` service container, which its tests share, each making its own database. It publishes no port: a step gives the tests its container's own address in `HEALDAN_TEST_DB_URL`, as a connection to a published port goes through Docker's proxy, which doubled a statement's round trip on a runner (46 µs without it, 89 with; about 0.09 s a test). It runs as `test-db.sh`'s does (the same user, password, locale, tmpfs and settings), through `POSTGRES_INITDB_ARGS`' `-c` flags and `--tmpfs` in the service's `options`, as every test makes a database and opens about 40 connections.
  - Its Maven repository cache falls back to master's newest copy, and only master saves it (from one shard), so a POM edit downloads only what it adds.
  - The repository has 10 GB of Actions caches, and GitHub evicts those used least recently beyond that. The Docker build's layer cache at `mode=max` (about 5 GB a master push) fills that and evicts the `m2-` copy, and until a master run's saving shard passes and saves a new one (`actions/cache` saves only from a job that passed), every shard downloads everything. So the image build's layer cache is `mode=min` (see "Docker"). Check `gh cache list --repo Healdan-Project/healdan` before adding a cache that's large or saved often.
  - Each shard deletes the restored copy's `_remote.repositories` files, so Maven uses every cached file whichever Maven saved it. Maven 3.9 records a file's repository by id and 3.10 by id and URL hash, and 3.9 rejects 3.10's. `ubuntu-latest`'s images ship both, so without the deletion a shard on the other Maven downloads everything again.
  - The Docker build doesn't need this: its `maven:3.9` image writes and reads its own copy, and 3.10 accepts 3.9's records.
  - A shard whose restore of the copy was an exact hit (its POMs those the copy was saved for) passes Maven `-nsu` (`MAVEN_METADATA` in the workflow), so a version range's list of versions (Bouncy Castle's own POMs have a range) and an unversioned plugin's come from the cached copy, and Maven asks a repository only for what the copy lacks. Without it Maven asks every repository again on each new day (UTC). A failed connection falls back to the copy, but an answer of "not found" doesn't: the build stops at `No versions available for org.bouncycastle:bcutil-jdk18on:jar:[1.81,1.82) within specified range`, with no warning (two shards on 2026-11-19, both on runners in another cloud than the rest). The saving shard still asks, so each copy it saves has that day's lists, and so does the Docker build, since what it resolves is what ships.
- `.github/scripts/code-changed.sh` writes three outputs for a pull request (a push gets all true):
  - `code` is false when it changes only docs (`docs/`, `site/`, Markdown outside `src/`), `clients/helper/`, `clients/libreoffice/`, `clients/icons/`, or any of them. The Java and Docker workflows then skip their build steps and still report the required checks. A change under `clients/office/` counts as code as well as clients, because `healdan-api` packages the Office add-in's pages and manifest into its jar (Markdown there stays docs).
  - `clients` is true when it changes anything under `clients/`, `clients.yml`, or the API contract (`healdan-api`'s `openapi.yaml`, which the helper's contract tests read; not the admin API's `openapi-admin.yaml`, which they don't read). `clients.yml` otherwise skips its test jobs.
  - `web` is true when it changes anything under `healdan-web/`, `web.yml`, or either API contract (`openapi.yaml` or `openapi-admin.yaml`; the apps' types are generated from them). `web.yml` otherwise skips its app job.
- `.github/workflows/clients.yml` runs the helper's `dotnet test` on `ubuntu-24.04` and `macos-15`, the extension's Python tests on `ubuntu-24.04`, and the Office add-in's `node --test` there too. Its `Clients` job passes when they did, or were skipped because nothing under `clients/` changed. `Clients` is one of master's required checks.
  - A `helper-v1.2.3` tag (or a run by hand) also runs `package-mac`, which packages the macOS helper with `clients/helper/packaging/mac/package.sh`, and `release-mac`, which attaches the `.dmg` to the tag's release, only for a pushed tag and once `xcrun stapler validate` passes on it. They never run for pull requests, and `Clients` doesn't need them.

## Docker

- `Dockerfile` (stages `build` → `tools` → `runtime`) and `compose.yaml` are this fork's own. The docs site's Install manual (`site/content/install/`) is the user guide, and its Developer Guide covers the dev overlay, tests and CI; the design is `docs/superpowers/specs/2026-10-15-docker-compose-stack-design.md`, and the database's `docs/superpowers/specs/2026-11-18-postgresql-design.md` (cited below as "PostgreSQL spec").
- The container never runs the setup wizard. `docker/tools/src/DockerInit.java` (the start-up tool) seeds `context.properties` and, on a fresh database, creates the schema by running the `DbInit` scripts from every `plugin.xml`, each plugin's generic script (`DBMS = postgresql`, which has no variant), so a plugin's `DbInit` extension is picked up for new installs. Then, on every start, it installs any of CE's plugins not yet installed with CE's own `PluginRegistry`, before Tomcat starts, so a fresh stack's sign-in page doesn't say "The application has to be restarted" (§15 of the Docker spec); the entrypoint puts the conf folder on its classpath for them. Existing databases are never migrated, apart from Healdan's own `hd_` tables, which Flyway upgrades on every start (see "Healdan's code"). A plugin or upstream change that adds SQL to CE's tables needs it applied by hand there.
  - On every start against an existing database, `DockerInit` checks that CE's tables have every table and column the plan's `DbInit` scripts create (`DbInitPlan.createdColumns`, against `information_schema.columns` in `current_schema()`), and stops, naming each missing one and pointing to the Install manual's Changes to LogicalDOC's Tables, before Tomcat starts. It never adds them, and what a database has besides doesn't count. A table a later plugin's script creates stops it too, as nothing else would create it (§16 of the Docker spec). A fresh database's start runs the same check after `DBInit`.
  - Its order (PostgreSQL spec §8.2, §8.3): the trusted proxies; the guard, which writes nothing; the conf volume's keys; the checks of the server and database; the role's lock timeout; then the schema, or the check of CE's tables, and the plugins. Its probes ask `to_regclass` and never read a table that may be missing, so a start puts no `ERROR` line in PostgreSQL's log.
  - **The guard** (`StartGuard`) stops the start, changing nothing in the conf volume or the database, with one of three messages, each naming its page: `MOVE_FIRST` when the conf volume's `jdbc.url` or `jdbc.dbms` names MariaDB (or MySQL) and PostgreSQL holds no move at all (no `docker_move` table) or doesn't answer within `ANSWER_SECONDS` (15, not `DB_WAIT_SECONDS`, as `DB_HOST` may still name the MariaDB server); `MOVE_AGAIN`, whatever the conf names, when the database holds a move that didn't finish (a `docker_move` row with no `finished`, or a `docker_move` table with no row); and `RESTORE_FIRST` when the database is empty and Original's folder (`repository/docs`) holds anything, a folder it can't list included. It reads the conf file, and `context-override.properties` beside it, with a plain `Properties.load`, as `ContextProperties`' constructor touches the file. A fresh install passes all three.
  - **The checks** (`DockerInit.checkDatabase`, which the move shares; `DbChecks` decides) refuse a server older than PostgreSQL 18, a database that isn't UTF-8 and a role that can't create tables in its schema, and warn (`WARNING:` lines) of a major newer than 18 and of a collation that doesn't sort by code point. Then `alter role … in database … set lock_timeout = '50s'` gives the app's role PostgreSQL spec §7.4's lock timeout, which every connection of the role takes, Tomcat's pool and Flyway included; it's read back on a new connection, and a refused `alter role` stops the start.
  - **`jdbc.url`** is `jdbc:postgresql://<DB_HOST>:<DB_PORT>/<DB_NAME>?logServerErrorDetail=false` (`ConfigPlan.jdbcUrl`, which refuses a `DB_HOST` or `DB_NAME` outside `ConfigPlan.HOST` and `DATABASE`, the rule the move checks its source by, so nothing can cut the parameter off): without the parameter pgjdbc puts the server's detail, the failing row's values, into every `SQLException`'s message, and no log line may print a row's values. PostgreSQL's own log keeps the detail, and the move's connections use the same URL.
- On every start, keys in the image's default `context.properties` that the conf volume lacks are added. Values are never overwritten, with four exceptions:
  - `product.release` and `product.year` (`ConfigPlan.IMAGE_KEYS`) describe the image, so they're always taken from it.
  - A key still holding a default an earlier image shipped takes the image's (`ConfigPlan.REPLACED_DEFAULTS`); an admin's own value stays. So far that's `cachecontrol`, whose `*.nocache.js:no-cache` makes browsers check the GWT loaders on every load. When Healdan changes a default that existing installs should get, add the value it replaces there.
  - Non-breaking spaces (0xA0) in `security.csp` (`ConfigPlan.PLAIN_SPACE_KEYS`) become plain ones, in an admin's policy too, and the rest of the value stays. Upstream's value had one after `object-src`, so browsers ignored `object-src 'none'`.
  - The four keys Healdan owns (`ConfigPlan.HEALDAN_KEYS`) are set whatever the file holds, and `DockerInit` reads each back. `store` is `com.logicaldoc.healdan.storage.HealdanStorage`, so `healdan-storage`'s `HealdanStorage` is CE's `store` bean while the image's defaults, upstream's, keep `FSStore`; an install moves to it on its first start on an image that has it, its files staying where they are. `jdbc.driver` (`org.postgresql.Driver`), `jdbc.dbms` (`postgresql`, as CE's `isPostgreSQL()` and `StatsCollector` spell it) and `hibernate.dialect` (`org.hibernate.dialect.PostgreSQLDialect`) are PostgreSQL's, so a conf volume a MariaDB install wrote is put right at its first start after the move; the old version, which seeds them once, then fails on that volume, so the Install manual's Going Back puts them back by hand. Outside Docker the keys are what the file says (`FSStore` by default, and `healdan-storage` then does nothing), and an install there gets none of the start-up tool's work: the Developer Guide's Building from Source says what to set by hand.
- **The `db` service** is `postgres:18` (PostgreSQL spec §6, §8.1), its data in the volume `pg-data` at `/var/lib/postgresql` (the image keeps it in `18/docker` there, and a later major's image starts its own folder beside it, so a new major is a dump and restore, as the Install manual's Upgrading gives it). `POSTGRES_INITDB_ARGS` is `--encoding=UTF8 --locale-provider=builtin --builtin-locale=C.UTF-8 --locale=C --auth-host=scram-sha-256 --auth-local=trust`: the image's own `pg_hba.conf` trusts loopback TCP, so `--auth-host` makes every TCP connection ask for a password, and the socket stays trusted for backups and `docker compose exec db psql -U postgres`. `docker/postgres/10-healdan-role.sh`, mounted into `/docker-entrypoint-initdb.d/`, runs once on an empty data folder: it makes the app's ordinary role (`DB_USER`) and its database (`DB_NAME`, owned by it, from `template0`, in the built-in `C.UTF-8`) and takes the superuser's password away. First, a TCP rule of `pg_hba.conf` whose method is `trust` (which `--auth-host` leaves none of) is made `scram-sha-256` rather than refused, as the image never runs the script again on the data folder a refused start leaves, and the restart would serve the file as it is. It refuses an empty setting, a `DB_USER` that is the superuser's name or begins `pg_` and a `DB_NAME` of `postgres`, `template0` or `template1` before any statement, sets `log_min_error_statement = panic` first so a failing statement never logs the password, and exits 1 on any failure. The health check is `pg_isready` over TCP (the first start's temporary server listens on the socket only), then the app's role's `select 1` over the socket, so a first start the script refused never reads healthy. `compose.dev.yaml` publishes it on `127.0.0.1:${DEV_DB_PORT:-5432}`, the port `docker/tests/test-db.sh`'s server takes too: to run both, set `DEV_DB_PORT`, or `HEALDAN_TEST_DB_PORT` with the URL `start` prints. MariaDB's old volume, `db-data`, is named only in `compose.move.yaml`, so nothing else mounts or removes it.
- **`compose.move.yaml`** adds `mariadb` (`mariadb:11.4` on `db-data`, with the old `db` service's character-set flags) for `docker compose -f compose.yaml -f compose.move.yaml run --rm app move-from-mariadb [--replace-nul]`. The entrypoint acts on `move-from-mariadb` before anything else (no owner changed, no conf seeded, no folder made) and runs `MoveFromMariaDb` as the app user in place of the start-up tool and Tomcat. The source is `MOVE_SOURCE_HOST` (`mariadb`), `MOVE_SOURCE_PORT` (3306) and `MOVE_SOURCE_NAME`, `_USER` and `_PASSWORD` (each defaulting to its `DB_` variable).
  - Its steps are in `MoveFromMariaDb`'s Javadoc and the spec's §9, and how it reads MariaDB (dates as text, the binary protocol, MariaDB's own tallies) in the plan's Decision Log 35. It refuses a source not at version 12 (`SOURCE_VERSION`), and a target holding anything but its own unfinished move: an unfinished move beside `docker_init` is refused too, never emptied, as only a started database has both. It makes Healdan's tables at version 13 (`TARGET_VERSION`) and no later one. It never writes to MariaDB or touches the volumes or a storage backend, and prints no row's value, password or URL with a password. Any failure leaves the target unfinished, which the guard won't start on and the next run starts over; `Move complete.` is its last line, printed once both connections are closed.
- The app has three volumes: `logicaldoc-conf` (`/opt/logicaldoc/conf`), `logicaldoc-repository` (`/opt/logicaldoc/repository`) and `logicaldoc-cache` (`/opt/logicaldoc/cache`, `healdan-storage`'s read cache, which only holds copies, so backups leave it out). The entrypoint hands all three to uid 1000 at every start, and goes on when a share refuses but uid 1000 can write to it. `setenv.sh` names `healdan-storage`'s folders: staging (`healdan.storageStaging`, `repository/staging`), the cache (`healdan.storageCache`) and the backends' key files (`healdan.storageKeys`, `conf/healdan-storage-keys`).
- `docker/server.xml`'s `RemoteIpValve` believes `X-Forwarded-For` and `-Proto` only from `LOGICALDOC_TRUSTED_PROXIES`, or, when it's unset, the Docker networks the container is on. `DockerInit` (`TrustedProxies`) works the list out and checks it on every start, and `setenv.sh` passes it to Tomcat as `healdan.trustedProxies`.
- LogicalDOC only runs external programs listed in a classpath `allowed-commands.txt`. The lines in `docker/allowed-commands.txt` are re-added to the conf volume's copy on every start; a new external tool needs a line there.

## Architecture

**Modules.** `logicaldoc-util` sits at the bottom. `logicaldoc-core` builds on it, and the feature modules build on core: `webservice` (REST via CXF; Healdan's `SoapRemover` removes its SOAP endpoints), `webdav`, `cmis`, `dropbox`, `android` and `ios`. `logicaldoc-webapp` is the WAR that bundles everything. `logicaldoc-gui` (GWT client) depends only on util. `logicaldoc-i18n` holds the resource bundles.

**Plugin system (JPF).** Almost every module is a plugin, and adding a plugin takes four pieces:
- `src/main/resources/plugin.xml` declares the plugin's ID, its dependencies and the extensions it contributes.
- A class extending `com.logicaldoc.util.plugin.LogicalDOCPlugin` registers servlets at install time with `addServlet(...)`. That edits `web.xml`, so a restart is required. It can also register scheduled tasks and loggers.
- `src/main/assembly/assemblyplugin.xml` packages a `*-plugin.zip` (classifier `plugin`). It takes only the dependencies its `<include>`s name, not theirs, and the WAR's `WEB-INF/lib` is the webapp's own dependencies and those zips' jars. So a library's own dependency ships only when some zip names it: core's names `org.apache.poi:*` but not POI's SparseBitSet, which `healdan-core`'s zip ships (#202). `docker/tools`' `WarParsersTest` catches one missing for POI's PowerPoint and Excel readers, not for other parsers, and its `WarStorageTest` one missing for the AWS SDK's and Tink's jars, which `healdan-storage`'s zip ships.
- An `artifactItem` in `logicaldoc-webapp/pom.xml` (maven-dependency-plugin) copies that zip in, and an antrun step unzips it into the WAR. Without this entry, the plugin isn't shipped.

Core's `plugin.xml` defines the extension points other plugins hook into: `DbInit`, `Parser`, `Language`, `ResourceBundle`, `Task`, `DocumentListener`, `FolderListener`, `UserListener`, `TicketListener`, `Authentication`, `ThumbnailBuilder`, `FormatConverter`, `Search`, `Feature`, `SystemInfo`, `TokenFilter`, `Store`, `Aspect` and `TokenProvider`. `logicaldoc-dropbox` is the smallest complete example of a plugin.

**Spring wiring.** `web.xml` boots `com.logicaldoc.util.spring.MainContext`. It component-scans `com.logicaldoc` for `@PluginContext` classes and imports the webapp's `context.xml`, which defines the datasource, session factory and transactions.
- Each module has a `XxxContext` class annotated `@PluginContext` + `@ComponentScan` + `@ImportResource("classpath:context/context-xxx.xml")`.
- Runtime settings come from `context.properties`, read through `ContextProperties`, which `Context.get().getConfig()` returns.
- Beans are fetched with `Context.get(Type.class)`, and DAOs expose a static `XxxDAO.get()`.
  - A bean definition Spring can't make must be `abstract`. To learn what a `FactoryBean` makes, a lookup by type makes every one not yet made, lazy ones too. One that fails is made again at the next lookup, as the failure empties Spring's cache of names by type, and Spring 6.2 records each failure without a lock, so two lookups at once could throw and answer a request with a 500 (`TransactionProxyTemplateTest`).
- **Both Spring and Hibernate only scan `com.logicaldoc`.** Code in any other package root isn't discovered unless you extend the scans.

**Persistence.**
- Hibernate 7 uses JPA-annotated `@Entity` classes, which `com.logicaldoc.util.spring.LocalSessionFactory` finds by classpath scan. The `*.hbm.xml` mapping location in `context.xml` is configured, but no such files exist.
- DAOs follow one pattern: an interface `XxxDAO extends PersistentObjectDAO<T>` and an implementation `HibernateXxxDAO extends HibernatePersistentObjectDAO<T>`.
- Every `PersistentObject` has a `tenantId` (multi-tenant).
- CE has no migration tool (Healdan's own tables use Flyway, below, with one folder of scripts, PostgreSQL's). CE's schema is plain SQL in `sql/logicaldoc-<module>.sql`, with DBMS-specific variants (`.mysql`, `.mariadb`, `.oracle`, `.mssql`) that `PluginDbInit` picks when one exists; there's none for PostgreSQL, so the stack, the move and Healdan's tests make CE's tables from the generic scripts (the move's check of its MariaDB source reads the `.mariadb` ones). Plugins add tables through a `DbInit` extension with a `sqlFile` parameter.
- CE maps Java `boolean` fields onto `int` columns, which PostgreSQL refuses a boolean for. `healdan-core`'s `src/main/resources/hibernate.properties` sets `hibernate.type.preferred_boolean_jdbc_type=INTEGER`, which Hibernate reads at its start, so it binds every `boolean` as an integer (`BooleanBindingTest`; `AbstractHealdanTestCase` checks it first in every test; `WarHibernateTest` that the WAR has no other `hibernate.properties`, as Hibernate reads only the first). A flag in Healdan's tables is an `int` column and an `int` field too.
- `HibernatePersistentObjectDAO`'s typed single-value reads (`queryForObject`, and `queryForList`'s single-column form, through `processQueryForListRecord`) hand the driver's value to the fork-owned `HealdanTypedReads` (`logicaldoc-core/.../core/HealdanTypedReads.java`, beside `HealdanHooks`), which converts an exactly held number (integer, `BigInteger`, `BigDecimal`) in Java: to `Long` or `Integer` when it fits exactly, and to `Double`, `Float`, `BigDecimal` or plain text; anything else goes to `getObject(1, type)` as before. pgjdbc refuses a `Long` from an `int` or a `numeric`, and the refusal rolls back the caller's transaction at its commit, silently (`HealdanTypedReadsTest`, in `UPSTREAM_TESTS`; `TypedReadsOnPostgresTest`).
- Healdan's SQL is written for PostgreSQL alone (spec §7.3 of `docs/superpowers/specs/2026-11-18-postgresql-design.md`). On PostgreSQL a failed statement ends its transaction, whatever Java catches, so no statement of Healdan's is expected to fail inside a transaction. An insert that may find its key taken says `on conflict` and names its key, so a unique index added later still fails loudly: `PreviewJobs.add`, `StoredFiles.recordWrite` (`(hd_docid, hd_resource)`) and `HeldCopies.hold` (`(hd_backendid, hd_location)`) do nothing, and `EmailIndex.put` updates. Work that may fail without failing its caller runs inside a savepoint: `healdan-core`'s `com.logicaldoc.healdan.util.Savepoints` (`run`, which rolls back on any `Throwable`, and on a release that fails; `inTransaction`, whether a template's statements are the caller's transaction's). The listeners that log and swallow a failure inside CE's save (`EmailDocumentListener`, `PreviewDocumentListener`) run their statements in one: `PreviewDocumentListener` keeps its Java-only guard (the event, an Office file name) outside, as a savepoint is two round trips on every save, and `EmailDocumentListener` puts the whole of its `try` inside. The two favourite-names listeners need none: their `afterStore` reads the row before the store from the dictionary or the session's map, and follows the rename in a transaction of its own. SQL given to CE's DAO helpers never uses `::`, which `NamedParameterStatement` reads as a parameter: write `cast(x as text)`. Where a person types a value SQL compares, trim it in Java first (PostgreSQL compares trailing spaces, MariaDB didn't), and give an `order by` on a key that can be NULL its `nulls first` or `last`.
- Every connection of the app's role waits 50 seconds at most for a lock (`lock_timeout`, set by the start-up tool; see "Docker"), so a lock cycle such as `FileLocks`' ends by failing one transaction, which its callers retry or mend.
- The second-level cache is Infinispan (`infinispan.xml`, or `infinispan-cluster.xml` when clustering is on).

**UI ↔ server.** The UI uses GWT 2.12 and SmartGWT 14.1, with GWT modules `frontend`, `login`, `setup` and `common` under `com.logicaldoc.gui`.
- RPC calls go from interfaces in `gui/**/client/services` (`@RemoteServiceRelativePath`) to `logicaldoc-webapp/.../web/service/*ServiceImpl`, mapped in `logicaldoc-webapp/src/main/webapp/WEB-INF/web.xml` under `/frontend/*`.
- Grid and list data come from `web/data/*DataServlet`, which serves XML for SmartGWT DataSources at `/data/*.xml`.
- Other ways into the server are REST at `/services/rest/*` (`logicaldoc-webservice`, endpoints in `webservice/rest/endpoint`; `healdan-core`'s `SoapRemover` removes the module's SOAP endpoints at startup), WebDAV at `/webdav/*`, and CMIS.

**Edition feature gating.**
- The GUI shows or hides features with `Feature.enabled(n)`, which checks for the name `Feature_<n>`.
- Those names come from `Feature` extensions declared in plugins' `plugin.xml` (collected by `SystemInfo`).
- The GUI already contains client code for enterprise-only features whose server implementations aren't in this repo, for example the `ai`, `google`, `onlyoffice`, `saml` and `whatsapp` service interfaces.
- Replacing a paid extra therefore means three things: implement that RPC interface on the server, register its servlet, and declare the matching `Feature_<n>` extension.

## Healdan's code

- **`healdan-core`** is Healdan's plugin module (JPF id `healdan-core`, which requires `logicaldoc-core`). It holds Healdan's server rules and all its data, under `com.logicaldoc.healdan`, so CE's Spring and Hibernate scans find it with no edits.

  - Text Healdan stores may hold anything but NUL and a lone surrogate, emoji included (`util.StorableText`, PostgreSQL spec §7.5). Where a person types it, `holds` refuses it, with a message ending `StorableText.CANT_KEEP` ("characters Healdan can't keep") that names neither emoji nor the database. Where it comes from a file or a provider (an email's headers and file names, a provider's claims), `clean` puts a space for NUL and U+FFFD for a lone surrogate, and `cut` shortens without splitting a surrogate pair. `healdan-api` answers such text `400 bad-request`: `TextFilter` (`@PreMatching`, so a request signed out gets `400`, not `401`) for a query parameter, and `ApiJson`'s two deserialisers for text anywhere in a JSON body, `JsonNode` trees included, which `ProblemMapper` names by field; `openapi.yaml`'s header says the rule once. The previews and the email index report from each `runOnce` round, the mover from its sweep and `runOnce()`, and the Trash destroyer and the storage retests, purge, alert and nightly check from their schedulers only (a direct call reports nothing; Phase 5's Run Now must report). `Jobs.all()` lists Healdan's eight in `Jobs.ORDER` (the storage ones wherever `healdan-storage` is, and on `FSStore` servers switched off: `HealdanJob.enabled()`, which `healdan-storage`'s `StorageJob` answers from `StoreTracking.active()`), then CE's six tasks from `TaskManager`: last start is the schedule's previous fire time, last end that plus its last duration once idle, next run the next fire time. A task's error is the latest `ErrorStore.latest` has from its logger since its last start, so any ERROR during a run fails it, but `Task.run`'s "The task is stopped" and "The task gets interrupted" (`NOT_FAILURES`). The email index is `done` once `email.index` says so. `JobView.overdue`: switched on, not running, next run more than twice its interval past (from the last end, or a CE task's last start) and an hour at least. `JobView` has no schedule: CE's schedules wait for Phase 5's Background Jobs screen.
  - `DashboardService` (`admin.dashboard`, spec §8.1) makes Needs Attention (eight codes, `AttentionItem`), `unchecked` (codes whose source couldn't be read) and Server Health (ten tiles, `HealthTile`) in one `read()`, each from its own source: the storage port (stuck files, backends `unreachable` or `failing`; no port is nothing to check unless `store` is `HealdanStorage`), `IndexCounts.counts()`, `ErrorStore.unresolved` (faults in 24 hours and the latest's time, one query), `PreviewJobs`' counts, `Jobs.all()`, the volumes of `store.1.dir`, `index.dir` and `conf.logdir` (`DISK_LOW_PERCENT`, 85, a constant), JDBC's product and version with `pg_database_size` or MariaDB's `information_schema.tables` for `getCatalog()`, `ProviderClient.answers` per enabled provider at most every 5 minutes (a fetch whose failure isn't remembered, so it never fails a sign-in), and CE's `EMailSender` logger's unresolved errors in 24 hours. Each source is `Cached` for a minute (the database's five), worked out again once on a virtual thread `healdan-admin-dashboard`, the last answer served while younger than twice that; a request waits only for a source with none, 5 seconds at most for all, then it's still being worked out. A read running past its `maxAge` is stuck (`Cached.Stuck`, logged once, answered at once, not waited for), and one past ten times that is given up on and read again. `Dashboard.readAt` is the oldest answer's time, which the page's Updated shows. A job both failed and overdue counts as failed only. A failed or unfinished source puts its codes in `unchecked` and gives its tiles `problem` with status `attention`, logged at warn by class only. Links come from `DashboardService.Screen`, `/frontend.jsp` until each screen ships; Clients, Matters, Workspace Templates, Stores, Backends and Users (`/admin/users`) have their Admin addresses (`DashboardScreensTest`): `files-stuck` links to Stores, or to Backends when only files with no Store are stuck (`Found`'s screen), and `backend-unreachable`, `disk-low`, the Storage Backends tile and the Disk tile to Backends, but `disk-low` and the Disk tile to the Classic Interface where storage backends are off (no item or tile links to Clients, Matters, Workspace Templates or Users yet), and the Admin app's `ServerLink` opens a link to one of its own screens with the router, a modified click, another origin and the Classic Interface left to the browser. `AdminDashboardResource` serves it at `GET /v1/admin/dashboard`. ## Tests

- Tests use JUnit 4. The base class `com.logicaldoc.util.junit.AbstractTestCase` builds a Spring context from the module's test `context.xml` and `context.properties`.
- For upstream modules, that context includes an in-memory HSQLDB loaded from `getDatabaseScripts()`. For core, that's `sql/logicaldoc-core.sql` plus the test `data.sql` fixture data. Upstream's tests, those in CI's `UPSTREAM_TESTS` included, stay on HSQLDB and never touch an `hd_` table.
- Each module has its own base class, such as `AbstractCoreTestCase`, `AbstractWebappTestCase` or `AbstractWebserviceTestCase`. Extend the closest one.
- `healdan-core`'s `AbstractHealdanTestCase` runs every `healdan-*` test on PostgreSQL, a database of its own per test (`TestDatabase.createParked(databaseScripts())`; each name carries a number unique to its JVM, so the modules' suites can share one server at once), made before the context and dropped (`with (force)`) once upstream's `tearDown` has run. It hands `AbstractTestCase` no scripts (`getDatabaseScripts()` is final and empty, so upstream's HSQLDB steps do nothing), checks the boolean setting is in force, puts the database's tables in place (`TestDatabase.unpark`), empties the store (`store.1.dir`), since ids restart with each test's database while the store under `target/` stays, and runs `HealdanStartup.run()`, which finds the migrations applied and runs the seeds.
  - A test's database is a copy of a template (`create database … template`, about 20 ms where loading the scripts and migrating took about 130). The JVM's first test with a given `databaseScripts()` (`sql/logicaldoc-core.sql`, `data.sql`; what subclasses override) makes the template: an empty database from `template0` (UTF-8, `locale_provider builtin builtin_locale 'C.UTF-8' locale 'C'`, whatever the server's default, as `TestDatabase.create()` still makes one for the tests that want it empty), the scripts loaded through HSQLDB's `SqlFile`, then `HealdanMigrator`'s migrations, with no Spring context. The JVM drops its templates as it ends. A row the scripts or the migrations insert carries the template's time, not the test's; the seeds still run in every test, in its own context.
  - The template's tables are parked: in the schema `healdan_parked`, off the search path, beside an empty `public`. The context has to start with no CE table in sight, as it did on an empty database: `HealdanStartup`'s `@PostConstruct` then finds no CE schema, so it runs no seed before the store is emptied and starts no worker or start listener. `unpark` drops the empty `public` and renames the parked schema to it, in one transaction, and fails if anything was made in `public` meanwhile (`TestDatabaseTest`). Never copy a template with its tables in `public`.
  - Its `getConfigResource()` is final: it writes `baseConfigResource()` (`context.properties`; what subclasses override) again as `pg-<base>` with the test's `jdbc.url`, user and password. For `context.properties` it starts from `pg-context.properties` while that is at least as new as the base, as CE writes changed settings back and a later test reads them, so an edit to the test `context.properties` reaches the next run. The test `context.properties` says `jdbc.driver=org.postgresql.Driver`, `jdbc.dbms=postgresql` and PostgreSQL's dialect, and the test `context.xml` reads `${jdbc.driver}`.
  - HSQLDB's jars stay on Healdan's test classpath: upstream's `AbstractTestCase` names `SqlFile` and its error class, and `TestDatabase.load` uses `SqlFile`. pgjdbc is a test dependency of `healdan-core`, `healdan-api`, `healdan-storage` and `healdan-web`, at the version the WAR ships (`postgresql.version` in `logicaldoc-parent/pom.xml`, which `logicaldoc-webapp/pom.xml` uses too).
  - `VetoAtomicityTest` keeps one context and one database for its class, and its `FixtureBackup.restore` needs a superuser (`session_replication_role`), as the test server's `healdan` is.
- `healdan-api`'s `ApiTestCase` extends `AbstractHealdanTestCase` (from `healdan-core`'s test-jar) and drives the real `ApiServlet`, filters included, through Spring's servlet mocks. Its `context.properties` is copied at build time from `../healdan-core/src/test/resources`.
- `healdan-web`'s `AdminAppServletTest` extends `AbstractHealdanTestCase` too, signing real people in to CE web sessions on the test database, so `healdan-web`'s tests need the PostgreSQL and `healdan-core` installed with its test-jar. Its `context.properties` is copied from `../healdan-core/src/test/resources` as `healdan-api`'s is, its test classpath is `healdan-api`'s (`HealdanContext`'s scan finds the API's beans), and `healdan.secretKey` is under `target/`. `AppServletTest` needs no database. Both serve fixture builds under `src/test/resources/healdan/app/`, and `AppServletTest#testNeverReachesTheAdminApp` checks no `/app/` path reaches `healdan/app/admin/`.
- The sign-in throttle is on in every `healdan-core` and `healdan-api` test (the `throttle-signin` seed runs on each fresh test database), so a test that fails one user's password five times blocks that user for the rest of the test, unless it then gives that user a new password or creates the account after the failures, which clears its username's count (`ThrottleUserListener`).
- The Trash's rules hold in every `healdan-core`, `healdan-api` and `healdan-storage` test, as they run through CE's DAO: a non-admin's folder move needs Move on everything in the tree and Add on the target, and a folder delete is refused while a live document inside is checked out or immutable, so a test that moves or deletes folders as a non-admin grants the rights first (`HealdanFixtures.grant`; `AbstractRulesTestCase` has a ready layout), and every delete makes a Trash item. The upstream tests for the Trash's edits to CE are in CI's `UPSTREAM_TESTS`, named in the upstream edits' list above.
- `healdan-api`'s `ApiCall` sends a request to `http://localhost:8080`, the test context's `server.url`, unless `server(...)` names another. A sign-in start on any other name is sent to the public address first.
- Provider sign-in tests run against `FakeProvider`, a JDK HTTP server in `healdan-core`'s test-jar that serves discovery, keys and a token endpoint and signs its ID tokens with Nimbus. `SignInTestHooks`, in the same test-jar, allows plain HTTP, sets the TLS provider calls trust (`FakeProvider.trust()` uses it) and moves the clocks of pending sign-ins, one-time codes and the re-check; `FakeProvider.close()` resets it.
- `healdan-storage`'s tests extend `AbstractStorageTestCase` (on `AbstractHealdanTestCase`), which runs CE through `HealdanStorage`: it writes `healdan-core`'s test `context.properties` again as `context-storage.properties` with `store` swapped (its `baseConfigResource()`, which the base class writes again as `pg-context-storage.properties`), and registers the module's `plugin.xml`. Staging, the cache, the key files and the secret key are under `target/`. Storage is tested in three layers: `MemoryBackend` (faults on demand; `s3Like` acts as a bucket) and `LocalBackend` under `target/`, with `BackendContract` run on each backend; `FakeS3`, a JDK HTTP and HTTPS server in the tests that answers `S3Backend`'s calls and refuses what S3 refuses (`S3BackendTest`); and Garage on the smoke stack (step 5f). No test makes a real start, so tests call `Mover.runOnce()` and the like themselves; `StorageStartupTest` starts the timers with their waits shortened.
- Some tests load plugin manifests from fixture jars in `src/test/resources` through `getPluginArchives()`. Those jars are hand-maintained fixtures, not built from source.
- Tests write their stores, indexes and temp files under `target/`.
