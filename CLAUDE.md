# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo, Healdan (`Healdan-Project/healdan` on GitHub), is a hard fork of LogicalDOC Community Edition (LGPLv3), a Java document management system. It started from 9.3.1 and follows upstream's releases; the root POM's version is the one it's on. It's detached from GitHub's fork network. The plan is to take it in its own direction (a new UI, bespoke features, replacements for features LogicalDOC sells as paid extras) while still merging upstream core and security fixes.

- Upstream is `https://github.com/logicaldoc/community.git`. A fresh clone needs `git remote add upstream <that url>`.
- Sync upstream by merging `upstream/master` into a dedicated branch and opening a PR to `master`. Merge, never squash or rebase, so the shared history stays intact; the repository allows only merge commits. Keep sync PRs free of feature work.
  - Existing databases never get LogicalDOC's schema changes (see "Docker"). When a sync changes LogicalDOC's tables, in a `logicaldoc-*` module's `sql/` scripts or in the columns an entity maps, add the SQL an existing database needs, with a check, to the Install manual's Changes to LogicalDOC's Tables (`site/content/install/upgrading.md`) in the sync PR, a merge fix like the icons.
- Healdan's own modules (`healdan-*`) follow upstream's version: their POM parent and `plugin.xml` version match the root POM's. A module left behind makes Maven look for stock LogicalDOC jars, which the build no longer fetches: it fails with `Non-resolvable parent POM … Could not find artifact com.logicaldoc:logicaldoc:pom:<old version>`. Bump the module instead.
  - When a clean sync merge brings a LogicalDOC release bump, `.github/scripts/upstream-sync.sh` adds a "Follow upstream to <version>" commit. After a conflicted merge it doesn't, so whoever resolves the conflicts bumps them too.
- Upstream changes `logicaldoc-core` and `logicaldoc-gui` the most. To keep syncs cheap, put new work in new plugin modules and avoid editing upstream files where possible.
- Upstream sometimes ships POMs that fail Maven validation (for example, a duplicate dependency). If CI fails within a minute, check POM errors, the icon check, the doc-links check, the hosts check, the Maven repository check, the database driver check and the web licence check (next bullets) first.
- The GUI bundles Font Awesome Free 6, but upstream writes the GUI against Font Awesome Pro. Pro styles (`fal`, `fa-light`, `fa-thin`, …) and Pro-only icon names compile fine and only show up at runtime, as blinking missing-icon placeholders.
  - `.github/scripts/check-fontawesome-icons.py` catches them. It runs first in `build-logicaldoc.yml`, and `build` must pass before a PR can merge. Run it locally with `python3 .github/scripts/check-fontawesome-icons.py`.
  - When it flags lines an upstream sync brought in, swap them for Free icons in the sync PR itself. That's a merge fix, not feature work.
- Nothing links to LogicalDOC's docs (docs, wiki, help or forums.logicaldoc.com). `.github/scripts/check-logicaldoc-doc-links.py` runs next to the icon check and fails `build` on one, naming the file and line. When a sync brings one in, point it at docs.healdan.com in the sync PR, a merge fix like the icons. Its `ALLOWED` list holds the few exact lines Healdan leaves alone, each with its reason (the `SystemInfo` defaults `HealdanSystemInfo` replaces). The docs site's pages are checked by `check-site-sources.py` instead, which allows no such link.
- Healdan never contacts LogicalDOC's servers (no statistics, registration, licence or news calls). `.github/scripts/check-logicaldoc-hosts.py` runs after the doc-links check and fails `build` on any host, URL or email address at logicaldoc.com, .it, .net or .org, naming the file and line. It skips tests, prose, the docs site and the SOAP, CMIS and WebDAV XML namespaces. When a sync brings one in, remove the call in the sync PR, a merge fix like the icons. Its `ALLOWED` list holds the exact lines nothing contacts, each with its reason.
- Builds get the artifacts only LogicalDOC's Maven repository has from Healdan's copies at `https://maven.healdan.com/` (repository `Healdan-Project/maven`), through a mirror of the `logicaldoc` repository in `docker/maven-settings.xml`. JAI, betelio, ksoap2 and Oracle's JDBC driver aren't among them: their licences don't allow hosting them, or they have none, so the build drops JAI, betelio and Oracle's driver, and leaves `logicaldoc-webserviceclient`, ksoap2's only user, out. `.github/scripts/check-maven-repositories.py` runs after the hosts check and fails `build` when a POM or the settings file points a repository at a LogicalDOC host the mirror doesn't cover.
  - Upstream's parent POM also declares two retired repositories: `java.net` (`maven.java.net`, whose certificate chain no longer validates) and `sourceforge` (`oss.sonatype.org`, Sonatype's retired OSSRH, which answers 404). Nothing comes from either, but Maven asks every repository for each version range's metadata, so a second mirror in the settings file, `retired-repositories`, sends both to Maven Central (§12 of the design spec). The check also fails `build` on a repository on either host under an id no mirror to Central or to Healdan's copies covers; when a sync brings one, add its id to that mirror's `mirrorOf` in the sync PR, a merge fix like the icons.
  - When a sync bumps one of those artifacts or brings a new one, the build fails with `Could not find artifact … in healdan`. In the sync PR, as a merge fix, check its licence allows hosting it, run `python3 import-artifact.py <group>:<artifact>:<version> --project … --licence …` in a checkout of `Healdan-Project/maven`, push, and re-run CI once `python3 import-artifact.py --verify https://maven.healdan.com/` passes. One whose licence doesn't allow hosting is dropped instead, as JAI was. A missing `com.logicaldoc:*` artifact is never imported: it means a module or version was left behind, so bump it. When the old GWT UI retires, its GWT libraries leave the build too (§3.1 of `docs/superpowers/specs/2026-10-29-healdan-maven-repository-design.md`).
- Healdan runs on MariaDB only, and supports only open-source databases (Healdan-Project/healdan#110). Its own Java tests run on PostgreSQL 18, and upstream's on HSQLDB (see "Tests"). MySQL isn't supported and won't be added. Oracle and SQL Server are gone: the WAR ships neither driver and the setup wizard doesn't offer them (`docs/superpowers/specs/2026-11-01-open-source-databases-design.md`). CE's code paths for them (`isOracle()`, `isSQLServer()` and the branches they guard) and upstream's `.oracle` and `.mssql` SQL variants stay, as they never run and removing them would cost every sync (upstream edits core's schema files most months, and a deleted file would conflict each time). The wizard still offers MySQL, though it starts on MariaDB, and the WAR still ships MySQL's driver, though Healdan refuses to start on it (owner, 2026-11-01). PostgreSQL is to become its only database (`docs/ROADMAP.md`, principle 9 and the backlog; the design is `docs/superpowers/specs/2026-11-18-postgresql-design.md`, the plan `docs/superpowers/plans/2026-11-18-postgresql.md`, and the facts `docs/reference/postgresql-recon.md`). Healdan's code runs on both until the stack moves to PostgreSQL, at the switch, a later pull request.
  - `.github/scripts/check-database-drivers.py` runs after the Maven repository check and fails `build` on a POM dependency on Oracle's or SQL Server's JDBC driver, or a tracked file naming one of their driver classes, naming the file and line. It skips tests, prose and the docs site. When a sync brings one in, take it out in the sync PR, a merge fix like the icons.
- The User app's npm packages ship in a page Healdan serves, so their licences matter. `.github/scripts/check-web-licences.py` runs after the database driver check and fails `build` on a package in `healdan-web/web/package-lock.json` that the app ships (no `dev: true`) with a licence outside MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC and 0BSD, or with none, or a development-only one outside those and BlueOak-1.0.0, CC0-1.0, CC-BY-4.0, Python-2.0 and Unlicense. It names the package and its licence. Its `ALLOWED` list holds the reviewed exceptions, each with the licence reviewed and its reason; an entry whose package the lockfile now gives another licence fails, and so does one the lockfile no longer has. `scripts/notices.mjs` writes the notices of what ships into `apps/user/dist/notices.txt`, and fails on a shipped package with no licence file, and on a `DECLARED_ONLY` entry (a reviewed package that declares its licence without a file) that the app no longer ships without one.
- `README.md` opens with Healdan's notice that it's a modified version of LogicalDOC CE, which the LGPL asks for, then its Status section (experimental, no warranty, use at your own risk), then points to the docs site. It's Healdan's own now: when a sync brings an edit to upstream's README, keep Healdan's. `Build_this_Sources.md` and `docker/README.md` are short pointers to the site.
  - The docs site's home page and the Install manual's first page carry the same status notice. Change all three together.
  - `GPL-3.0.txt` is the GPLv3, which the LGPL in `LICENSE` incorporates. It isn't named `COPYING`, because GitHub would then stop detecting the repository's licence as LGPL-3.0.

## Roadmap

- `docs/ROADMAP.md` holds Healdan's direction: who it's for, the glossary, the milestone order, and what's decided versus open for each milestone. Read it before starting feature work.
  - Healdan's *Store* and *Workspace* don't mean what LogicalDOC's `Store` and workspace mean. See its glossary.
  - Each milestone gets a design spec in `docs/superpowers/specs/` before anyone builds it. Update the milestone's status in the roadmap as it moves.
  - Superpowers' brainstorming, writing-plans, subagent-driven-development and executing-plans skills are for milestone-sized work, the kind that gets a spec. Work directly on fixes, reviews, docs edits, upstream syncs and other small changes: those skills' questions, plan documents and per-task subagents take far longer than such a change needs.
- `docs/reference/logicaldoc-ce-capability-map.md` records what CE already has, what's only hidden by GUI feature gates, what's half built and what's missing, with file paths. Check it before re-researching.

## Build and test

You need JDK 25 and Maven 3.9+, Docker for the `healdan-*` modules' test database (below), and on x86-64 a processor with AVX2 (x86-64-v3): `healdan-web`'s build runs Vite 8, whose Rolldown binary dies with `Illegal instruction` (exit 132) without it, as it does on a VM with QEMU's default processor type (the Install manual's Troubleshooting has the fix; `-Dhealdan.web.skip=true` skips that build). The JDK is the one the `Dockerfile`'s `MAVEN_IMAGE` and `TOMCAT_IMAGE` name; CI's `build` check reads it from there and fails if the two differ. `source.level` in `logicaldoc-parent/pom.xml` sets the Java language level, and the GWT client compiles at source level 17. Some dependencies aren't on Maven Central. They come from Healdan's copies at `https://maven.healdan.com/` and from `https://repo.terracotta.org/maven2`, which `docker/maven-settings.xml` lists. CI and the Docker build copy it to `~/.m2/settings.xml`; copy it there for local builds.

```bash
mvn -B -ntp -DskipTests install                          # full reactor build (what the Docker image runs)
mvn -B -ntp -pl logicaldoc-webapp -am -DskipTests package # deployable WAR -> logicaldoc-webapp/target/*.war
mvn -pl logicaldoc-core test                              # one module's tests (sibling modules must be installed first)
mvn -pl logicaldoc-core test -Dtest=DocumentManagerTest   # one test class
mvn -pl logicaldoc-core test -Dtest='DocumentManagerTest#testCopyToFolder' # one method
docker/tests/test-db.sh start                             # the PostgreSQL 18 healdan-*'s tests run on, at 127.0.0.1:5432 (`stop` removes it)
mvn -pl healdan-core test -Dtest=FilingRulesTest          # Healdan's tests, or one class of them
mvn -pl healdan-core -DskipTests install                  # healdan-core with its test-jar, which healdan-api's tests need
mvn -pl healdan-api test -Dtest=FolderResourceTest        # the API's tests, or one class of them
mvn -pl healdan-storage test                              # the storage module's tests (needs healdan-core installed with its test-jar, as healdan-api's do)
mvn -pl healdan-web test -Dhealdan.web.skip=true          # the web module's servlet tests, without the Node build (needs healdan-core installed with its test-jar too)
dotnet test clients/helper/Healdan.Helper.sln             # the desktop helper's tests (.NET 10 SDK; global.json pins it)
dotnet test clients/helper/Healdan.Helper.sln --filter "Category=MacKeychain" # the real macOS keychain, by hand on a Mac
HEALDAN_MAC_OFFICE=1 dotnet test clients/helper/Healdan.Helper.sln --filter "Category=MacOffice" # the real Word, Excel and PowerPoint, by hand on a Mac with Office (they open windows)
python3 -m unittest discover -s clients/libreoffice/tests -v # the LibreOffice extension's tests (standard library only)
node --test 'clients/office/test/*.test.js'               # the Office add-in's logic (Node 22+, nothing to install; Node 21+ takes the argument as a file pattern, so a folder fails)
cd healdan-web/web && npm ci --ignore-scripts             # the web apps' packages (Node 24, `.nvmrc`; Maven's build downloads its own into healdan-web/target/)
cd healdan-web/web && npm run generate                    # the apps' API types, from healdan-api's openapi.yaml and openapi-admin.yaml
cd healdan-web/web && npm run typecheck                   # tsc over the packages (tsc -p .), then each app as a program of its own
cd healdan-web/web && npm run lint                        # ESLint
cd healdan-web/web && npm test                            # the apps' and packages' Vitest tests and Node's runner for scripts/
cd healdan-web/web && npm run build                       # generate and typecheck, then Vite's builds into apps/user/dist/ and apps/admin/dist/
mvn -pl healdan-web -am -DskipTests package -Dhealdan.web.skip=true -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true # healdan-web without the Node build (its jar then holds no app) or the GWT compile
clients/libreoffice/build.sh                              # the LibreOffice extension, packaged as clients/libreoffice/healdan.oxt (reproducible)
dotnet run --project clients/helper/tools/IconRender      # the extension's toolbar images and icon, from the helper's icons (by hand, on a Mac)
clients/helper/packaging/mac/package.sh 1.2.3             # Healdan Helper.app and its .dmg, on a Mac; signed only with SIGN_IDENTITY set
clients/helper/packaging/linux/package.sh 1.2.3 amd64     # the Ubuntu 26.04 .deb (or arm64) in packaging/linux/out/; needs no signing
HEALDAN_HELPER_DEV_ROOT=/tmp/hh dotnet run --project clients/helper/Healdan.Helper # a Debug helper with its files and keychain entry apart; no links or .oxt, and no notifications on a Mac (on Linux they go through notify-send)
python3 docker/demo/build.py                              # the demo firm's files, from docker/demo/sources/ (needs a built image)
```

- `logicaldoc-parent` is a reactor module, and the root POM inherits from it, so dependency and plugin versions live there.
- `logicaldoc-gui` runs a GWT compile for each GWT module (frontend, login, setup), which is slow. Skip it with `-Dgwt.skipCompilation=true` when you aren't touching the UI; the module's Java still compiles, which `healdan-core` needs.
  - Up to `test` that's enough. For `package` or `install`, add `-Dmaven.antrun.skip=true` and `-pl '!logicaldoc-webapp'`, as CI's `build` check does. The GUI's antrun step fails without the GWT output, and skipping antrun leaves every plugin zip unfinished, so the WAR built from them is broken.
- `healdan-web` builds the User app and the Admin app (`healdan-web/web`, an npm workspace) through `frontend-maven-plugin`, which downloads Node into `healdan-web/target/` (the version in `.nvmrc`, which the POM names too: change both, as `scripts/workspace.test.mjs` fails until they match) and runs `npm ci --ignore-scripts` and `npm run build` in `generate-resources`; `maven-resources-plugin` then copies `apps/user/dist/` into the jar's `healdan/app/user`, which `AppServlet` serves, and (`copy-admin-app`) `apps/admin/dist/` into `healdan/app/admin`, which `AdminAppServlet` serves. `-Dhealdan.web.skip=true` skips Node, and each copy then does nothing when its `dist/` doesn't exist, so the jar holds no app and `/app/` answers 503, as `/admin/` does an administrator. CI's `build` check passes it everywhere; the `Web` check and the Docker build do the Node build (the Dockerfile keeps npm's cache in a mount).
  - The workspace's `.npmrc` sets `ignore-scripts` and `save-exact`, so a developer's own `npm install` runs no package's install script either and pins what it adds (`scripts/workspace.test.mjs` checks both).
- Spring-based tests fail in `setUp` unless `~/logicaldoc-dev.properties` exists. An empty file works; CI creates one.
- The `healdan-*` modules' tests need a PostgreSQL 18 server; upstream modules' tests don't (they run on HSQLDB in memory). `docker/tests/test-db.sh start` runs `postgres:18` as the container `healdan-test-db` on the Docker network `healdan-test` (made if missing), published on `127.0.0.1` at 5432 or `HEALDAN_TEST_DB_PORT`, user `healdan` (a superuser) and password `healdan-test`, its data on a tmpfs, with `fsync`, `synchronous_commit` and `full_page_writes` off and 300 connections. It waits for `pg_isready` over TCP and prints the URL for the host and for a container; run while it's up, it says so and exits 0. `stop` removes the container, and with it the databases a killed run left. It removes the server for every run using it, so don't stop it while another run's tests may still be going.
  - The tests read `HEALDAN_TEST_DB_URL` (the server's JDBC URL without a database, by default `jdbc:postgresql://localhost:5432/`), `HEALDAN_TEST_DB_USER` (`healdan`) and `HEALDAN_TEST_DB_PASSWORD` (`healdan-test`), whose defaults reach the server `start` runs. With another `HEALDAN_TEST_DB_PORT`, set the URL `start` prints. Maven in a container joins `--network healdan-test` with `HEALDAN_TEST_DB_URL=jdbc:postgresql://healdan-test-db:5432/`.
  - With no server, each test fails in `setUp` with `Healdan's tests need a PostgreSQL. Start one with: docker/tests/test-db.sh start`.
- `healdan-core`'s, `healdan-api`'s, `healdan-storage`'s and `healdan-web`'s tests run against the installed jars of the modules they use. After changing `logicaldoc-core`, `logicaldoc-webapp` or `logicaldoc-gui`, re-install that module (`-pl <module> -DskipTests -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true install`) before running them.
- `healdan-api`'s, `healdan-storage`'s and `healdan-web`'s tests also need `healdan-core` installed, test-jar included: they reuse its `AbstractHealdanTestCase`, fixtures and test `context.properties`. Re-install it after changing `healdan-core`.
  - `-DskipTests` still compiles tests, so it builds and installs that test-jar. `-Dmaven.test.skip=true` doesn't, and their `with-tests` profiles then leave the test-jar dependency out, so the build works but `healdan-api`'s, `healdan-storage`'s and `healdan-web`'s tests can't run until `healdan-core` is installed with `-DskipTests`.
- `master` takes changes only through pull requests. Its ruleset, `master: require CI`, requires `build`, `Test (amd64)`, `Test (arm64)`, `Clients` and `Web` (not strict: a branch needn't be up to date), blocks force pushes and deletion, and has no bypass, so it binds the owner's account and every session using it. Issue Healdan-Project/healdan#9 has the reasons.
- CI's `build` check compiles every module except the WAR, skipping the GWT compile, and runs Healdan's tests in parallel shards. The Docker image CI does the GWT compile and the WAR. Upstream modules' other tests don't run in CI.
  - The tests are every test class in a `healdan-*` module (found without a list) and the upstream tests named in the workflow's `UPSTREAM_TESTS`, which cover Healdan's edits to upstream code. Add a test class there when a change edits upstream code. A name no upstream module has fails the check.
  - The `checks` job runs the quick checks, then `.github/scripts/test-shards.py` splits the tests into shards of about five minutes (at most eight). Each class weighs its time in the newest successful run, which the `test-times` job caches, or 3 s per `@Test` until it has one. Each `Tests (n of N)` job installs the modules, without javadoc or plugin zips, and runs its share. The `build` job, the check master requires, passes when they all did, or when a docs-only pull request skipped them.
  - Each `Tests (n of N)` job has a `postgres:18` service container, which its tests share, each making its own database; the `TestDatabase` defaults reach it at `localhost:5432`. It runs as `test-db.sh`'s does (the same user, password, locale, tmpfs and settings), through `POSTGRES_INITDB_ARGS`' `-c` flags and `--tmpfs` in the service's `options`, as every test makes a database and loads CE's schema statement by statement.
  - Its Maven repository cache falls back to master's newest copy, and only master saves it (from one shard), so a POM edit downloads only what it adds.
  - The repository has 10 GB of Actions caches, and GitHub evicts those used least recently beyond that. The Docker build's layer cache at `mode=max` (about 5 GB a master push) fills that and evicts the `m2-` copy, and until a master run's saving shard passes and saves a new one (`actions/cache` saves only from a job that passed), every shard downloads everything. So the image build's layer cache is `mode=min` (see "Docker"). Check `gh cache list --repo Healdan-Project/healdan` before adding a cache that's large or saved often.
  - Each shard deletes the restored copy's `_remote.repositories` files, so Maven uses every cached file whichever Maven saved it. Maven 3.9 records a file's repository by id and 3.10 by id and URL hash, and 3.9 rejects 3.10's. `ubuntu-latest`'s images ship both, so without the deletion a shard on the other Maven downloads everything again.
  - The Docker build doesn't need this: its `maven:3.9` image writes and reads its own copy, and 3.10 accepts 3.9's records.
  - A shard whose restore of the copy was an exact hit (its POMs those the copy was saved for) passes Maven `-nsu` (`MAVEN_METADATA` in the workflow), so a version range's list of versions (Bouncy Castle's own POMs have a range) and an unversioned plugin's come from the cached copy, and Maven asks a repository only for what the copy lacks. Without it Maven asks every repository again on each new day (UTC). A failed connection falls back to the copy, but an answer of "not found" doesn't: the build stops at `No versions available for org.bouncycastle:bcutil-jdk18on:jar:[1.81,1.82) within specified range`, with no warning (two shards on 2026-11-19, both on runners in another cloud than the rest). The saving shard still asks, so each copy it saves has that day's lists, and so does the Docker build, since what it resolves is what ships.
- `.github/scripts/code-changed.sh` writes three outputs for a pull request (a push gets all true):
  - `code` is false when it changes only docs (`docs/`, `site/`, Markdown outside `src/`), `clients/helper/`, `clients/libreoffice/`, `clients/icons/`, or any of them. The Java and Docker workflows then skip their build steps and still report the required checks. A change under `clients/office/` counts as code as well as clients, because `healdan-api` packages the Office add-in's pages and manifest into its jar (Markdown there stays docs).
  - `clients` is true when it changes anything under `clients/`, `clients.yml`, or the API contract (`healdan-api`'s `openapi.yaml`, which the helper's contract tests read; not the admin API's `openapi-admin.yaml`, which they don't read). `clients.yml` otherwise skips its test jobs.
  - `web` is true when it changes anything under `healdan-web/`, `web.yml`, or either API contract (`openapi.yaml` or `openapi-admin.yaml`; the apps' types are generated from them). `web.yml` otherwise skips its app job.
- `.github/workflows/clients.yml` runs the helper's `dotnet test` on `ubuntu-24.04` and `macos-15`, the extension's Python tests on `ubuntu-24.04`, and the Office add-in's `node --test` there too. Its `Clients` job passes when they did, or were skipped because nothing under `clients/` changed. `Clients` is one of master's required checks.
  - A `helper-v1.2.3` tag (or a run by hand) also runs `package-mac`, which packages the macOS helper with `clients/helper/packaging/mac/package.sh`, and `release-mac`, which attaches the `.dmg` to the tag's release, only for a pushed tag and once `xcrun stapler validate` passes on it. They never run for pull requests, and `Clients` doesn't need them.
  - The same tag (or run by hand) runs `package-linux` too, which builds the amd64 and arm64 `.deb`s with `clients/helper/packaging/linux/package.sh` in an `ubuntu:26.04` container on the `ubuntu-24.04` runner, installs the amd64 one and checks `ldd` for missing libraries, and `release-linux`, which attaches both `.deb`s to the release `release-mac` made, only for a pushed tag and after `release-mac`, so a Mac build that isn't notarised blocks Linux's release of that tag too. They never run for pull requests, and `Clients` doesn't need them.
  - Only official releases stay on GitHub: `release-mac` for `1.2.3` deletes the `1.2.3-*` pre-releases whole, with their `.dmg`s and the Ubuntu `.deb`s attached to them, keeping their tags as the record of what was tested, and refuses to publish a pre-release of a version already released.
  - Release tags (`helper-v*`, `v*`) can't be moved or deleted: the `Release tags` ruleset blocks it, with no bypass. A tag pushed on the wrong commit stays, and the next release candidate replaces it.
  - Signing and notarising need six secrets in the `helper-release` environment, which only `helper-v*` tags may use (`APPLE_DEVELOPER_ID_P12`, `APPLE_DEVELOPER_ID_PASSWORD`, `APPLE_TEAM_ID`, `NOTARY_KEY`, `NOTARY_KEY_ID`, `NOTARY_ISSUER`; the Developer Guide's CI page says what each holds). A tag's `package-mac` waits there until the owner approves it (the environment's required reviewer, which admins can't bypass), and only then gets them. Without them, as in a run by hand on a branch, the package is built unsigned and only uploaded as an artifact.
- `.github/workflows/web.yml` runs the workspace's `npm ci --ignore-scripts`, `generate`, `typecheck`, `lint`, `test` and `build` in `healdan-web/web` on `ubuntu-24.04`, with the Node in `.nvmrc`, for both apps (its job is still named `User app (ubuntu-24.04)`). Its `Web` job passes when the app job did, or was skipped because `code-changed.sh` said `web=false`. `Web` is one of master's required checks.
- Helper tests with `[Trait("Category", "Stack")]` need `HEALDAN_STACK_URL` and skip without it; `StackProviderSignInTests` also needs `HEALDAN_STACK_SIGNIN_PROVIDER`. `docker/smoke-test.sh` step 5d runs them against the smoke stack, only with `SMOKE_HELPER_TEST=1` (CI sets it, after setting up .NET), and fails unless two passed and none skipped (`HELPER_STACK_TESTS` in the script, which a new `Stack` test changes). A pull request that changes only the helper, the extension or the icons doesn't build the image, so those tests run on master after the merge and on pull requests that change the server.
- `logicaldoc-webservicesamples` and `logicaldoc-webserviceclient` aren't in the reactor.

## Docker

- `Dockerfile` (stages `build` → `tools` → `runtime`) and `compose.yaml` are this fork's own. The docs site's Install manual (`site/content/install/`) is the user guide, and its Developer Guide covers the dev overlay, tests and CI; the design is `docs/superpowers/specs/2026-10-15-docker-compose-stack-design.md`.
- The container never runs the setup wizard. `docker/tools/src/DockerInit.java` seeds `context.properties` and, on a fresh database, creates the schema by running the `DbInit` scripts from every `plugin.xml`, so a plugin's `DbInit` extension is picked up for new installs. Then, on every start, it installs any of CE's plugins not yet installed with CE's own `PluginRegistry`, before Tomcat starts, so a fresh stack's sign-in page doesn't say "The application has to be restarted" (§15 of the Docker spec); the entrypoint puts the conf folder on its classpath for them. Existing databases are never migrated, apart from Healdan's own `hd_` tables, which Flyway upgrades on every start (see "Healdan's code"). A plugin or upstream change that adds SQL to CE's tables needs it applied by hand there.
  - On every start against an existing database, `DockerInit` checks that CE's tables have every table and column the plan's `DbInit` scripts create (`DbInitPlan.createdColumns`, against `information_schema.columns`), and stops, naming each missing one and pointing to the Install manual's Changes to LogicalDOC's Tables, before Tomcat starts. It never adds them, and what a database has besides doesn't count. A table a later plugin's script creates stops it too, as nothing else would create it (§16 of the Docker spec). A fresh database's start runs the same check after `DBInit`.
- On every start, keys in the image's default `context.properties` that the conf volume lacks are added. Values are never overwritten, with four exceptions:
  - `product.release` and `product.year` (`ConfigPlan.IMAGE_KEYS`) describe the image, so they're always taken from it.
  - A key still holding a default an earlier image shipped takes the image's (`ConfigPlan.REPLACED_DEFAULTS`); an admin's own value stays. So far that's `cachecontrol`, whose `*.nocache.js:no-cache` makes browsers check the GWT loaders on every load. When Healdan changes a default that existing installs should get, add the value it replaces there.
  - Non-breaking spaces (0xA0) in `security.csp` (`ConfigPlan.PLAIN_SPACE_KEYS`) become plain ones, in an admin's policy too, and the rest of the value stays. Upstream's value had one after `object-src`, so browsers ignored `object-src 'none'`.
  - `store` (`ConfigPlan.HEALDAN_KEYS`) is set to `com.logicaldoc.healdan.storage.HealdanStorage` whatever the file holds, and `DockerInit` checks it was stored, so `healdan-storage`'s `HealdanStorage` is CE's `store` bean while the image's defaults, upstream's, keep `FSStore`. An install moves to it on its first start on an image that has it, its files staying where they are. Outside Docker the key is what the file says, upstream's `FSStore` by default, and `healdan-storage` then does nothing.
- The app has three volumes: `logicaldoc-conf` (`/opt/logicaldoc/conf`), `logicaldoc-repository` (`/opt/logicaldoc/repository`) and `logicaldoc-cache` (`/opt/logicaldoc/cache`, `healdan-storage`'s read cache, which only holds copies, so backups leave it out). The entrypoint hands all three to uid 1000 at every start, and goes on when a share refuses but uid 1000 can write to it. `setenv.sh` names `healdan-storage`'s folders: staging (`healdan.storageStaging`, `repository/staging`), the cache (`healdan.storageCache`) and the backends' key files (`healdan.storageKeys`, `conf/healdan-storage-keys`).
- `docker/server.xml`'s `RemoteIpValve` believes `X-Forwarded-For` and `-Proto` only from `LOGICALDOC_TRUSTED_PROXIES`, or, when it's unset, the Docker networks the container is on. `DockerInit` (`TrustedProxies`) works the list out and checks it on every start, and `setenv.sh` passes it to Tomcat as `healdan.trustedProxies`.
- LogicalDOC only runs external programs listed in a classpath `allowed-commands.txt`. The lines in `docker/allowed-commands.txt` are re-added to the conf volume's copy on every start; a new external tool needs a line there.
- `docker/setenv.sh` ends `CATALINA_OPTS` with `-XX:-UseBASE64Intrinsics`, so `.env` can't undo it, for CVE-2026-114938 (§17 of the Docker spec, Healdan-Project/healdan#273). It goes only in the change that moves `TOMCAT_IMAGE` to an exact Tomcat version's tag with Java 25.0.5.1 or later, since `docker compose up -d --build` reuses a cached base image. Smoke step 2's stack asks for the intrinsics in `CATALINA_OPTS`, and the step checks the JVM's final flags have them off. The Install manual's Upgrading page runs `docker pull` on `TOMCAT_IMAGE`'s tag before that build, so a change to the tag changes the page too.

## Architecture

**Modules.** `logicaldoc-util` sits at the bottom. `logicaldoc-core` builds on it, and the feature modules build on core: `webservice` (REST via CXF; Healdan's `SoapRemover` removes its SOAP endpoints), `webdav`, `cmis`, `dropbox`, `android` and `ios`. `logicaldoc-webapp` is the WAR that bundles everything. `logicaldoc-gui` (GWT client) depends only on util. `logicaldoc-i18n` holds the resource bundles.

**Plugin system (JPF).** Almost every module is a plugin, and adding a plugin takes four pieces:
- `src/main/resources/plugin.xml` declares the plugin's ID, its dependencies and the extensions it contributes.
- A class extending `com.logicaldoc.util.plugin.LogicalDOCPlugin` registers servlets at install time with `addServlet(...)`. That edits `web.xml`, so a restart is required. It can also register scheduled tasks and loggers.
- `src/main/assembly/assemblyplugin.xml` packages a `*-plugin.zip` (classifier `plugin`). It takes only the dependencies its `<include>`s name, not theirs, and the WAR's `WEB-INF/lib` is the webapp's own dependencies and those zips' jars. So a library's own dependency ships only when some zip names it: core's names `org.apache.poi:*` but not POI's SparseBitSet, which `healdan-core`'s zip ships (#202). `docker/tools`' `WarParsersTest` catches one missing for POI's PowerPoint and Excel readers, not for other parsers, and its `WarStorageTest` one missing for the AWS SDK's and Tink's jars, which `healdan-storage`'s zip ships.
- An `artifactItem` in `logicaldoc-webapp/pom.xml` (maven-dependency-plugin) copies that zip in, and an antrun step unzips it into the WAR. Without this entry, the plugin isn't shipped.

Core's `plugin.xml` defines the extension points other plugins hook into: `DbInit`, `Parser`, `Language`, `ResourceBundle`, `Task`, `DocumentListener`, `FolderListener`, `UserListener`, `TicketListener`, `Authentication`, `ThumbnailBuilder`, `FormatConverter`, `Search`, `Feature`, `SystemInfo`, `TokenFilter`, `Store`, `Aspect` and `TokenProvider`. `logicaldoc-dropbox` is the smallest complete example of a plugin.

**Spring wiring.** `web.xml` boots `com.logicaldoc.util.spring.MainContext`. It component-scans `com.logicaldoc` for `@PluginContext` classes and imports the webapp's `context.xml`, which defines the datasource, session factory and transactions.
- Each module has a `XxxContext` class annotated `@PluginContext` + `@ComponentScan` + `@ImportResource("classpath:context/context-xxx.xml")`.
- Runtime settings come from `context.properties`, read through `ContextProperties`, which `Context.get().getConfig()` returns.
- Beans are fetched with `Context.get(Type.class)`, and DAOs expose a static `XxxDAO.get()`.
  - A bean definition Spring can't make must be `abstract`. To learn what a `FactoryBean` makes, a lookup by type makes every one not yet made, lazy ones too. One that fails is made again at the next lookup, as the failure empties Spring's cache of names by type, and Spring 6.2 records each failure without a lock, so two lookups at once could throw and answer a request with a 500 (`TransactionProxyTemplateTest`).
- **Both Spring and Hibernate only scan `com.logicaldoc`.** Code in any other package root isn't discovered unless you extend the scans.

**Persistence.**
- Hibernate 7 uses JPA-annotated `@Entity` classes, which `com.logicaldoc.util.spring.LocalSessionFactory` finds by classpath scan. The `*.hbm.xml` mapping location in `context.xml` is configured, but no such files exist.
- DAOs follow one pattern: an interface `XxxDAO extends PersistentObjectDAO<T>` and an implementation `HibernateXxxDAO extends HibernatePersistentObjectDAO<T>`.
- Every `PersistentObject` has a `tenantId` (multi-tenant).
- CE has no migration tool (Healdan's own tables use Flyway, below, with a folder of scripts for MariaDB and one for PostgreSQL). CE's schema is plain SQL in `sql/logicaldoc-<module>.sql`, with DBMS-specific variants (`.mysql`, `.mariadb`, `.oracle`, `.mssql`) that `PluginDbInit` picks when one exists; there's none for PostgreSQL, so Healdan's tests load core's generic script. Plugins add tables through a `DbInit` extension with a `sqlFile` parameter.
- CE maps Java `boolean` fields onto `int` columns, which PostgreSQL refuses a boolean for. `healdan-core`'s `src/main/resources/hibernate.properties` sets `hibernate.type.preferred_boolean_jdbc_type=INTEGER`, which Hibernate reads at its start, so it binds every `boolean` as an integer on both databases (`BooleanBindingTest`; `AbstractHealdanTestCase` checks it first in every test; `WarHibernateTest` that the WAR has no other `hibernate.properties`, as Hibernate reads only the first). A flag in Healdan's tables is an `int` column too.
- `HibernatePersistentObjectDAO`'s typed single-value reads (`queryForObject`, and `queryForList`'s single-column form, through `processQueryForListRecord`) hand the driver's value to the fork-owned `HealdanTypedReads` (`logicaldoc-core/.../core/HealdanTypedReads.java`, beside `HealdanHooks`), which converts an exactly held number (integer, `BigInteger`, `BigDecimal`) in Java: to `Long` or `Integer` when it fits exactly, and to `Double`, `Float`, `BigDecimal` or plain text; anything else goes to `getObject(1, type)` as before. pgjdbc refuses a `Long` from an `int` or a `numeric`, and the refusal rolls back the caller's transaction at its commit, silently (`HealdanTypedReadsTest`, in `UPSTREAM_TESTS`; `TypedReadsOnPostgresTest`).
- On PostgreSQL a failed statement ends its transaction, whatever Java catches. So no statement of Healdan's is expected to fail inside a transaction, and one that may fail without failing its caller runs inside a savepoint: `healdan-core`'s `com.logicaldoc.healdan.util.Savepoints` (`run`, which rolls back on any `Throwable`; `insertIfAbsent`; spec §7.3 of `docs/superpowers/specs/2026-11-18-postgresql-design.md`). The listeners that log and swallow a failure inside CE's save (`EmailDocumentListener`, `PreviewDocumentListener`) run their statements in one: `PreviewDocumentListener` keeps its Java-only guard (the event, an Office file name) outside, as a savepoint is two round trips on every save, and `EmailDocumentListener` puts the whole of its `try` inside. The two favourite-names listeners need none: their `afterStore` reads the row before the store from the dictionary or the session's map, and follows the rename in a transaction of its own. Until the switch, Healdan's SQL runs on MariaDB too: no `on conflict` or other PostgreSQL-only syntax. SQL given to CE's DAO helpers never uses `::`, which `NamedParameterStatement` reads as a parameter: write `cast(x as text)`.
- The second-level cache is Infinispan (`infinispan.xml`, or `infinispan-cluster.xml` when clustering is on).

**UI ↔ server.** The UI uses GWT 2.12 and SmartGWT 14.1, with GWT modules `frontend`, `login`, `setup` and `common` under `com.logicaldoc.gui`.
- RPC calls go from interfaces in `gui/**/client/services` (`@RemoteServiceRelativePath`) to `logicaldoc-webapp/.../web/service/*ServiceImpl`, mapped in `logicaldoc-webapp/src/main/webapp/WEB-INF/web.xml` under `/frontend/*`.
- Grid and list data come from `web/data/*DataServlet`, which serves XML for SmartGWT DataSources at `/data/*.xml`.
- Other ways into the server are REST at `/services/rest/*` (`logicaldoc-webservice`, endpoints in `webservice/rest/endpoint`; `healdan-core`'s `SoapRemover` removes the module's SOAP endpoints at startup), WebDAV at `/webdav/*`, and CMIS.

**Edition feature gating.**
- The GUI shows or hides features with `Feature.enabled(n)`, which checks for the name `Feature_<n>`.
- Those names come from `Feature` extensions declared in plugins' `plugin.xml` (collected by `SystemInfo`).
- The GUI already contains client code for enterprise-only features whose server implementations aren't in this repo, for example the `ai`, `google`, `onlyoffice`, `saml` and `whatsapp` service interfaces.
- Replacing a paid extra therefore means three things: implement that RPC interface on the server, register its servlet, and declare the matching `Feature_<n>` extension.

The web page can still make a key for it, which `HealdanThrottle` refuses at sign-in on every route.
  - A provider sign-in opens its CE session through the whole chain with a one-time `hd_signin_` key (`SignIns`, `SignInAuthenticator`), on M2's pattern; `HealdanTokenAuthenticator` leaves those keys alone. The helper gets a 60-second one-time code for its device token instead, and a helper start whose PKCE challenge another sign-in still has, waiting or with a code, is refused as `expired`.

- **Email** (M5; spec `docs/superpowers/specs/2026-11-03-m5-email-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.email` and `healdan-api`'s `EmailResource` (`POST /api/v1/emails/inspect`, `POST /api/v1/emails`, `GET /api/v1/emails`; in `openapi.yaml`).   - The Message-ID is the `emailmessageid` property (`ATTR_EMAILMESSAGEID`, the `profile-message-id` seed), which `EmailDocumentListener` reads on every route: the header without brackets or whitespace, at most 998 characters, an `.msg`'s from its `PR_INTERNET_MESSAGE_ID` stream, which `EmailFields` reads with POI (CE's `EMail` has none). Only copies the caller can read count; no user means every copy counts.

The rule serialises on `DocumentManager`'s monitor, inside which each `create` and `moveToFolder` runs its listeners and, when no outer transaction is open, commits, so its check (with a fresh look at READ_COMMITTED for a transaction begun before the call) sees every filing that went through the monitor before it. `OncePerMatterConcurrencyTest` fails without it. Folder copies and merges (one transaction of several stores), folder moves and restores, and a direct `DocumentDAO.store` or `DocumentManager.update` that moves a document don't go through it, so one of them at the same moment as an upload of the same message into the same matter can still leave two copies. A cluster would need a lock again.
  - `EmailFiling` (with `Filer`, the filing of one document taken out of `DocumentResource.create`) files the email, its ticked attachments (`MessageParts` decides which are attachments and which inline; attachments take the email's sent properties) and their `attachment` links, each document in its own transaction and undone by compensation on a failure. `MessageLocks` holds a JVM lock per matter and Message-ID, which `Filer` takes too for an email filed on its own, so a repeat waits for the first filing, 30 seconds at most, then `409 filing-in-progress`. Filing needs WRITE on the folder, as `POST /v1/documents` does.
  - Never log subjects, addresses, attachment names or message contents at info or above; Message-IDs at debug only.
- **`healdan-storage`** keeps each Store's files on a storage backend of its own, a local or NFS folder or an S3 bucket (JPF id `healdan-storage`, which requires `healdan-core`; spec `docs/superpowers/specs/2026-11-01-s3-storage-backends-design.md`). Its code is under `com.logicaldoc.healdan.storage`, which `HealdanContext`'s scan finds. The Developer Guide's How Healdan Extends LogicalDOC page has how it plugs into CE. The docs are the Admin Guide's Storage Backends section (`site/content/admin/storage-backends/`), Stores and Healdan Settings pages; the Install manual's Cloud Storage, Backup and Restore, Host Folders, What Runs, Configuration, Upgrading, Troubleshooting and Known Limitations pages; and the Developer Guide's How Healdan Extends LogicalDOC, API (`503 storage-unreachable`), Tests, Continuous Integration and Building from Source pages. Its build, test and Docker facts are above and under "Tests".
  - `HealdanStorage` is CE's one `store` bean through the `store=` key (`ConfigPlan.HEALDAN_KEYS` in Docker), and never a Spring component, which would make a second instance, `healdanStorage`, on `FSStore` servers too, that `Context.get(HealdanStorage.class)` finds before CE's (`Store.get()` and CE's `@Resource` look `store` up by name). Its `init()` reads no table, as Spring calls it before Flyway has run. On `FSStore` the module's other beans, its download filter and its seeds do nothing, and the Storage tab refuses every change.
  - `hd_storage_file` (JDBC, `StoredFiles`) has a row per file, keyed by doc id and resource name. Backend 0 is staging, which has no `hd_storage_backend` row, and 1 is Original (`store.1.dir`). Each write gives the row a new random 64-bit `hd_write`, never a counter, which the mover's commit and the read cache's entries check. `exists`, `size` and `listResources` answer from the rows, and a file with no row is read from Original's folder. The mover lists only rows with `hd_waiting` set, so whatever leaves a file off its Store's backend sets it (`recordWrite`, `moved`, `setStore`, the recording seed, and `storeBackendChanged`, which every Store switch calls, including one back to Original, which deletes the Store's `hd_storage_store` row), and the nightly check mends one that drifted. Its SQL follows the PostgreSQL rules in its plan's Global Constraints (`docs/superpowers/plans/2026-11-03-s3-storage-backends.md`).
  - One lock per file (`FileLocks`, striped in the JVM): saves and deletes hold it while they write a file's bytes and row, the mover for its commit, and the purge while it checks and deletes a held copy. Nobody holds two. The mover and the purge, once they hold one, write nothing while an open transaction has written that file's rows (`writtenByOpenTransaction`), and leave the file for a later pass. Healdan runs one node; a cluster would need a lock in the database.
  - A local hold (and staging's) moves the copy under `.held/` at once, while its `hd_storage_held` row and the delete of its `hd_storage_file` row are the caller's transaction's. `HoldRollback` puts it back on a rollback, holding its lock, before `FileLocks`' marks clear (their order is `HoldRollback.ORDER + 1`), so the mover and the purge never find the row back before the copy. It replaces a file in the place only when nobody else has written or deleted the file since the hold (`FileLocks.marksMade` and `marksHere`), so the file is the transaction's own write; otherwise the copy stays. A copy left under `.held/` waits for the purge's next run, which puts back any local held copy whose row reads it from there rather than delete it. A hold whose row can't be written puts its copy back at once. A delete that finds a file under `.held/` and not in its place holds that copy again.
  - Staging, the read cache and the key files are `-Dhealdan.storageStaging`, `-Dhealdan.storageCache` and `-Dhealdan.storageKeys`; without them, `staging/` and `cache/` beside `store.1.dir`, and `healdan-storage-keys/` beside `SecretBox`'s key. Staging can't be, hold or sit inside Original's folder or the key files', nor the cache any of those three (`Staging.apart`, by path, links not followed). A backend added or edited can't overlap them, the configuration folder or another backend (`BackendDrafts.checkPlace`): folders by path and with links followed, and S3 buckets and prefixes within one S3 service (every AWS host is one, any other endpoint its host and port).
  - An encrypted backend's key is `backend-<id>.key`, 32 bytes, mode 600 in a folder of mode 700, never in the database: lose it and the recovery key, and its files can't be read. Every backend has a marker naming this install (`storage.installId`) and the backend, `.healdan-backend` in a folder or `<prefix>.healdan-backend` in a bucket; one missing or another's fails the backend, so an unmounted share is never written to, and the recording seed stops startup rather than mark an Original with no marker and no file while `ld_document` has documents not deleted. An encrypted backend's `.healdan-check` must decrypt under the key file at start, at the first write to a backend not yet checked, and on Test.
  - The hooks in `healdan-core`: `HealdanStartup.start()` calls each `HealdanStartListener`, and `StorageStartup` then starts the checks, the mover, the retests, the purge, the alert and the nightly check (tests call `run()`, which calls none); `HealdanHooksImpl.afterFolderRestore` calls each `FolderTreeListener`, as CE's folder restore tells no listener; the seeds join `SeedRunner.ORDER` by name, a name with no bean skipped; and `StorageUnreachableException` (`healdan-core`'s `util`) is an outage, which `healdan-api` answers `503 storage-unreachable` and `PreviewWorker` waits out without spending a try.
  - The Admin app reads storage through `healdan-core`'s port `StorageAdministration` (`com.logicaldoc.healdan.admin.storage`, plain records in `StorageRecords`, nothing secret: no S3 key or secret, no recovery key, an endpoint as scheme, host and port), which `StorageAdministrationImpl` (`storage.web`) implements over `StorageAdmin.overview()`, unchanged. `healdan-core` and `healdan-api` can't depend on `healdan-storage`, so it's found by type (`Context.get().getBeansOfType`), as `HealdanStartListener`s are (spec §9.7; `StorageAdministrationImplTest`).
  - `storage-hide-stores` hides CE's Stores screen (menu 105), which could change `store.1.dir`. `DownloadErrorFilter` holds a CE download's first 1,024 bytes, so an outage met before they're sent gets a `503` page (or `/convertpdf`'s placeholder), not an empty `200`.
- **The Trash** (M6 §16; spec `docs/superpowers/specs/2026-11-16-folders-and-trash-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.trash`, with `healdan-api`'s `TrashResource` (`/v1/trash`) and `FolderChanges` (`FolderResource`'s folder delete, move and `contents`), and the User app's `views/TrashView.tsx` (`/app/trash`) and `organising/` (folder moves and deletes, the cross-matter question, Undo). The docs are the Admin Guide's The Trash and Removed Items page, the User Guide's The Trash and Copying, Moving and Deleting, and the Developer Guide's API, The Web App and How Healdan Extends LogicalDOC.
  - The tree rules hold on every route, admins needing none of the permissions. A folder move needs Move on every live folder and document in it, hidden ones included, and Add where it goes: `PermissionRules.checkMoveTree` from `RulesFolderListener`, and `HealdanTreeChecks.movedTrees` (through `HealdanRpcChecks` for the Classic Interface) before `FolderServiceImpl.move` and `SoapFolderService.move` write, so a Classic merge's subfolders need it too. `beforeFolderDeleteTree` runs `checkFolderDelete` and `checkDeleteTree`, then `TrashRules.checkDeletable`, which refuses a live document inside that is checked out or immutable, admins' too, and only then records the item, so a person without Delete inside learns nothing of what's there. A non-admin restores a folder only from the Trash (`ld_deleted` 1), a live one refused as well as a removed one (`checkFolderRestore`).
  - The Classic Interface's three removal RPCs (`deleteFromTrash` twice, `emptyTrash`) ask the `removeFromTrash` and `emptyTrash` hooks first (`TrashRemoval`), so a folder's removal takes its contents and is recorded. A restore, on every route, sets a restored document `TO_INDEX` (`TrashDocumentListener` on `RESTORED`), as CE's restore never re-indexed.
  - Every delete, on every route, is one item in `hd_trash` (V11) with a member in `hd_trash_member` for each folder and document it took, deleted, removed, restored or destroyed. `TrashRecorder` records a tree in `beforeFolderDeleteTree`, a document from `TrashDocumentListener` (position 170) and a folder deleted alone from `TrashFolderListener` (140), in the delete's transaction; a member already deleted in an item records nothing. CMIS records first and commits each row on its own, so `afterFolderDeleteTree` (`TrashRecorder.settle`) drops what it didn't take.
  - A restore brings back only its item's members (`TrashRestore`, through `folderRestoreScope`); one a restore leaves behind, its folder not live, moves to the item holding that folder, or to an item of its own. A member removed on its own leaves its item for one of its own (`TrashRecorder.splitOff`), so Removed lists every removed member.
  - `TrashDestroyer` destroys what was removed more than `trash.removedDays` before (1 to 365, 30 by default), nightly at 02:47 server time (`TrashStartup`), each document in its own transaction, as `_system`, which the `trash-system-destroy` seed gives Destroy Documents. A document's member is written destroyed before CE's destroy runs, so nothing but the commit follows `healdan-storage`'s hold of its file, which a rollback wouldn't undo; the item's folders and aliases then go in one transaction, and one the job can't take yet (a row still in it, a folder taking its security from it, a live alias) stays removed for the next night. `trash-record-existing` makes items of what was deleted before the Trash. Tests call `runOnce` themselves; `TrashTestHooks`, in `healdan-core`'s test-jar, fails a destroy for other modules' tests.
  - The API refuses a Store's Trash item (`409 refused`), which only an admin's delete in the Classic Interface makes, as CE puts a Store back under the root whatever is asked; it's restored there. A matter's own folder and a Store are never moved, deleted or destroyed by the app or the job.
  - In the app, folder rows select with documents (a plain click still opens a folder; Shift, Command, the arrow keys, Space and a right-click select), a drag's `ROWS_TYPE` payload carries folders with their kind and level, and every delete's toast has Undo (`@healdan/ui`'s `toastWithAction`, 10 s, F6 reaches it), which restores the items the delete answered with.
- **The Admin app's records** (spec `docs/superpowers/specs/2026-11-18-admin-app-design.md` §8.1, §9.3 to §9.6) are `healdan-core`'s `com.logicaldoc.healdan.admin` and the packages under it; the docs are the Developer Guide's How Healdan Extends LogicalDOC, API (The Admin App's Routes) and Tests pages, and the Admin Guide's The Admin App. No test makes a real start, so tests call `ErrorWriter.drainOnce()` and `UsageSummary.refreshNow()` themselves, and `DashboardService.forget()` before a fresh `read()`.
  - `hd_admin_event` (V12) is the administration record: when, who (id and username), from where (`AdminContext`, which `AdminFilter` sets to the request's address; none outside an admin request, as from the Classic Interface), the `AdminArea`, the action (`client.renamed`), the target's kind, id and name, and a JSON detail of the changed fields, `{"before":…,"after":…}` in name order, a secret's `{"secret":true}` (`AdminEvent.Change.secret()`) with no value. `AdminEvents.record` writes in the caller's transaction, so a failed record fails the change; `recordAfter`, for a change that isn't one transaction, writes after it in a savepoint, never throws, and logs a failure at error naming the action and the target's kind and id, never a value. `ClientService` and `MatterService` (`@Transactional`) record their creates and edits themselves, so the Classic Interface's and the seeds' client and matter changes are recorded too; a create records every field it set, an edit only what changed, and an edit that changes nothing isn't recorded.
  - `hd_error` (a row per fingerprint: level, area, logger, latest message, stack and documents named, total, first and last seen, resolved by whom) and `hd_error_hour` (a count per fault and UTC hour, written as UTC's own date and time, a `LocalDateTime`, so the server's clocks going back can't join two hours), both V12, are the errors the server logged (`admin.errors`). At a real start `ErrorWriter`, a `HealdanStartListener`, attaches `ErrorCapture`'s Log4j appender in code (no `log.xml` edit; `log4j-core` is a `provided` dependency of `healdan-core`) for `ERROR` and above, to the root and to every `additivity="false"` logger (36 in the webapp's `log.xml`, the Indexer's among them), again after a reload (a `PROPERTY_CONFIG` listener, only if the root lacks one: attaching tells the listener again), and starts one daemon thread, `healdan-error-writer`. The appender never blocks, logs or touches the database: it copies the event, capped (message 4,000 characters, stack 16,000, NULs taken out), onto a queue of 1,000, counting what doesn't fit (`dropped()`), and ignores its own package's loggers and the writer's thread. The writer drains batches of 100 into `ErrorStore`, oldest first, keeps the head while the database fails (waiting 1 s, doubling to 1 min), and leaves an error out only when it's refused itself three times in a row (a `DataIntegrityViolationException`, SQLState classes 22 and 23, or a failure outside the database), counted in `skipped()`; a connection, timeout, lock, full disk or read-only database never leaves one out. The fingerprint (`ErrorFingerprint`) is the SHA-256 of the exception's class, the logging class and line (or the logger's name) and the message without its numbers and quoted names, plus the logger's name when the logging class isn't the logger's or nested in it, so each CE task, whose failures `Task.run` logs from one place through the task's own logger, is a fault of its own; the area is `ErrorAreas`', from the logger's package. One writer, so a write updates first and inserts when no row changed. It prunes 10 minutes after the start, then daily: hour counts after 31 days, and resolved faults unseen for 90. `ErrorCaptureTest` runs on a Log4j context of its own (`capture-log4j.xml`).
  - `UsageSummary` (`admin.dashboard`, a `HealdanStartListener`) keeps the Dashboard's Usage in memory, worked out on its own daemon thread, `healdan-admin-summary`, at the start and then 15 minutes after the last one ended, never on a request's thread; only the signed-in count is made per request, from `SessionManager`. A failed refresh keeps the last summary with `failedAt`, and stopping mid-refresh logs at debug, not error, which the capture would count as a fault. A matter's documents are those stamped with its client and matter numbers (`ld_document_ext`), a Store's its matters'. Its days start at midnight in the reader's `zone` (R90): `current(zone)` keeps a summary for the server's zone and the four asked for most recently, and a zone asked for the first time gets the empty one and has its own made at once on the summary's thread. `healdan-api`'s `AdminDashboardResource` serves it at `GET /v1/admin/dashboard/usage?zone=`, and `AdminFindResource` is `GET /v1/admin/find?q=` (at most five each of clients, live matters and people). `RouteCoverageTest.DESCRIBED_AHEAD` holds the admin routes `openapi-admin.yaml` describes before the server answers them, none now, and fails on one that's implemented.
  - `IndexCounts` (`admin.index`, spec §9.6) counts documents not in the Trash, shortcuts left out: failed is `TO_INDEX`, not archived, with its latest `event.indexed` or `event.indexed.error` row the error (each document's chosen by one ordered look through its own `ld_history` rows: the latest date, a row with none older than any with one, then the highest id, as MariaDB keeps whole seconds); waiting is `TO_INDEX` or `TO_INDEX_METADATA`, not archived, and not failed. `counts()` gives indexed, waiting and failed in one pass; `failed(offset, limit)` lists the failed with their stamped matters.
  - Job status (`admin.jobs`, spec §9.5): each of Healdan's jobs is a `HealdanJob` bean (name, label, `canRunNow`/`runNow`) that reports to `JobStatus` under its name (`started`, then `finished` or `failed`, each with its next run, and `scheduled` for a first run known before it's made), in memory only; reporting never throws, and an error is the exception's class and message, or the job's own text, at most 1,000 characters. The previews and the email index report from each `runOnce` round, the mover from its sweep and `runOnce()`, and the Trash destroyer and the storage retests, purge, alert and nightly check from their schedulers only (a direct call reports nothing; Phase 5's Run Now must report). `Jobs.all()` lists Healdan's eight in `Jobs.ORDER` (the storage ones wherever `healdan-storage` is, and on `FSStore` servers switched off: `HealdanJob.enabled()`, which `healdan-storage`'s `StorageJob` answers from `StoreTracking.active()`), then CE's six tasks from `TaskManager`: last start is the schedule's previous fire time, last end that plus its last duration once idle, next run the next fire time. A task's error is the latest `ErrorStore.latest` has from its logger since its last start, so any ERROR during a run fails it, but `Task.run`'s "The task is stopped" and "The task gets interrupted" (`NOT_FAILURES`). The email index is `done` once `email.index` says so. `JobView.overdue`: switched on, not running, next run more than twice its interval past (from the last end, or a CE task's last start) and an hour at least. `JobView` has no schedule: CE's schedules wait for Phase 5's Background Jobs screen.
  - `DashboardService` (`admin.dashboard`, spec §8.1) makes Needs Attention (eight codes, `AttentionItem`), `unchecked` (codes whose source couldn't be read) and Server Health (ten tiles, `HealthTile`) in one `read()`, each from its own source: the storage port (stuck files, backends `unreachable` or `failing`; no port is nothing to check unless `store` is `HealdanStorage`), `IndexCounts.counts()`, `ErrorStore.unresolved` (faults in 24 hours and the latest's time, one query), `PreviewJobs`' counts, `Jobs.all()`, the volumes of `store.1.dir`, `index.dir` and `conf.logdir` (`DISK_LOW_PERCENT`, 85, a constant), JDBC's product and version with `pg_database_size` or MariaDB's `information_schema.tables` for `getCatalog()`, `ProviderClient.answers` per enabled provider at most every 5 minutes (a fetch whose failure isn't remembered, so it never fails a sign-in), and CE's `EMailSender` logger's unresolved errors in 24 hours. Each source is `Cached` for a minute (the database's five), worked out again once on a virtual thread `healdan-admin-dashboard`, the last answer served while younger than twice that; a request waits only for a source with none, 5 seconds at most for all, then it's still being worked out. A read running past its `maxAge` is stuck (`Cached.Stuck`, logged once, answered at once, not waited for), and one past ten times that is given up on and read again. `Dashboard.readAt` is the oldest answer's time, which the page's Updated shows. A job both failed and overdue counts as failed only. A failed or unfinished source puts its codes in `unchecked` and gives its tiles `problem` with status `attention`, logged at warn by class only. Links come from `DashboardService.Screen`, `/frontend.jsp` until each screen ships. `AdminDashboardResource` serves it at `GET /v1/admin/dashboard`. The contract quotes `'off'`, which bare YAML reads as false: `OpenApiFileTest` checks every string enum holds strings.

  - One helper runs per user on both systems: `Program.Main` holds a lock file, `helper.lock` (`SingleInstance`), in the helper's folder (`$XDG_DATA_HOME/healdan-helper/` or `~/.local/share/healdan-helper/` on Ubuntu), and a helper that can't open it starts anyway, logging that. A helper whose `channel.json` names a live process (on Ubuntu, the user's own) whose channel answers counts too, on both systems: one from before the lock, or one that couldn't open the file. So on macOS a second copy started for a link while the first is still signing in hands the link over, once, and quits, instead of starting a second full helper. On Ubuntu the desktop entry runs `HealdanHelper %u`: the first start takes its link from its arguments and holds it until signed in, and a second process hands each link to the running helper with `POST /v1/link` (`LinkHandOver`), waiting up to 30 s for one still starting (and never sending again one that got no answer in time), then quits. A link waiting longer is dropped, with a log line and a notice naming its doc #; a second start with no link says the helper is already running, and a `healdan:` link that isn't an open link says it was ignored. The session accepts links before its channel starts, and opens the held one once it listens.

Crash detection counts only the user's own `soffice.bin` processes (`OwnProcesses`, from `/proc`: the user's uid, in the helper's pid namespace, not zombies), so another user's or a container's LibreOffice can't hide a crash. `[LinuxFact]` tests skip off Linux.

The autostart entry has `TryExec`, so after a removal that keeps it (a conffile) nothing starts. `package.sh` drops .NET's `libcoreclrtraceptprovider.so`, which needs `liblttng-ust.so.0`, absent from 26.04, and loads only with LTTng tracing on. There's no HarfBuzz workaround: the trial's start-up crash didn't recur.

## Tests

- Tests use JUnit 4. The base class `com.logicaldoc.util.junit.AbstractTestCase` builds a Spring context from the module's test `context.xml` and `context.properties`.
- For upstream modules, that context includes an in-memory HSQLDB loaded from `getDatabaseScripts()`. For core, that's `sql/logicaldoc-core.sql` plus the test `data.sql` fixture data. Upstream's tests, those in CI's `UPSTREAM_TESTS` included, stay on HSQLDB and never touch an `hd_` table.
- Each module has its own base class, such as `AbstractCoreTestCase`, `AbstractWebappTestCase` or `AbstractWebserviceTestCase`. Extend the closest one.
- `healdan-core`'s `AbstractHealdanTestCase` runs every `healdan-*` test on PostgreSQL, a database of its own per test (`TestDatabase.create()`, from `template0`, UTF-8, `locale_provider builtin builtin_locale 'C.UTF-8' locale 'C'`, whatever the server's default; each name carries a number unique to its JVM, so the modules' suites can share one server at once), made before the context and dropped (`with (force)`) once upstream's `tearDown` has run. It hands `AbstractTestCase` no scripts (`getDatabaseScripts()` is final and empty, so upstream's HSQLDB steps do nothing), checks the boolean setting is in force, then loads `databaseScripts()` (`sql/logicaldoc-core.sql`, `data.sql`; what subclasses override) through HSQLDB's `SqlFile`, empties the store (`store.1.dir`), since ids restart with each test's database while the store under `target/` stays, and runs Healdan's migrations and seeds.
  - Its `getConfigResource()` is final: it writes `baseConfigResource()` (`context.properties`; what subclasses override) again as `pg-<base>` with the test's `jdbc.url`, user and password. For `context.properties` it starts from `pg-context.properties` while that is at least as new as the base, as CE writes changed settings back and a later test reads them, so an edit to the test `context.properties` reaches the next run. The test `context.properties` says `jdbc.driver=org.postgresql.Driver`, `jdbc.dbms=postgresql` and PostgreSQL's dialect, and the test `context.xml` reads `${jdbc.driver}`.
  - HSQLDB's jars stay on Healdan's test classpath: upstream's `AbstractTestCase` names `SqlFile` and its error class, and `TestDatabase.load` uses `SqlFile`. pgjdbc is a test dependency of `healdan-core`, `healdan-api`, `healdan-storage` and `healdan-web`, at the version the WAR ships (`postgresql.version` in `logicaldoc-parent/pom.xml`, which `logicaldoc-webapp/pom.xml` uses too).
  - `VetoAtomicityTest` keeps one context and one database for its class, and its `FixtureBackup.restore` needs a superuser (`session_replication_role`), as the test server's `healdan` is.
- `healdan-api`'s `ApiTestCase` extends `AbstractHealdanTestCase` (from `healdan-core`'s test-jar) and drives the real `ApiServlet`, filters included, through Spring's servlet mocks. Its `context.properties` is copied at build time from `../healdan-core/src/test/resources`.
- `healdan-web`'s `AdminAppServletTest` extends `AbstractHealdanTestCase` too, signing real people in to CE web sessions on the test database, so `healdan-web`'s tests need the PostgreSQL and `healdan-core` installed with its test-jar. Its `context.properties` is copied from `../healdan-core/src/test/resources` as `healdan-api`'s is, its test classpath is `healdan-api`'s (`HealdanContext`'s scan finds the API's beans), and `healdan.secretKey` is under `target/`. `AppServletTest` needs no database. Both serve fixture builds under `src/test/resources/healdan/app/`, and `AppServletTest#testNeverReachesTheAdminApp` checks no `/app/` path reaches `healdan/app/admin/`.
- The sign-in throttle is on in every `healdan-core` and `healdan-api` test (the `throttle-signin` seed runs on each fresh test database), so a test that fails one user's password five times blocks that user for the rest of the test, unless it then gives that user a new password or creates the account after the failures, which clears its username's count (`ThrottleUserListener`).
- The Trash's rules hold in every `healdan-core`, `healdan-api` and `healdan-storage` test, as they run through CE's DAO: a non-admin's folder move needs Move on everything in the tree and Add on the target, and a folder delete is refused while a live document inside is checked out or immutable, so a test that moves or deletes folders as a non-admin grants the rights first (`HealdanFixtures.grant`; `AbstractRulesTestCase` has a ready layout), and every delete makes a Trash item. The upstream tests for the Trash's edits to CE are in CI's `UPSTREAM_TESTS`, named in the upstream edits' list above.
- `healdan-api`'s `ApiCall` sends a request to `http://localhost:8080`, the test context's `server.url`, unless `server(...)` names another. A sign-in start on any other name is sent to the public address first.
- Provider sign-in tests run against `FakeProvider`, a JDK HTTP server in `healdan-core`'s test-jar that serves discovery, keys and a token endpoint and signs its ID tokens with Nimbus. `SignInTestHooks`, in the same test-jar, allows plain HTTP, sets the TLS provider calls trust (`FakeProvider.trust()` uses it) and moves the clocks of pending sign-ins, one-time codes and the re-check; `FakeProvider.close()` resets it.
- `healdan-storage`'s tests extend `AbstractStorageTestCase` (on `AbstractHealdanTestCase`), which runs CE through `HealdanStorage`: it writes `healdan-core`'s test `context.properties` again as `context-storage.properties` with `store` swapped (its `baseConfigResource()`, which the base class writes again as `pg-context-storage.properties`), and registers the module's `plugin.xml`. Staging, the cache, the key files and the secret key are under `target/`. Storage is tested in three layers: `MemoryBackend` (faults on demand; `s3Like` acts as a bucket) and `LocalBackend` under `target/`, with `BackendContract` run on each backend; `FakeS3`, a JDK HTTP and HTTPS server in the tests that answers `S3Backend`'s calls and refuses what S3 refuses (`S3BackendTest`); and Garage on the smoke stack (step 5f). No test makes a real start, so tests call `Mover.runOnce()` and the like themselves; `StorageStartupTest` starts the timers with their waits shortened.
- Some tests load plugin manifests from fixture jars in `src/test/resources` through `getPluginArchives()`. Those jars are hand-maintained fixtures, not built from source.
- Tests write their stores, indexes and temp files under `target/`.
