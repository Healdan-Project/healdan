# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo, Healdan (`Healdan-Project/healdan` on GitHub), is a hard fork of LogicalDOC Community Edition (LGPLv3), a Java document management system. It started from 9.3.1 and follows upstream's releases; the root POM's version is the one it's on. It's detached from GitHub's fork network. The plan is to take it in its own direction (a new UI, bespoke features, replacements for features LogicalDOC sells as paid extras) while still merging upstream core and security fixes.

- Upstream is `https://github.com/logicaldoc/community.git`. A fresh clone needs `git remote add upstream <that url>`.
- Sync upstream by merging `upstream/master` into a dedicated branch and opening a PR to `master`. Merge, never squash or rebase, so the shared history stays intact. Keep sync PRs free of feature work.
  - Existing databases never get LogicalDOC's schema changes (see "Docker"). When a sync changes LogicalDOC's tables, in a `logicaldoc-*` module's `sql/` scripts or in the columns an entity maps, add the SQL an existing database needs, with a check, to the Install manual's Changes to LogicalDOC's Tables (`site/content/install/upgrading.md`) in the sync PR, a merge fix like the icons.
- Healdan's own modules (`healdan-*`) follow upstream's version: their POM parent and `plugin.xml` version match the root POM's. A module left behind makes Maven look for stock LogicalDOC jars, which the build no longer fetches: it fails with `Non-resolvable parent POM … Could not find artifact com.logicaldoc:logicaldoc:pom:<old version>`. Bump the module instead.
  - When a clean sync merge brings a LogicalDOC release bump, `.github/scripts/upstream-sync.sh` adds a "Follow upstream to <version>" commit. After a conflicted merge it doesn't, so whoever resolves the conflicts bumps them too.
- Upstream changes `logicaldoc-core` and `logicaldoc-gui` the most. To keep syncs cheap, put new work in new plugin modules and avoid editing upstream files where possible.
- Upstream sometimes ships POMs that fail Maven validation (for example, a duplicate dependency). If CI fails within a minute, check POM errors, the icon check, the doc-links check, the hosts check, the Maven repository check, the database driver check and the web licence check (next bullets) first.
- The GUI bundles Font Awesome Free 6, but upstream writes the GUI against Font Awesome Pro. Pro styles (`fal`, `fa-light`, `fa-thin`, …) and Pro-only icon names compile fine and only show up at runtime, as blinking missing-icon placeholders.
  - `.github/scripts/check-fontawesome-icons.py` catches them. It runs first in `build-logicaldoc.yml`, and `build` must pass before a PR can merge. Run it locally with `python3 .github/scripts/check-fontawesome-icons.py`.
  - When it flags lines an upstream sync brought in, swap them for Free icons in the sync PR itself. That's a merge fix, not feature work.
- Nothing links to LogicalDOC's docs (docs, wiki, help or forums.logicaldoc.com). `.github/scripts/check-logicaldoc-doc-links.py` runs next to the icon check and fails `build` on one, naming the file and line. When a sync brings one in, point it at docs.healdan.com in the sync PR, a merge fix like the icons. Its `ALLOWED` list holds the few exact lines Healdan leaves alone, each with its reason (the `SystemInfo` defaults `HealdanSystemInfo` replaces). The docs site's pages are checked by `check-site-sources.py` instead, which allows no such link.
- Healdan never contacts LogicalDOC's servers (no statistics, registration, licence or news calls). `.github/scripts/check-logicaldoc-hosts.py` runs after the doc-links check and fails `build` on any host, URL or email address at logicaldoc.com, .it, .net or .org, naming the file and line. It skips tests, prose, the docs site and the SOAP, CMIS and WebDAV XML namespaces. When a sync brings one in, remove the call in the sync PR, a merge fix like the icons. Its `ALLOWED` list holds the exact lines nothing contacts, each with its reason.
- Builds get the artifacts only LogicalDOC's Maven repository has from Healdan's copies at `https://maven.healdan.com/` (repository `Healdan-Project/maven`), through a mirror of the `logicaldoc` repository in `docker/maven-settings.xml`. JAI, betelio, ksoap2 and Oracle's JDBC driver aren't among them: their licences don't allow hosting them, or they have none, so the build drops JAI, betelio and Oracle's driver, and leaves `logicaldoc-webserviceclient`, ksoap2's only user, out. `.github/scripts/check-maven-repositories.py` runs after the hosts check and fails `build` when a POM or the settings file points a repository at a LogicalDOC host the mirror doesn't cover.
  - When a sync bumps one of those artifacts or brings a new one, the build fails with `Could not find artifact … in healdan`. In the sync PR, as a merge fix, check its licence allows hosting it, run `python3 import-artifact.py <group>:<artifact>:<version> --project … --licence …` in a checkout of `Healdan-Project/maven`, push, and re-run CI once `python3 import-artifact.py --verify https://maven.healdan.com/` passes. One whose licence doesn't allow hosting is dropped instead, as JAI was. A missing `com.logicaldoc:*` artifact is never imported: it means a module or version was left behind, so bump it. When the old GWT UI retires, its GWT libraries leave the build too (§3.1 of `docs/superpowers/specs/2026-10-29-healdan-maven-repository-design.md`).
- Healdan runs on MariaDB only, with HSQLDB for tests, and supports only open-source databases (Healdan-Project/healdan#110). MySQL isn't supported and won't be added. Oracle and SQL Server are gone: the WAR ships neither driver and the setup wizard doesn't offer them (`docs/superpowers/specs/2026-11-01-open-source-databases-design.md`). CE's code paths for them (`isOracle()`, `isSQLServer()` and the branches they guard) and upstream's `.oracle` and `.mssql` SQL variants stay, as they never run and removing them would cost every sync (upstream edits core's schema files most months, and a deleted file would conflict each time). The wizard still offers MySQL, though it starts on MariaDB, and the WAR still ships MySQL's driver, though Healdan refuses to start on it (owner, 2026-11-01). PostgreSQL is to become the first-class database (`docs/ROADMAP.md`, principle 9 and the backlog; `docs/reference/postgresql-recon.md` has the facts for its design session).
  - `.github/scripts/check-database-drivers.py` runs after the Maven repository check and fails `build` on a POM dependency on Oracle's or SQL Server's JDBC driver, or a tracked file naming one of their driver classes, naming the file and line. It skips tests, prose and the docs site. When a sync brings one in, take it out in the sync PR, a merge fix like the icons.
- The User app's npm packages ship in a page Healdan serves, so their licences matter. `.github/scripts/check-web-licences.py` runs after the database driver check and fails `build` on a package in `healdan-web/web/package-lock.json` that the app ships (no `dev: true`) with a licence outside MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC and 0BSD, or with none, or a development-only one outside those and BlueOak-1.0.0, CC0-1.0, CC-BY-4.0, Python-2.0 and Unlicense. It names the package and its licence. Its `ALLOWED` list holds the reviewed exceptions, each with the licence reviewed and its reason; an entry whose package the lockfile now gives another licence fails, and so does one the lockfile no longer has. `scripts/notices.mjs` writes the notices of what ships into `apps/user/dist/notices.txt`, and fails on a shipped package with no licence file.
- `README.md` opens with Healdan's notice that it's a modified version of LogicalDOC CE, which the LGPL asks for, then its Status section (experimental, no warranty, use at your own risk), then points to the docs site. It's Healdan's own now: when a sync brings an edit to upstream's README, keep Healdan's. `Build_this_Sources.md` and `docker/README.md` are short pointers to the site.
  - The docs site's home page and the Install manual's first page carry the same status notice. Change all three together.
  - `GPL-3.0.txt` is the GPLv3, which the LGPL in `LICENSE` incorporates. It isn't named `COPYING`, because GitHub would then stop detecting the repository's licence as LGPL-3.0.

## Build and test

You need JDK 25 and Maven 3.9+. The JDK is the one the `Dockerfile`'s `MAVEN_IMAGE` and `TOMCAT_IMAGE` name; CI's `build` check reads it from there and fails if the two differ. `source.level` in `logicaldoc-parent/pom.xml` sets the Java language level, and the GWT client compiles at source level 17. Some dependencies aren't on Maven Central. They come from Healdan's copies at `https://maven.healdan.com/` and from `https://repo.terracotta.org/maven2`, which `docker/maven-settings.xml` lists. CI and the Docker build copy it to `~/.m2/settings.xml`; copy it there for local builds.

```bash
mvn -B -ntp -DskipTests install                          # full reactor build (what the Docker image runs)
mvn -B -ntp -pl logicaldoc-webapp -am -DskipTests package # deployable WAR -> logicaldoc-webapp/target/*.war
mvn -pl logicaldoc-core test                              # one module's tests (sibling modules must be installed first)
mvn -pl logicaldoc-core test -Dtest=DocumentManagerTest   # one test class
mvn -pl logicaldoc-core test -Dtest='DocumentManagerTest#testCopyToFolder' # one method
mvn -pl healdan-core test -Dtest=FilingRulesTest          # Healdan's tests, or one class of them
mvn -pl healdan-core -DskipTests install                  # healdan-core with its test-jar, which healdan-api's tests need
mvn -pl healdan-api test -Dtest=FolderResourceTest        # the API's tests, or one class of them
mvn -pl healdan-storage test                              # the storage module's tests (needs healdan-core installed with its test-jar, as healdan-api's do)
dotnet test clients/helper/Healdan.Helper.sln             # the desktop helper's tests (.NET 10 SDK; global.json pins it)
dotnet test clients/helper/Healdan.Helper.sln --filter "Category=MacKeychain" # the real macOS keychain, by hand on a Mac
HEALDAN_MAC_OFFICE=1 dotnet test clients/helper/Healdan.Helper.sln --filter "Category=MacOffice" # the real Word, Excel and PowerPoint, by hand on a Mac with Office (they open windows)
python3 -m unittest discover -s clients/libreoffice/tests -v # the LibreOffice extension's tests (standard library only)
node --test 'clients/office/test/*.test.js'               # the Office add-in's logic (Node 22+, nothing to install; Node 21+ takes the argument as a file pattern, so a folder fails)
cd healdan-web/web && npm ci --ignore-scripts             # the User app's packages (Node 24, `.nvmrc`; Maven's build downloads its own into healdan-web/target/)
cd healdan-web/web && npm run generate                    # the app's API types, from healdan-api's openapi.yaml
cd healdan-web/web && npm run typecheck                   # tsc over the workspace
cd healdan-web/web && npm run lint                        # ESLint
cd healdan-web/web && npm test                            # the app's Vitest tests and Node's runner for scripts/
cd healdan-web/web && npm run build                       # generate and typecheck, then Vite's build into apps/user/dist/
mvn -pl healdan-web -am -DskipTests package -Dhealdan.web.skip=true -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true # healdan-web without the Node build (its jar then holds no app) or the GWT compile
clients/libreoffice/build.sh                              # the LibreOffice extension, packaged as clients/libreoffice/healdan.oxt (reproducible)
dotnet run --project clients/helper/tools/IconRender      # the extension's toolbar images and icon, from the helper's icons (by hand, on a Mac)
clients/helper/packaging/mac/package.sh 1.2.3             # Healdan Helper.app and its .dmg, on a Mac; signed only with SIGN_IDENTITY set
HEALDAN_HELPER_DEV_ROOT=/tmp/hh dotnet run --project clients/helper/Healdan.Helper # a Debug helper with its files and keychain entry apart; no links, notifications or .oxt
python3 docker/demo/build.py                              # the demo firm's files, from docker/demo/sources/ (needs a built image)
```

- `logicaldoc-parent` is a reactor module, and the root POM inherits from it, so dependency and plugin versions live there.
- `logicaldoc-gui` runs a GWT compile for each GWT module (frontend, login, setup), which is slow. Skip it with `-Dgwt.skipCompilation=true` when you aren't touching the UI; the module's Java still compiles, which `healdan-core` needs.
  - Up to `test` that's enough. For `package` or `install`, add `-Dmaven.antrun.skip=true` and `-pl '!logicaldoc-webapp'`, as CI's `build` check does. The GUI's antrun step fails without the GWT output, and skipping antrun leaves every plugin zip unfinished, so the WAR built from them is broken.
- `healdan-web` builds the User app (`healdan-web/web`, an npm workspace) through `frontend-maven-plugin`, which downloads Node into `healdan-web/target/` (the version in `.nvmrc`, which the POM names too: change both) and runs `npm ci --ignore-scripts` and `npm run build` in `generate-resources`; `maven-resources-plugin` then copies `apps/user/dist/` into the jar's `healdan/app/user`, which `AppServlet` serves. `-Dhealdan.web.skip=true` skips Node, and the copy then does nothing when `dist/` doesn't exist, so the jar holds no app and `/app/` answers 503. CI's `build` check passes it everywhere; the `Web` check and the Docker build do the Node build (the Dockerfile keeps npm's cache in a mount).
- Spring-based tests fail in `setUp` unless `~/logicaldoc-dev.properties` exists. An empty file works; CI creates one.
- `healdan-core`'s, `healdan-api`'s and `healdan-storage`'s tests run against the installed jars of the modules they use. After changing `logicaldoc-core`, `logicaldoc-webapp` or `logicaldoc-gui`, re-install that module (`-pl <module> -DskipTests -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true install`) before running them.
- `healdan-api`'s and `healdan-storage`'s tests also need `healdan-core` installed, test-jar included: they reuse its `AbstractHealdanTestCase`, fixtures and test `context.properties`. Re-install it after changing `healdan-core`.
  - `-DskipTests` still compiles tests, so it builds and installs that test-jar. `-Dmaven.test.skip=true` doesn't, and their `with-tests` profiles then leave the test-jar dependency out, so the build works but `healdan-api`'s and `healdan-storage`'s tests can't run until `healdan-core` is installed with `-DskipTests`.
- CI's `build` check compiles every module except the WAR, skipping the GWT compile, and runs Healdan's tests in parallel shards. The Docker image CI does the GWT compile and the WAR. Upstream modules' other tests don't run in CI.
  - The tests are every test class in a `healdan-*` module (found without a list) and the upstream tests named in the workflow's `UPSTREAM_TESTS`, which cover Healdan's edits to upstream code. Add a test class there when a change edits upstream code. A name no upstream module has fails the check.
  - The `checks` job runs the quick checks, then `.github/scripts/test-shards.py` splits the tests into shards of about five minutes (at most eight). Each class weighs its time in the newest successful run, which the `test-times` job caches, or 3 s per `@Test` until it has one. Each `Tests (n of N)` job installs the modules, without javadoc or plugin zips, and runs its share. The `build` job, the check master requires, passes when they all did, or when a docs-only pull request skipped them.
  - Its Maven repository cache falls back to master's newest copy, and only master saves it (from one shard), so a POM edit downloads only what it adds.
  - Each shard deletes the restored copy's `_remote.repositories` files, so Maven uses every cached file whichever Maven saved it. Maven 3.9 records a file's repository by id and 3.10 by id and URL hash, and 3.9 rejects 3.10's. `ubuntu-latest`'s images ship both, and on 2026-10-29 every shard re-downloaded everything and failed on SourceForge's 403.
  - The Docker build doesn't need this: its `maven:3.9` image writes and reads its own copy, and 3.10 accepts 3.9's records.
- `.github/scripts/code-changed.sh` writes three outputs for a pull request (a push gets all true):
  - `code` is false when it changes only docs (`docs/`, `site/`, Markdown outside `src/`), `clients/helper/`, `clients/libreoffice/`, `clients/icons/`, or any of them. The Java and Docker workflows then skip their build steps and still report the required checks. A change under `clients/office/` counts as code as well as clients, because `healdan-api` packages the Office add-in's pages and manifest into its jar (Markdown there stays docs).
  - `clients` is true when it changes anything under `clients/`, `clients.yml`, or the API contract (`healdan-api`'s `openapi.yaml`, which the helper's contract tests read). `clients.yml` otherwise skips its test jobs.
  - `web` is true when it changes anything under `healdan-web/`, `web.yml`, or the API contract (the app's types are generated from it). `web.yml` otherwise skips its app job.
- `.github/workflows/clients.yml` runs the helper's `dotnet test` on `ubuntu-24.04` and `macos-15`, the extension's Python tests on `ubuntu-24.04`, and the Office add-in's `node --test` there too. Its `Clients` job passes when they did, or were skipped because nothing under `clients/` changed. `Clients` is one of master's required checks.
  - A `helper-v1.2.3` tag (or a run by hand) also runs `package-mac`, which packages the macOS helper with `clients/helper/packaging/mac/package.sh`, and `release-mac`, which attaches the `.dmg` to the tag's release, only for a pushed tag and once `xcrun stapler validate` passes on it. They never run for pull requests, and `Clients` doesn't need them.
  - Only official releases stay on GitHub: `release-mac` for `1.2.3` deletes the `1.2.3-*` pre-releases and their `.dmg`s, keeping their tags as the record of what was tested, and refuses to publish a pre-release of a version already released.
  - Signing and notarising need six secrets in the `helper-release` environment, which only `helper-v*` tags may use (`APPLE_DEVELOPER_ID_P12`, `APPLE_DEVELOPER_ID_PASSWORD`, `APPLE_TEAM_ID`, `NOTARY_KEY`, `NOTARY_KEY_ID`, `NOTARY_ISSUER`; the Developer Guide's CI page says what each holds). Without them, as in a run by hand on a branch, the package is built unsigned and only uploaded as an artifact.
- `.github/workflows/web.yml` runs the User app's `npm ci --ignore-scripts`, `generate`, `typecheck`, `lint`, `test` and `build` in `healdan-web/web` on `ubuntu-24.04`, with the Node in `.nvmrc`. Its `Web` job passes when the app job did, or was skipped because `code-changed.sh` said `web=false`. `Web` is the check for master's ruleset to require.
- Helper tests with `[Trait("Category", "Stack")]` need `HEALDAN_STACK_URL` and skip without it; `StackProviderSignInTests` also needs `HEALDAN_STACK_SIGNIN_PROVIDER`. `docker/smoke-test.sh` step 5d runs them against the smoke stack, only with `SMOKE_HELPER_TEST=1` (CI sets it, after setting up .NET), and fails unless two passed and none skipped (`HELPER_STACK_TESTS` in the script, which a new `Stack` test changes). A pull request that changes only the helper, the extension or the icons doesn't build the image, so those tests run on master after the merge and on pull requests that change the server.
- `logicaldoc-webservicesamples` and `logicaldoc-webserviceclient` aren't in the reactor.

## Docker

- `Dockerfile` (stages `build` → `tools` → `runtime`) and `compose.yaml` are this fork's own. The docs site's Install manual (`site/content/install/`) is the user guide, and its Developer Guide covers the dev overlay, tests and CI; the design is `docs/superpowers/specs/2026-10-15-docker-compose-stack-design.md`.
- The container never runs the setup wizard. `docker/tools/src/DockerInit.java` seeds `context.properties` and, on a fresh database, creates the schema by running the `DbInit` scripts from every `plugin.xml`, so a plugin's `DbInit` extension is picked up for new installs. Then, on every start, it installs any of CE's plugins not yet installed with CE's own `PluginRegistry`, before Tomcat starts, so a fresh stack's sign-in page doesn't say "The application has to be restarted" (§15 of the Docker spec); the entrypoint puts the conf folder on its classpath for them. Existing databases are never migrated, apart from Healdan's own `hd_` tables, which Flyway upgrades on every start (see "Healdan's code"). A plugin or upstream change that adds SQL to CE's tables needs it applied by hand there.
  - On every start against an existing database, `DockerInit` checks that CE's tables have every table and column the plan's `DbInit` scripts create (`DbInitPlan.createdColumns`, against `information_schema.columns`), and stops, naming each missing one and pointing to the Install manual's Changes to LogicalDOC's Tables, before Tomcat starts. It never adds them, and what a database has besides doesn't count. A table a later plugin's script creates stops it too, as nothing else would create it (§16 of the Docker spec). A fresh database's start runs the same check after `DBInit`.
- On every start, keys in the image's default `context.properties` that the conf volume lacks are added. Values are never overwritten, with four exceptions:
  - `product.release` and `product.year` (`ConfigPlan.IMAGE_KEYS`) describe the image, so they're always taken from it.
  - A key still holding a default an earlier image shipped takes the image's (`ConfigPlan.REPLACED_DEFAULTS`); an admin's own value stays. So far that's `cachecontrol`, whose `*.nocache.js:no-cache` makes browsers check the GWT loaders on every load. When Healdan changes a default that existing installs should get, add the value it replaces there.
  - Non-breaking spaces (0xA0) in `security.csp` (`ConfigPlan.PLAIN_SPACE_KEYS`) become plain ones, in an admin's policy too, and the rest of the value stays. Upstream's value had one after `object-src`, so browsers ignored `object-src 'none'`.
  - `store` (`ConfigPlan.HEALDAN_KEYS`) is set to `com.logicaldoc.healdan.storage.HealdanStorage` whatever the file holds, and `DockerInit` checks it was stored, so `healdan-storage`'s `HealdanStorage` is CE's `store` bean while the image's defaults, upstream's, keep `FSStore`. An install moves to it on its first start on an image that has it, its files staying where they are. Outside Docker the key is what the file says, upstream's `FSStore` by default, and `healdan-storage` then does nothing.
- The app has three volumes: `logicaldoc-conf` (`/opt/logicaldoc/conf`), `logicaldoc-repository` (`/opt/logicaldoc/repository`) and `logicaldoc-cache` (`/opt/logicaldoc/cache`, `healdan-storage`'s read cache, which only holds copies, so backups leave it out). The entrypoint hands all three to uid 1000 at every start, and goes on when a share refuses but uid 1000 can write to it. `setenv.sh` names `healdan-storage`'s folders: staging (`healdan.storageStaging`, `repository/staging`), the cache (`healdan.storageCache`) and the backends' key files (`healdan.storageKeys`, `conf/healdan-storage-keys`).
- `docker/server.xml`'s `RemoteIpValve` believes `X-Forwarded-For` and `-Proto` only from `LOGICALDOC_TRUSTED_PROXIES`, or, when it's unset, the Docker networks the container is on. `DockerInit` (`TrustedProxies`) works the list out and checks it on every start, and `setenv.sh` passes it to Tomcat as `healdan.trustedProxies`.
- LogicalDOC only runs external programs listed in a classpath `allowed-commands.txt`. The lines in `docker/allowed-commands.txt` are re-added to the conf volume's copy on every start; a new external tool needs a line there.
- Tests (the Developer Guide's Tests page describes each):
  - `docker build --target tools .` for the init tool's unit tests (`DbInitPlanTest` reads the WAR's own `DbInit` scripts), and `WarParsersTest`, which parses a `.pptx`, an `.xlsx` and an `.xls` with the server's parsers for them on the WAR's own `WEB-INF/lib`. Maven's test classpath has every library's dependencies, so only it catches one of POI's that no plugin zip ships (#202). Other parsers' libraries aren't checked. `WarStorageTest`, beside it, does the same for `healdan-storage`'s zip. It builds the S3 client as the S3 backend does and sends one request to a closed loopback port, and it round-trips 3 MiB through Tink's streaming AEAD. A class of the AWS SDK's or Tink's that the zip leaves out fails the image build. `PluginInstallTest` installs the plugins as DockerInit does, then starts them again in a second JVM, as Tomcat does, which must ask for no restart. The copy of `web.xml` its installs edit is the one the image ships, so a container made afresh, whose plugins the repository volume says are installed, has their edits.
  - `docker/tests/test-*.sh`. Beside them, `docker/tests/bulk-documents.sh` isn't a test: it files `COUNT` generated documents into a folder on a throwaway stack (`BASE TOKEN FOLDER_ID COUNT [WORD]`), to measure big folders and searches.
  - `docker/smoke-test.sh` for end to end. Its step 2b runs `docker/tests/test-proxies.sh`, which forwarded addresses Tomcat believes. Its step 5c runs `docker/tests/test-api.sh`, M2's client flow through `/api/v1` with a Bearer token, through CE's real filter chain (SOAP's addresses answering 404, sign in, file, check out, save, download, the throttle, LogicalDOC's `loginApiKey` refusing the token, sign out). That script needs a fresh stack with the smoke overlay (it signs in as `admin`/`admin`, and leaves a username blocked for 15 minutes). Its step 5d, only with `SMOKE_HELPER_TEST=1` (CI sets it, after setting up .NET), runs the helper's stack tests (`dotnet test clients/helper/Healdan.Helper.sln --filter Category=Stack` with `HEALDAN_STACK_URL`): `admin` opens, saves twice and closes a document through the helper's cycle, and `sso-helper2` signs in through the stand-in Keycloak as the helper does, with a fake browser (`HEALDAN_STACK_SIGNIN_PROVIDER`, `_USER`, `_PASSWORD`, and `HEALDAN_STACK_KEYCLOAK`, Keycloak's host port). Its step 5e runs `docker/tests/test-signin.sh`, provider sign-in through the stand-in Keycloak with `curl` and a cookie jar (the web page's flow, linking by email, the gate, the helper's code and its exchange, and a person disabled at Keycloak losing their device token at the next re-check). Its step 5f runs `docker/tests/test-storage.sh`, storage backends against the stand-in Garage: a file filed in Smoke Cloud reaches Garage encrypted, files moved in from Smoke move up uncached, reads come back through Garage and from the read cache, with Garage stopped a save waits in staging, an uncached file answers `503` through the API, `/download` and a shared link, and `/convertpdf` of an uncached PDF serves CE's placeholder, and a matter moved to Smoke brings its files home, Garage keeping them held. Step 8 runs it again with `after-restart`: the rows as they were, a file read through Garage for the first time, and one read from the cache rebuilt from its folder with Garage stopped. The script stops and starts Garage itself, and needs curl 8.0.0 or later, whose `--aws-sigv4` sends the `x-amz-content-sha256` header Garage requires. ## Architecture

**Modules.** `logicaldoc-util` sits at the bottom. `logicaldoc-core` builds on it, and the feature modules build on core: `webservice` (REST via CXF; Healdan's `SoapRemover` removes its SOAP endpoints), `webdav`, `cmis`, `dropbox`, `android` and `ios`. `logicaldoc-webapp` is the WAR that bundles everything. `logicaldoc-gui` (GWT client) depends only on util. `logicaldoc-i18n` holds the resource bundles.

**Plugin system (JPF).** Almost every module is a plugin, and adding a plugin takes four pieces:
- `src/main/resources/plugin.xml` declares the plugin's ID, its dependencies and the extensions it contributes.
- A class extending `com.logicaldoc.util.plugin.LogicalDOCPlugin` registers servlets at install time with `addServlet(...)`. That edits `web.xml`, so a restart is required. It can also register scheduled tasks and loggers.
- `src/main/assembly/assemblyplugin.xml` packages a `*-plugin.zip` (classifier `plugin`). It takes only the dependencies its `<include>`s name, not theirs, and the WAR's `WEB-INF/lib` is the webapp's own dependencies and those zips' jars. So a library's own dependency ships only when some zip names it: core's names `org.apache.poi:*` but not POI's SparseBitSet, which `healdan-core`'s zip ships (#202). `docker/tools`' `WarParsersTest` catches one missing for POI's PowerPoint and Excel readers, not for other parsers, and its `WarStorageTest` one missing for the AWS SDK's and Tink's jars, which `healdan-storage`'s zip ships.
- An `artifactItem` in `logicaldoc-webapp/pom.xml` (maven-dependency-plugin) copies that zip in, and an antrun step unzips it into the WAR. Without this entry, the plugin isn't shipped.

Core's `plugin.xml` defines the extension points other plugins hook into: `DbInit`, `Parser`, `Language`, `ResourceBundle`, `Task`, `DocumentListener`, `FolderListener`, `UserListener`, `TicketListener`, `Authentication`, `ThumbnailBuilder`, `FormatConverter`, `Search`, `Feature`, `SystemInfo`, `TokenFilter`, `Store`, `Aspect` and `TokenProvider`. `logicaldoc-dropbox` is the smallest complete example of a plugin.

**Spring wiring.** `web.xml` boots `com.logicaldoc.util.spring.MainContext`. It component-scans `com.logicaldoc` for `@PluginContext` classes and imports the webapp's `context.xml`, which defines the datasource, session factory and transactions.
- Each module has a `XxxContext` class annotated `@PluginContext` + `@ComponentScan` + `@ImportResource("classpath:context/context-xxx.xml")`.
- Runtime settings come from `context.properties`, read through `ContextProperties`, which `Context.get().getConfig()` returns.
- Beans are fetched with `Context.get(Type.class)`, and DAOs expose a static `XxxDAO.get()`.
- **Both Spring and Hibernate only scan `com.logicaldoc`.** Code in any other package root isn't discovered unless you extend the scans.

**Persistence.**
- Hibernate 7 uses JPA-annotated `@Entity` classes, which `com.logicaldoc.util.spring.LocalSessionFactory` finds by classpath scan. The `*.hbm.xml` mapping location in `context.xml` is configured, but no such files exist.
- DAOs follow one pattern: an interface `XxxDAO extends PersistentObjectDAO<T>` and an implementation `HibernateXxxDAO extends HibernatePersistentObjectDAO<T>`.
- Every `PersistentObject` has a `tenantId` (multi-tenant).
- CE has no migration tool (Healdan's own tables use Flyway, below). CE's schema is plain SQL in `sql/logicaldoc-<module>.sql`, with DBMS-specific variants (`.mysql`, `.mariadb`, `.oracle`, `.mssql`) that `PluginDbInit` picks when one exists. Plugins add tables through a `DbInit` extension with a `sqlFile` parameter.
- The second-level cache is Infinispan (`infinispan.xml`, or `infinispan-cluster.xml` when clustering is on).

**UI ↔ server.** The UI uses GWT 2.12 and SmartGWT 14.1, with GWT modules `frontend`, `login`, `setup` and `common` under `com.logicaldoc.gui`.
- RPC calls go from interfaces in `gui/**/client/services` (`@RemoteServiceRelativePath`) to `logicaldoc-webapp/.../web/service/*ServiceImpl`, mapped in `logicaldoc-webapp/src/main/webapp/WEB-INF/web.xml` under `/frontend/*`.
- Grid and list data come from `web/data/*DataServlet`, which serves XML for SmartGWT DataSources at `/data/*.xml`.
- Other ways into the server are REST at `/services/rest/*` (`logicaldoc-webservice`, endpoints in `webservice/rest/endpoint`; `healdan-core`'s `SoapRemover` removes the module's SOAP endpoints at startup), WebDAV at `/webdav/*`, and CMIS.

**Edition feature gating.**
- The GUI shows or hides features with `Feature.enabled(n)`, which checks for the name `Feature_<n>`.
- Those names come from `Feature` extensions declared in plugins' `plugin.xml` (collected by `SystemInfo`).
- The GUI already contains client code for enterprise-only features whose server implementations aren't in this repo, for example the `ai`, `google`, `onlyoffice`, `saml` and `whatsapp` service interfaces.
- Replacing a paid extra therefore means three things: implement that RPC interface on the server, register its servlet, and declare the matching `Feature_<n>` extension.

## Healdan's code

- **`healdan-core`** is Healdan's plugin module (JPF id `healdan-core`, which requires `logicaldoc-core`). It holds Healdan's server rules and all its data, under `com.logicaldoc.healdan`, so CE's Spring and Hibernate scans find it with no edits.
  - Its GUI code is in `logicaldoc-gui` under `com.logicaldoc.gui.frontend.client.healdan`, reached from one-line hooks in upstream GUI classes.
  - Its servlets register with `@WebServlet`, never `addServlet`, because the Docker image rebuilds `web.xml`. RPC paths are `/frontend/healdan*` and data paths `/data/healdan*`.
  - Its listeners enforce the rules on every route. Extension ids in its `plugin.xml` must be unique: JPF silently drops the whole plugin on a duplicate.
  - At a real start `HealdanStartup.start()` fills CE's `ParserFactory` once, after the seeds and before the workers, CE's scheduler and any request (`HealdanStartupParsersTest`). CE fills it on first use, in a plain `HashMap`, and two first uses at once (the Indexer's two threads after a start) can leave it without `pdf` for good. `CatchAllParser` then converts a PDF to PDF and asks again, a new thread at each level, until the JVM can start no more threads (PR C's smoke test, 2026-11-11). Nothing may call `ParserFactory.init()` while anything parses.
- **`healdan-api`** is Healdan's JSON API, the HTTP layer at `/api/*` (JPF id `healdan-api`, which requires `healdan-core`; M2's spec is `docs/superpowers/specs/2026-10-23-m2-api-foundation-design.md`). Its code is under `com.logicaldoc.healdan.api`, and `HealdanContext`'s scan finds its beans, so it has no `@PluginContext` of its own. Domain code (tokens, read models) stays in `healdan-core`. The docs site's Developer Guide has a page for API clients (`site/content/developer/api.md`).
  - `ApiServlet` (`@WebServlet("/api/*")`) runs a CXF JAX-RS server on its own `ExtensionManagerBus`, not CXF's Spring bus, which would expose every `/services/rest` server under `/api/rest` too. Its resources are the Spring beans in the package that carry `@Path`.
  - `/api/**` is `security="none"` in `context-security.xml`: the API's `TokenFilter` signs requests in from `Authorization: Bearer hd_…` device tokens, or, when a request has no Bearer `Authorization` header, from the browser's CE web session on `WebSessionRoute`'s rule (M6 spec §8.1): `Sec-Fetch-Site: same-origin`; an `Origin`, when sent, that is the public address's or the request's own; `X-Healdan-Client: web` on `POST`, `PATCH`, `PUT` and `DELETE`, in any case, the method being the request's own (CXF's `_method` and `X-HTTP-Method-Override` stay off, which `WebSessionRouteTest` pins); and the CE session id only from the HTTP session's `sid` attribute. Never from a `sid` parameter or header, the `ldoc-sid` cookie, Basic or `X-API-KEY`. A same-origin request that breaks the rule is `403 web-session-refused`, and no open session `401`. `AppServlet` asks `WebSessionRoute` for the session and its user too, so a page load the API would refuse goes to sign-in.
  - On the web session `Caller.token()` is null, which the device-hold code (`DeviceHolds`, `ApiViews.heldHere`) takes as no device, so a resource that reads the token checks for null. It signs out with `DELETE /v1/session`, and a token with `DELETE /v1/auth/tokens/current`.
  - Device tokens work only at `/api`. `HealdanTokenAuthenticator` accepts one only inside `ApiTokens.openSession`, which hands CE's chain a one-time key, and refuses every other `hd_` key but the `hd_signin_` ones, which it leaves to `SignInAuthenticator` (M4), so CE's routes (`loginApiKey`, `X-API-KEY`, Basic) never take a token. Letting a token in elsewhere, such as WebDAV, needs a narrow allowance there.
  - `healdan-api/src/main/resources/healdan/api/openapi.yaml` (OpenAPI 3.1, served at `/api/v1/openapi.yaml`, browsable at `/api/docs/`) is hand-written and is the contract: `ApiTestCase` checks every response a test gets against it, and `RouteCoverageTest` fails when the routes and the file differ. A new endpoint goes into it in the same change. A list schema built with `allOf` needs `unevaluatedProperties: false` (see `Page`).
  - Errors are RFC 9457 problems with stable `code`s (`ApiProblem`); unreadable means `404`, as in the old UI.
- **`healdan-web`** is the User app, Healdan's browser app at `/app/` (JPF id `healdan-web`; M6's spec is `docs/superpowers/specs/2026-11-10-m6-user-app-design.md`). Its Java is `com.logicaldoc.healdan.app`: `AppServlet` (`@WebServlet("/app/*")`) serves the built app from the jar, answering any path that isn't a file the jar holds or under `assets/` (so `/app/doc/10388.2` too) with `index.html`, and, with no web session the API would accept (`WebSessionRoute.session` and `user`), stores the return path (`ReturnPath`, accepted only in a strict form, else `/app/`) and redirects to `login.jsp`. A signed-in page load forgets the return path. The app is the npm workspace `healdan-web/web` (React, TypeScript, Vite; `packages/api` typed from `openapi.yaml`, `packages/ui` with the components, colour tokens and string catalogue, `apps/user`). Only the root context is supported. Its code talks to `/api/v1` only, through the same-origin web-session route (see `healdan-api` above), never with a token.
  - At an address that isn't secure (plain `http://` off the machine itself), browsers send no `Sec-Fetch-Site`, so the web route refuses every call: `main.tsx`'s `start` then draws only `frame/InsecureAddress.tsx`, which says so and links to the Classic Interface, before any API call (R91). Nothing the app loads may need a secure context: a drag's page token is made with `crypto.getRandomValues`, not `randomUUID`.
  - Every list, search and count request carries `zone`, the browser's IANA time zone (`filterParams`), in which the server cuts Today and a range's days (R90).
  - Screens import React Aria only through `@healdan/ui` (ESLint refuses it elsewhere), and `dangerouslySetInnerHTML` is refused everywhere. The Developer Guide's The Web App page has the workspace, running Vite's dev server against a stack (`npm run dev` in `apps/user`, `HEALDAN_DEV_TARGET`, a proxy for `/api`, `/login.jsp` and `/j_spring_security_check` that rewrites `Origin`) and adding a view.
  - PDFs preview with PDF.js, whose settings keep it inside `AppServlet`'s policy: no WebAssembly (`useWasm: false`), the worker, CMaps, standard fonts and JavaScript image decoders all from `/app/` (`apps/user/pdfjs-data.mjs` puts the data in the build), and no eval (PDF.js 6 has none, so it isn't passed `isEvalSupported`; `scripts/pdfjs-policy.test.mjs` checks). Change none without `e2e/working.spec.ts` in both browsers. The Developer Guide's The Web App page has them. `getResponse` on the API client is for binary answers and `202`s.
  - A filed email is read through `healdan-api`'s `MessageResource` (`/v1/documents/{n}/message`, `/body`, `/parts/{id}` and `/attachments/{id}/file`; spec §6.6, §9.4), `eml` and `msg` alike (`healdan-core`'s `StoredMessage`). `EmailBody` cleans the HTML with jsoup (`Safelist.relaxed()` plus styling, with every `url()`, `@import` and CSS escape taken out), embeds `cid:` pictures as `data:` up to 2 MiB, and removes internet pictures unless `pictures=true`. The `/body` page carries its own `Content-Security-Policy` (`EmailBody.policy`), and the app shows it in an `<iframe sandbox="allow-popups allow-popups-to-escape-sandbox">`, never with `allow-scripts` or `allow-same-origin`. Every answer that serves stored bytes inline (`/preview`'s pictures, `/parts/{id}?inline=true`) carries `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`. `AppServlet`'s policy stays as it is. A `msg` keeps no Content-IDs (CE's reader), so its inline pictures are attachments.
  - Filing is `apps/user/src/filing/` (spec §6.5): `FilingProvider` in the frame owns an in-memory upload queue (three at once, kept across views, `beforeunload` while it runs), the form that comes first (`details/FieldsForm.tsx`, shared with `PropertiesForm`) and the tray (`@healdan/ui`'s `Tray`, a top layer). It handles only drops that carry `Files`; a drop that carries `ROWS_TYPE` (`application/x-healdan-documents`, the app's own rows) is for the move to take. A drop on a document's row asks for a new version, which goes through `saveVersion` (shared with Check In), never taking over a hold (R14).
  - Below 1,024 pixels (`frame/narrow.ts`) the left pane and the right region fold away behind top-bar buttons (**Navigation**, **Details and Filters**) and open over the list, where Esc closes them; a click on a row never opens the region (`open('details', { reveal: false })`). **Signed-in Devices** (`devices/SignedInDevices.tsx`, from the person menu) lists `GET /v1/auth/tokens` with Revoke, and the web page's own sign-in isn't in it (R14). The Upload button, pressed with Option, shows the filing form first: the keyboard's route to it.
  - The old UI links to it with **Open in Healdan**, a hook in `MainMenu` (`HealdanAppLink`, an upstream edit listed in M6's spec §14.1), and the app links back with **Classic Interface** (`frontend.jsp`, same session). `ui.start` (`app` or `classic`) decides where a plain sign-in lands.
- **Sign-in through a provider** (M4, OpenID Connect; spec `docs/superpowers/specs/2026-11-01-m4-oidc-sign-in-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.signin`, with its pages in `healdan-api`'s `SignInResource` at `/api/signin/`. The docs are the Install manual's Sign-In Providers section (`site/content/install/sign-in/`), the Admin Guide's Healdan Settings page and the Developer Guide's API page.
  - Providers' settings are `signin.*` rows in `hd_setting` (`SignInProviders`, which validates everything before it writes). A link is the provider's id and the identity, with no issuer, so the identity claim and the issuer (but for a trailing slash) can't change while the provider has linked accounts (R21, R33), and the identity claim can't be one people can change: `email`, `preferred_username`, `upn`, `unique_name`, `name` or `nickname` (R34). Refusals reach the GUI as HTML, so they name a provider by its id, never its label. The group map is `hd_signin_group`. Links between accounts and identities are `hd_signin_identity` rows, kept as records once unlinked; `hd_linkkey` and `hd_linkuser` are set only while linked, so the unique indexes allow one link in use per identity and per account.
  - `SecretBox` seals client secrets, helpers' refresh tokens and storage backends' S3 secrets (AES-256-GCM) under a key file at `-Dhealdan.secretKey`, which `docker/setenv.sh` puts in the conf volume and the modules' tests put under `target/` (`healdan-storage`'s under `target/conf/`, the configuration folder no local backend may share). Losing it means entering the secrets again, helpers signing in again, and S3 backends failing until their secrets are entered. Once anything stored is sealed, only an admin who types a secret and confirms a new key makes one (`sealWithNewKey`): a client secret on the Sign-In tab, or an S3 secret on the Storage tab. Any other seal fails (`KeyMissingException`), so a key file missing for a while loses nothing. Keys are made under `healdan-secret.key.lock`, so two servers sharing the folder make one.
  - A linked account has `UserSource.OIDC` (stored as 3, appended so the others keep their numbers; `UserSourceTest` pins them), no password and no impersonators. `ProviderPasswordListener` refuses either with an `AuthenticationException`, the only veto `HibernateUserDAO` passes on: it logs and swallows a user listener's `PersistenceException`. CE's user delete runs no user listener at all.
  - Linking an account, or making a linked one a provider account again, deletes its LogicalDOC API keys and, after the commit, closes every open CE session of the account on this node, and every session its keys opened (`SignInAccounts`, R31). The web page can still make a key for it, which `HealdanThrottle` refuses at sign-in on every route.
  - A provider sign-in opens its CE session through the whole chain with a one-time `hd_signin_` key (`SignIns`, `SignInAuthenticator`), on M2's pattern; `HealdanTokenAuthenticator` leaves those keys alone. The helper gets a 60-second one-time code for its device token instead, and a helper start whose PKCE challenge another sign-in still has, waiting or with a code, is refused as `expired`.
  - `/api/signin/` is pages, not JSON API: `openapi.yaml`, `RouteCoverageTest` and `Contract` leave it out, as `/api/addin/`. `PublicAddress` (`healdan-core`'s `web` package) gives the server's public address to both and to the Sign-In tab.
  - Provider calls go through Nimbus (`ProviderClient`), which builds the requests and reads the answers, sent by the JDK's `HttpClient` with the JVM's trust store and HTTP proxy properties (a SOCKS proxy is refused, as the client would skip it), never LogicalDOC's proxy settings, and only over HTTPS unless `HEALDAN_SIGNIN_ALLOW_HTTP=true`, which only the sign-in overlay sets. Each call's whole answer must come within 10 seconds (a refresh's 20) and weigh at most 1 MiB (the keys 50 KB). A discovery document that couldn't be fetched is remembered for 30 seconds per provider, and every use fails at once meanwhile; `forget`, which saving a provider calls, clears it.
  - Of the provider's answers, only `invalid_grant` revokes a helper at its re-check (`ProviderRecheck`, from `TokenFilter`); an outage never does. The gate refusing the account, the account no longer linked to that provider (R19), and a refresh token that won't open revoke too. Revoking clears the token's sealed refresh token, whose column V7 widened (R35).
- **Email** (M5; spec `docs/superpowers/specs/2026-11-03-m5-email-design.md`) is `healdan-core`'s `com.logicaldoc.healdan.email` and `healdan-api`'s `EmailResource` (`POST /api/v1/emails/inspect`, `POST /api/v1/emails`, `GET /api/v1/emails`; in `openapi.yaml`). The docs are the User Guide's Filing Email from Outlook and Emails (Once in Each Matter), the Install manual's Office Integration (deploying `outlook-manifest.xml`), Known Limitations and Upgrading (emails filed before M5), and the Developer Guide's API (Filing Email), Desktop Clients and How Healdan Extends LogicalDOC (`hd_email` and the worker) pages.
  - The Message-ID is the `emailmessageid` property (`ATTR_EMAILMESSAGEID`, the `profile-message-id` seed), which `EmailDocumentListener` reads on every route: the header without brackets or whitespace, at most 998 characters, an `.msg`'s from its `PR_INTERNET_MESSAGE_ID` stream, which `EmailFields` reads with POI (CE's `EMail` has none). A check-in replaces the property and the row with the new version's, or takes them away when it's no message. `hd_email` (V8, `hd_docid`, `hd_messageid`, a SHA-256 hash; no matter column, since `MatterLocator.locate` finds each copy's matter afresh) is the index, and the attribute isn't the truth: CE's screens can edit it. Rows for documents deleted for good stay; every lookup joins `ld_document` and skips deleted documents and aliases.
  - `EmailIndexWorker` fills both for emails already in Healdan, with a cursor (`email.index.cursor`) and `email.index` = `done` in `hd_setting`. It runs from its cursor at every start; to run it again from the start delete both and restart.
  - A matter holds a message once (`OncePerMatter`): `OncePerMatterListener` (`healdanOncePerMatter`, position 135, after the email fields at 130 and before the doc # at 140) refuses new email documents and stores that move a document into another matter (never a move within its matter), and `HealdanHooksImpl` covers the routes that write before a listener (moves, restores, folder copies and merges). It refuses with `AlreadyFiledException`, a `HealdanRuleException`, which `ProblemMapper` answers as `409 already-filed` with the copy as `document`. Only copies the caller can read count; no user means every copy counts.
  - There's no lock on `hd_matter`: a lock held across a folder copy's later `DocumentManager` waits deadlocks with any upload. The rule serialises on `DocumentManager`'s monitor, inside which each `create` and `moveToFolder` runs its listeners and, when no outer transaction is open, commits, so its check (with a fresh look at READ_COMMITTED for a transaction begun before the call) sees every filing that went through the monitor before it. `OncePerMatterConcurrencyTest` fails without it. Folder copies and merges (one transaction of several stores), folder moves and restores, and a direct `DocumentDAO.store` or `DocumentManager.update` that moves a document don't go through it, so one of them at the same moment as an upload of the same message into the same matter can still leave two copies. A cluster would need a lock again.
  - `EmailFiling` (with `Filer`, the filing of one document taken out of `DocumentResource.create`) files the email, its ticked attachments (`MessageParts` decides which are attachments and which inline; attachments take the email's sent properties) and their `attachment` links, each document in its own transaction and undone by compensation on a failure. `MessageLocks` holds a JVM lock per matter and Message-ID, which `Filer` takes too for an email filed on its own, so a repeat waits for the first filing, 30 seconds at most, then `409 filing-in-progress`. Filing needs WRITE on the folder, as `POST /v1/documents` does.
  - Never log subjects, addresses, attachment names or message contents at info or above; Message-IDs at debug only.
- **`healdan-storage`** keeps each Store's files on a storage backend of its own, a local or NFS folder or an S3 bucket (JPF id `healdan-storage`, which requires `healdan-core`; spec `docs/superpowers/specs/2026-11-01-s3-storage-backends-design.md`). Its code is under `com.logicaldoc.healdan.storage`, which `HealdanContext`'s scan finds. The Developer Guide's How Healdan Extends LogicalDOC page has how it plugs into CE. The docs are the Admin Guide's Storage Backends section (`site/content/admin/storage-backends/`), Stores and Healdan Settings pages; the Install manual's Cloud Storage, Backup and Restore, Host Folders, What Runs, Configuration, Upgrading, Troubleshooting and Known Limitations pages; and the Developer Guide's How Healdan Extends LogicalDOC, API (`503 storage-unreachable`), Tests, Continuous Integration and Building from Source pages.   - `hd_storage_file` (JDBC, `StoredFiles`) has a row per file, keyed by doc id and resource name. Backend 0 is staging, which has no `hd_storage_backend` row, and 1 is Original (`store.1.dir`). Each write gives the row a new random 64-bit `hd_write`, never a counter, which the mover's commit and the read cache's entries check. `exists`, `size` and `listResources` answer from the rows, and a file with no row is read from Original's folder. The mover lists only rows with `hd_waiting` set, so whatever leaves a file off its Store's backend sets it (`recordWrite`, `moved`, `setStore`, the recording seed, and `storeBackendChanged`, which every Store switch calls, including one back to Original, which deletes the Store's `hd_storage_store` row), and the nightly check mends one that drifted. Nobody holds two. The mover and the purge, once they hold one, write nothing while an open transaction has written that file's rows (`writtenByOpenTransaction`), and leave the file for a later pass. Healdan runs one node; a cluster would need a lock in the database.
  - Staging, the read cache and the key files are `-Dhealdan.storageStaging`, `-Dhealdan.storageCache` and `-Dhealdan.storageKeys`; without them, `staging/` and `cache/` beside `store.1.dir`, and `healdan-storage-keys/` beside `SecretBox`'s key. Staging can't be, hold or sit inside Original's folder or the key files', nor the cache any of those three (`Staging.apart`, by path, links not followed). A backend added or edited can't overlap them, the configuration folder or another backend (`BackendDrafts.checkPlace`): folders by path and with links followed, and S3 buckets and prefixes within one S3 service (every AWS host is one, any other endpoint its host and port).
  - An encrypted backend's key is `backend-<id>.key`, 32 bytes, mode 600 in a folder of mode 700, never in the database: lose it and the recovery key, and its files can't be read. Every backend has a marker naming this install (`storage.installId`) and the backend, `.healdan-backend` in a folder or `<prefix>.healdan-backend` in a bucket; one missing or another's fails the backend, so an unmounted share is never written to, and the recording seed stops startup rather than mark an Original with no marker and no file while `ld_document` has documents not deleted. An encrypted backend's `.healdan-check` must decrypt under the key file at start, at the first write to a backend not yet checked, and on Test.

## Tests

- Tests use JUnit 4. The base class `com.logicaldoc.util.junit.AbstractTestCase` builds a Spring context from the module's test `context.xml` and `context.properties`.
- That context includes an in-memory HSQLDB loaded from `getDatabaseScripts()`. For core, that's `sql/logicaldoc-core.sql` plus the test `data.sql` fixture data.
- Each module has its own base class, such as `AbstractCoreTestCase`, `AbstractWebappTestCase` or `AbstractWebserviceTestCase`. Extend the closest one. `healdan-core`'s `AbstractHealdanTestCase` also runs Healdan's migrations and seeds on the test database.
- `healdan-api`'s `ApiTestCase` extends `AbstractHealdanTestCase` (from `healdan-core`'s test-jar) and drives the real `ApiServlet`, filters included, through Spring's servlet mocks. Its `context.properties` is copied at build time from `../healdan-core/src/test/resources`.
- The sign-in throttle is on in every `healdan-core` and `healdan-api` test (the `throttle-signin` seed runs on each fresh test database), so a test that fails one user's password five times blocks that user for the rest of the test, unless it then gives that user a new password or creates the account after the failures, which clears its username's count (`ThrottleUserListener`).
- `healdan-api`'s `ApiCall` sends a request to `http://localhost:8080`, the test context's `server.url`, unless `server(...)` names another. A sign-in start on any other name is sent to the public address first.
- Provider sign-in tests run against `FakeProvider`, a JDK HTTP server in `healdan-core`'s test-jar that serves discovery, keys and a token endpoint and signs its ID tokens with Nimbus. `SignInTestHooks`, in the same test-jar, allows plain HTTP, sets the TLS provider calls trust (`FakeProvider.trust()` uses it) and moves the clocks of pending sign-ins, one-time codes and the re-check; `FakeProvider.close()` resets it.
- `healdan-storage`'s tests extend `AbstractStorageTestCase` (on `AbstractHealdanTestCase`), which runs CE through `HealdanStorage`: it writes `healdan-core`'s test `context.properties` again as `context-storage.properties` with `store` swapped, and registers the module's `plugin.xml`. Staging, the cache, the key files and the secret key are under `target/`. Storage is tested in three layers: `MemoryBackend` (faults on demand; `s3Like` acts as a bucket) and `LocalBackend` under `target/`, with `BackendContract` run on each backend; `FakeS3`, a JDK HTTP and HTTPS server in the tests that answers `S3Backend`'s calls and refuses what S3 refuses (`S3BackendTest`); and Garage on the smoke stack (step 5f). No test makes a real start, so tests call `Mover.runOnce()` and the like themselves; `StorageStartupTest` starts the timers with their waits shortened.
- Some tests load plugin manifests from fixture jars in `src/test/resources` through `getPluginArchives()`. Those jars are hand-maintained fixtures, not built from source.
- Tests write their stores, indexes and temp files under `target/`.
