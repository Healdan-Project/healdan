## 1. Intent

Two pieces of work, one serving the other:

1. **A demo stack.** A throwaway Docker stack, started with one command, that holds a small law firm's worth of invented users, clients, matters and documents, with enough history to look lived in. It's where every screenshot on the docs site comes from. (owner)
2. **The docs site's last 21 interim pages.** Each one still links to LogicalDOC's docs. They get written, retired or cut down, until none is left, the `interim` shortcode is deleted and #56 closes. (owner)

Today the only seed data is the smoke fixture: Store "Smoke", one template, client 1 and matter 1.1. The site's screenshots show three different worlds: the web app's a Store called "Smoke" with matter 1001.1, the helper's matter "998.1 – Healdan Demo", and the API page's "Jane Smith".

## 2. Decisions

1. **The demo is a small law firm** (owner), Ashcombe Reeve LLP (§4). A legal clinic was the alternative.
2. **Its data is loaded by a seed step inside the server** (owner), `demo-fixture`, like the smoke fixture (§5). The alternatives were a script driving the running stack from outside, which would first need an admin API for Stores, clients, matters and users, and a hybrid of the two.
3. **The sample documents are text sources built into real files by LibreOffice, and the built files are committed** (owner) (§6). The alternatives were files made by hand, which can't be reviewed as diffs, and files generated by the seed in Java, which would put more demo code in the production jar.
4. **The mix of formats includes PDFs, emails and LibreOffice's own formats**, `.odt` and `.ods` (owner), as well as Word and Excel (§4.5).
5. **Every screenshot that shows data is retaken from the demo stack** (owner), so the whole site shows one firm (§7).
6. **The interim pages are handled as §3's table says** (owner: "go with them"). Three rows were the owner's to decide, and took Claude's pick (call):
   - **Sharing a Document** is written, with a caution that a ticket's link only works for someone who can reach the server;
   - **Aliases** becomes a short page saying why Healdan refuses them, since CE's menus still offer them;
   - **Dropbox** is retired, and a seed step hides its menu. Testing it would need a Dropbox developer app registered on the owner's account.
7. **Four pull requests** (owner) (§8).

- **Deleting a document or a folder re-dates it,** because the Trash lists by last-modified. (changed in the build)
- **The printed dates assume a first start on 2026-10-29.** The seed dates everything relative to the first start, so a stack built months later shows letters whose printed dates differ from their filing dates. (changed in the build)

## 5. The seed step and the overlay

### 5.1 The overlay

`docker/demo/compose.demo.yaml`:

- sets `HEALDAN_DEMO_FIXTURE=true`;
- sets one test password for all six demo users. It's written in the file because it isn't a secret, and it must pass CE's password policy;
- mounts `docker/demo/` read-only into the container;
- names the project `healdan-demo` with a top-level `name:`, which wins over `compose.yaml`'s when the overlay comes after it, so a forgotten `-p` can't start the demo on the production project. `-p` and `COMPOSE_PROJECT_NAME` still override it, so the command keeps `-p`. (changed in the build)

It's a throwaway stack with its own project name and port, like the smoke overlay:

```bash
LOGICALDOC_IMAGE=healdan-demo:local LOGICALDOC_PORT=8091 docker compose -p healdan-demo -f compose.yaml -f docker/demo/compose.demo.yaml up -d --build
```

`down -v` with the same `-p` removes it. It doesn't need the smoke overlay, and works alongside it.

### 5.2 The step

- **`DemoFixtureSeed`**, named `demo-fixture`, in `com.logicaldoc.healdan.seed`, runs last in `SeedRunner.ORDER`. Without the variable it does nothing and writes no marker, like `smoke-fixture`.
- **It reads a manifest** from the mounted folder, which lists:
  - the users, groups, Stores, templates, search folders, clients and matters, with their permissions;
  - each document, with its file, folder, Author, Typist, Class and Subclass;
  - a timeline of actions, each on a day: new version, note, tag, link, move, check-out, lock, password, delete, bookmark, message, ticket.
- **It acts as each user, through the same services the UI uses,** so doc #s, inherited properties and the filing rule apply as they would for a real person. A manifest that breaks one of Healdan's rules fails the seed, so the demo can't show what Healdan wouldn't allow.
- **The seed checks permissions itself** (the design said the services do). Inside a seed every actor counts as an admin (`FilingRules.isAdmin`, the `SEED` operation), and `DocumentManager.create` checks where a document goes but not who files it. So `DemoTimeline` checks, before each action, the permission the web page asks for, and fails on a refusal naming the user, the permission and the target. (changed in the plan)
  - Because Healdan counts everyone as an admin inside a seed, the timeline also runs the web page's own tree check before deleting a folder, and refuses a non-admin at a matter's top level. Only a manifest user in the `admin` group, `sokafor`, counts as an admin. (changed in the build)
  - It logs the history event the web page logs for each action (CHANGED, PERMISSION, DELETED, CHECKEDOUT and LOCKED), because CE's History event defaults to an empty string, so CE's own "if no event" checks never fire. (changed in the build)
- **Each document is indexed inside its own action** (changed in the plan). `DocumentManager.index` saves the document, which resets its last-modified date, and adds an Indexed history entry. Indexed by the background task, every document would show today's date.
  - CE reads a file no parser knows, an image for one, through its PDF conversion, and the conversion saves the document under the indexing that asked for it, which then fails on a stale record. So the timeline makes that conversion first. The tests' context has no working ImageMagick and never saw it; the first start of the real stack did. (changed in the build)
- **Backdating by watermark** (changed in the plan; the design had one last pass). `Backdater` remembers each table's highest id before an action and, afterwards, dates every newer row with the action's date, in each table the demo writes. It also sets the last-modified date of a document an action changed. `EmailDocumentListener` forces every new document's creation date to now, so the creation date can't be set before the create. Only the demo does this.
  - `Backdater` clears Hibernate's second-level cache after its updates, since Document and Folder are cached and a later save would write the stale dates back. (changed in the build)
  - `Backdater.touchFolder` dates a folder, for the deletes. (changed in the build)
- **Users are also in CE's `author` group,** which holds the menus everyday users need (`ld_menu_acl`); a new group holds none. Sam Okafor is in `admin`. (changed in the plan)

### 5.3 Guards and failure

- **It refuses a repository that already holds a document, any document at all** (changed in the plan; the design said "outside the Templates Store"). The filing rule keeps documents out of the Templates Store, so the two are the same, and the simpler query can't be wrong. If the variable is set on a real server by mistake, startup stops with a message, rather than mixing invented data in. (The smoke fixture creates folders only, so the two overlays can be used together.)
- **It also refuses a repository that holds any user besides CE's own `admin` and `_system`** (changed in the build). A real install that has people, Stores and clients but no documents yet passes the document check, and the demo would add `sokafor` to its `admin`, with a password the repository publishes. The check also stops a start after a firm that failed partway, whose users are in the database, before it fails again on a constraint. A fresh stack has only those two users, and the smoke fixture creates none.
- **A failure stops startup,** as any seed step's does. Documents write their files outside the database transaction, so the fix is `down -v` and a fresh start, which is fine for a throwaway stack.
- **Previews and thumbnails** of Office files come from Healdan's usual background work, a few minutes after the first start; CE makes a PDF's, an email's or an image's the first time someone opens it. The full-text index doesn't wait: each document is indexed inside its own action (§5.2). (changed in the plan; the Office-only limit changed in the build)

### 5.4 Tests

`DemoFixtureSeedTest` in `healdan-core` runs the step on the test database, with the real manifest and files from `docker/demo/`, and checks:

- the counts of users, groups, matters and documents;
- that doc # order matches the backdated filing dates;
- that only Partners can read 998.3, and that the document-only grant works;
- that the checked-out document is checked out, by Jamie Clarke;
- that the guard refuses a repository with any document in it, and one with a user besides `admin`, whether that user was there before or a firm that failed partway left it. (changed in the build)

The test context sets `hibernate.jdbc.time_zone`, so in the tests Hibernate reads dates in another zone than the seed's JDBC writes them in. The tests read backdated dates through JDBC. (changed in the build) `testTheRealManifest` runs the real manifest in about two and a half minutes. (changed in the build)

CI's `build` runs it like any `healdan-core` test, so a code change that breaks the demo fails the check. A change under `docker/` counts as code, so it runs then too.

### 6.2 The build

`docker/demo/build.py`, Python's standard library only like the repo's other scripts:

- assembles the emails;
- converts everything else with `soffice --headless`, run inside the Healdan image, so everyone gets the same LibreOffice whatever's installed locally.

Its output goes to `docker/demo/files/`, which is committed, so the stack needs nothing beyond the overlay. The manifest names files from there.

`build.py` passes `HOME=/tmp` to LibreOffice, and refuses a `.docx` or `.odt` built from an `.html` that carries a comment, because LibreOffice turns unknown `<meta>` tags into comments. Letters stay HTML. (changed in the build) It exits non-zero, naming them, if LibreOffice or ImageMagick wrote no file for an output (`soffice` can exit 0 without one), and copies nothing then. (changed in the build)

**One known limit.** LibreOffice stamps the time of conversion into what it writes, so the output isn't byte-for-byte reproducible, and CI can't tell that a source changed without its file being rebuilt. The convention: rebuild in the same commit as the source change. `DemoFixtureSeedTest` still fails on any file the manifest names that's missing.

### 6.3 Content rules

- Every word is written fresh for the demo, in British English. (call)
- Invented companies, people and addresses, `.example` email domains and Ofcom's drama phone numbers (§4).

- Under 5 MB in git, all told.

## 14. Follow-up: saving the Healdan profile (2026-10-30)

Writing Property Templates (PR 4, Healdan-Project/healdan#117) showed that the Healdan profile's template and attribute set can't be saved from **Administration → Document metadata → Templates**. Both are named "Healdan profile" (`HealdanConstants.PROFILE_TEMPLATE`), and LogicalDOC's forms check the name against `^([a-zA-Z0-9]+)$` at every save, changed or not: `TemplateNameTextValidator` in `TemplatePropertiesPanel`, and `SimpleTextValidator`, through `ItemFactory.newSimpleTextItem`, in `AttributeSetPropertiesPanel`. Save shows "Use alphanumeric chars only". So no admin could add a property to the profile, though the User Guide's Properties page says one can. Only the **Options** window, which saves on its own, worked.

**The fix is a GUI hook that lets a template or attribute set keep the name it has** (call). `HealdanNames.keepCurrent` (`com.logicaldoc.gui.frontend.client.healdan`) gives the name field a validator that accepts the name the object was loaded with, as well as anything LogicalDOC's rule accepts, with the rule's own expression and message. A new name still has to pass the rule.

The other way, a seed step renaming both to a name without a space, was bigger:

- every version records its template's name (`ld_version.ld_templatename`), and CMIS looks an old version's template up by it, so old versions would name a template that no longer exists, unless the step also rewrote CE's version rows;
- admins would see the new name in the Templates and Attribute sets lists, the documents list's Template column and a version's details, so the docs' pages and screenshots that name the profile would change with it;
- the shipped `profile` and `profile-comments` steps would have to keep the old name, and the new step would need a guard for a template an admin had already given the new name.

The hook changes no data, and nothing anyone sees except that Save works.

**Upstream edits:** a line and an import in each of `TemplatePropertiesPanel.prepareTemplateForm`, after CE sets the name field's validator, and `AttributeSetPropertiesPanel.addMetadata`, after CE makes the name field. Each is marked `Healdan:`.

**Tests:** `HealdanNamesTest`, `logicaldoc-gui`'s first test, checks the rule the hook applies: the current name passes even with a space, a new one only if LogicalDOC's rule passes it, and an empty one never. It's in the build workflow's `UPSTREAM_TESTS`, and the shards' test step skips the GWT compile (`-Dgwt.skipCompilation=true`), which `logicaldoc-gui`'s compile phase would otherwise run. On a demo stack, an admin added a property to the attribute set and to the template, and a value set on a folder showed on a document's Ext. Properties below it.

**Docs:** Property Templates' "What Can't Be Changed Here" becomes "Adding a Property", with the steps, and keeps the warning not to rename or delete the profile. The User Guide's Properties page links to it.
