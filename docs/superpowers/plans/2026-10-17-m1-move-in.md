# M1 "Move in" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build M1 "Move in" as the approved spec describes it. That covers:
- doc #s;
- client/matter workspaces created from templates;
- `#` lookup;
- search folders;
- My Matters and Recent Matters;
- email fields and Date filed;
- full text for Office and email files;
- server-enforced filing and permission rules;
- a self-upgrading Healdan schema;
- a light rebrand.

All of it ships inside the existing LogicalDOC UI.

**Architecture:**
- **Module.** One new JPF plugin module, `healdan-core`, holds every server rule and all Healdan data, under the package `com.logicaldoc.healdan`.
- **Listeners.** Document, folder and user listeners enforce the rules and stamp data on every route.
- **Schema and setup.** Flyway owns the `hd_` tables. Idempotent Java seeds create the CE objects Healdan needs.
- **Hooks into CE.** A new core file, `HealdanHooks`, lets Healdan check the CE code paths that bypass listeners, before they write anything.
- **GUI.** GUI code is new files under `com.logicaldoc.gui.frontend.client.healdan`, reached from one-line hooks in upstream GUI classes. Healdan's RPC servlets register through `@WebServlet`.

**Tech Stack:**
- LogicalDOC CE 9.3.1 on Java 21: Spring 6.2.8, Hibernate 7.4.4, JPF plugins.
- GWT 2.12 / SmartGWT 14.1 for the GUI.
- Flyway 13.x: `flyway-core`, `flyway-mysql` (MariaDB) and `flyway-database-hsqldb`.
- Apache POI 4.1.2 and CE's `MailUtil` (Jakarta Mail, msgparser 1.1.15), both already on the classpath.
- JUnit 4.13.2 and HSQLDB 2.7.1 for tests.
- Tomcat 11, MariaDB 11.4, Docker Compose.

**Spec:** [`docs/superpowers/specs/2026-10-17-m1-move-in-design.md`](../specs/2026-10-17-m1-move-in-design.md), approved by the owner on 2026-10-17. Read it alongside this plan; every § reference below points into it. Where the two disagree, the spec wins, except for the corrections listed under "Spec corrections and calls this plan makes".

## Global Constraints

Every task's requirements include these.

**Stack**
- JDK 21, Tomcat 11 and MariaDB 11.4 (`mariadb:11.4`), run with the `compose.yaml` stack on a single node.
- Only LogicalDOC's default tenant (`Tenant.DEFAULT_ID = 1`).

**Code layout**
- One new module, `healdan-core`. Its JPF plugin id is `healdan-core`, and it requires `logicaldoc-core`.
- Server code lives under `com.logicaldoc.healdan`. GUI code lives under `com.logicaldoc.gui.frontend.client.healdan` in `logicaldoc-gui`.

**Upstream edits**
- Edit only the upstream files listed in this plan's upstream-edit table: spec §13 plus the corrections below.
- Each edit is a small hook into Healdan code. New logic goes in new files.
- Many upstream files have CRLF line endings. Edit them with the Edit tool, and never rewrite one with a script.

**Schema**
- Healdan never changes the structure of LogicalDOC's tables. Its own tables are prefixed `hd_`.
- Flyway manages only the `hd_` tables:
  - history table `hd_schema_history`;
  - scripts at `classpath:healdan/db/migration/{vendor}/V<n>__<name>.sql`, for the vendors `mariadb` and `hsqldb`;
  - `baselineOnMigrate` on, at version `0`.
- A failed migration fails startup. `healdan-core` declares no `DbInit` extension.

**Seeds**
- Seeds are idempotent. Each step writes a `seed.<name>` marker to `hd_setting` and never runs again.
- A seed never re-creates something an admin deleted.
- A shipped seed's behaviour never changes; new defaults or fixes ship as a new seed step name. Every setting getter has an in-code default.

**Doc #**
- A doc # is a Java `long`, stored as unpadded decimal digits in `ld_document.ld_customid`.
- Numbers start at 1. A number never changes and is never reused.
- The counter is the `hd_counter` row named `docnumber`, and each number is taken in its own short transaction.

**Folder types and servlets**
- Folder type `1001` is a search folder.
- Servlets are registered with `@WebServlet`, never with `LogicalDOCPlugin.addServlet`. RPC paths are `/frontend/healdan*` and data paths are `/data/healdan*`.

**Display and defaults**
- A matter displays as `<client>.<matter> – <name>`, with unpadded numbers and an en dash (U+2013) between spaces, e.g. `998.1 – Healdan Demo`.
- Default settings:

  | Setting | Default |
  |---|---|
  | Matter label | "Matter" / "Matters" |
  | Numbering mode | per client |
  | Default Class | "Docs" |
  | Recent Matters | 30 days, at most 20 entries |
  | Recent Work and My Recent Work | 30 days |

- The history events that count as a change are `STORED`, `CHECKEDIN`, `CHANGED`, `RENAMED` and `MOVED`.

**Profile**
- The CE template is named **"Healdan profile"**.
- Its attribute names are exactly `client`, `matter`, `author`, `typist`, `docclass`, `docsubclass`, `legacydocnum`, `emailfrom`, `emailto`, `emailcc`, `emailsubject`, `emailsent` and `emailreceived`.

**Features**
- `Feature_71` is declared.
- Feature 54 (CUSTOMID) and feature 12 (saved searches) stay off.

**Rules**
- Every Healdan rule is enforced on the server. Admins are bound by every rule not marked "admins only".
- Lookups by number use the database, never Solr.

**GUI**
- Healdan's own GUI strings are English only and are hard-coded in Healdan GUI classes. The only i18n bundle edits are the relabels in spec §8.4.
- Icons are Font Awesome Free solid only, and `python3 .github/scripts/check-fontawesome-icons.py` must pass.

**JDBC and instantiation**
- Healdan's JDBC goes through Spring's `JdbcTemplate` on CE's `dataSource` bean, so it joins the caller's transaction. The doc # counter is the only exception.
- Any JDBC write to an `ld_` row that Hibernate caches is followed by `CacheEvictor` (Task 6).
- Classes CE creates by reflection need a public no-arg constructor and fetch beans with `Context.get(...)`. These are listeners, `Search` subclasses, `SystemInfo` and parsers.

**Commits**
- Use a plain imperative sentence, like the existing history (e.g. "Add the doc # counter").
- End every message with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

These five inputs aren't covered by any row of the spec, and they're the ones most likely to bite a real user. Each owning task carries the test that pins it.

1. **Messy real emails.** For example:
   - no `Date` header;
   - an RFC 2047-encoded or empty subject;
   - a subject with `/ \ : * ? " < > |`, or longer than 250 characters;
   - no recipients;
   - a corrupt `.msg`.

   In every case the upload succeeds. Unknown fields stay blank, never "now", and the name is cleaned and shortened, keeping its extension. Pinned in Task 13 (`testMessyEmailsNeverBlockUpload`).
2. **`#` input variants**: `# 1234`, `#01234`, `#1234 ` (trailing space), `#1234V2`, `#99999999999999999999`, `#1234.2.1.5`, `#abc`, `#`. None of them may throw. The first four are lookups. An overflowing number gets "No document #…". Malformed input gets a message saying it isn't a document number, and doesn't fall through to full-text search. Pinned in Task 18 (`DocNumberQueryTest`).
3. **Odd client and matter text**, such as a name containing `/`, leading or trailing spaces, an over-long name, two clients with the same matter name, `998.01` or ` 998.1 `, and mixed case in Matters/Clients searches. Expected behaviour:
   - `/` and empty names are refused;
   - names are trimmed;
   - `998.01` equals `998.1`;
   - text search ignores case.

   Pinned in Task 8 (`ClientMatterRefTest`), Task 15 (`testRefusesBadNames`) and Task 18 (`MatterSearchTest.testTextIsCaseInsensitive`).
4. **Encrypted, corrupt or huge Office files.** An encrypted `.docx` is an OLE container, not a zip. The indexer stores empty text and moves on, the upload isn't blocked, and nothing throws out of the parser. Pinned in Task 21 (`testEncryptedOrCorruptFilesYieldEmptyText`).
5. **Settings that point at something later deleted**: a deleted Templates Store, a deleted or disabled matter owner, or a default Class removed from the option list.
   - The New Matter dialog pre-selects the Store it was opened from, which is live (the default Store setting was retired, R92).
   - Creating a matter in a deleted Store, or with a disabled owner, is refused with a clear message.
   - New documents still get a Class, falling back to the stored setting value.

   Pinned in Task 15 (`testDanglingSettings`) and Task 11 (`testClassDefaultRemovedFromOptions`).

## Spec corrections and calls this plan makes

The code surveys behind this plan found places where the spec has to be corrected or extended. The owner should confirm these before building starts. The last task folds the confirmed ones into spec §13.

**Corrections to spec §13**
1. **Document restore hook.** `DocumentManager` has no `restore`; document restore is `HibernateDocumentDAO.restore`, which JDBC-undeletes the row before `store`. So the hook goes at the start of `HibernateDocumentDAO.restore`, not in `DocumentManager`.
2. **Folder restore needs an "after" hook too.** `HibernateFolderDAO.restore` never calls `store`, so the re-stamping that spec §7.2 asks for needs `HealdanHooks.afterFolderRestore` at the end of that method.
3. **`FolderServiceImpl.save` gets a RENAME check.** It can rename a folder and change its type with no permission check, so it needs the same RENAME check as `rename` whenever the name changes. Type changes are refused by Healdan's FolderListener.
4. **Two extra GUI hooks** (spec §13 anticipated a few like these):
   - `HitsListPanel`: double-clicking a folder hit opens that folder. CE does nothing there today, so matter hits would otherwise be dead.
   - `DocumentsPanel.openInFolder`: expand the Browser section by name, not as section 0, because My Matters and Recent Matters now sit above it.
5. **The logos are base64 data URIs in `GUIBranding.java`.** The files under `war/skin/images/brand/` aren't referenced by any code. The rebrand therefore edits `GUIBranding.java`, `war/favicon.ico` and `war/header.jsp`, and leaves the unused PNGs until the owner supplies artwork.

**Calls this plan makes**
6. **A version result opens a small Healdan dialog.** It shows that version with Preview and Download buttons, so `VersionsPanel` and `DocumentDetailsPanel` stay untouched. Spec §8.1 leaves this choice to the builder.
7. **Numeric Doc # sorting is done on both sides:**
   - a sort normalizer on the `customId` field in `DocumentsListGrid`, for client-side sorts;
   - a numeric comparator for `customId` in `DocumentsDataServlet.sortDocuments`, for server-side sorts.
8. **The smoke test needs a matter.** The filing rule refuses the smoke test's current uploads into the Default workspace, and a fresh stack has no way to create a matter without the GUI until M2. The plan therefore adds:
   - a smoke-only seed, `smoke-fixture`, gated by the env var `HEALDAN_SMOKE_FIXTURE=true`, which creates one Store, template, client and matter;
   - an overlay, `docker/tests/compose.smoke.yaml`, that sets the env var.

   Production never sets it.
9. **My Matters bookmarks stay in the Bookmarks section as well.** Hiding them there would mean the webapp knowing about matters (spec §8.2 is ambiguous on this).
10. **A seed failure fails startup,** like a failed migration. Healdan never runs half set up.

## Conventions

**Running Maven.** `mvn` below means Maven 3.9 on JDK 21, with these in place:
- `~/logicaldoc-dev.properties` exists. An empty file is fine; without it, every Spring-based test fails in `setUp`.
- `~/.m2/settings.xml` has the repository block from `.github/workflows/build-logicaldoc.yml` (lines 27–62).

**Running Maven without a host JDK.** Use the Docker wrapper:

```bash
docker run --rm -v healdan-m2:/root/.m2/repository -v "$PWD/docker/maven-settings.xml":/root/.m2/settings.xml:ro -v "$HOME/logicaldoc-dev.properties":/root/logicaldoc-dev.properties:ro -v "$PWD":/src -w /src maven:3.9-eclipse-temurin-21 mvn -B -ntp <args>
```

**One-time build of every module, skipping GWT:**

```bash
mvn -B -ntp -DskipTests -Dgwt.skipCompilation=true -Dmaven.antrun.skip=true install
```

After any change to `logicaldoc-core`, `logicaldoc-webapp` or `logicaldoc-gui` (beans and service interfaces), re-install that module the same way, with `-pl <module>`, before running `healdan-core` tests.

**Running tests:**
- `healdan-core`: `mvn -B -ntp -o -pl healdan-core test -Dtest=<Class>`
- upstream tests: `mvn -B -ntp -o -pl logicaldoc-webapp test -Dmaven.antrun.skip=true -Dtest=<Class>`

**GUI compile check** (GWT, several minutes):

```bash
mvn -B -ntp -o -pl logicaldoc-gui -DskipTests package && python3 .github/scripts/check-fontawesome-icons.py
```

**Running the stack.** Put `DB_PASSWORD=…` in `.env`, then run `docker compose up -d --build`. Sign in at `http://localhost:8080` as `admin` / `admin`. Start over with `docker compose down -v`. The automated end-to-end check is `docker/smoke-test.sh`.

**GUI tasks.** CE's GUI code has no unit tests. A GUI task is verified by:
- its server-side tests in `healdan-core`;
- the GUI compile check;
- a scripted manual check on the stack, using the built-in browser and taking a screenshot of the expected state.

**Test helpers.** These are the shared helpers `healdan-core` tests use. Every later task relies on them.

| Helper | Task | What it does |
|---|---|---|
| `AbstractHealdanTestCase` | 1 | Builds the context; after CE's schema exists, runs `HealdanStartup.run()` (migrations, then seeds) |
| `PluginFixtures` | 1 | Builds the plugin manifest jars tests need |
| `DbSnapshot`, `IndexSnapshot` | 3 | Prove that a refused operation changed nothing (spec §7.5) |
| `HealdanFixtures` (`fx`) | 8 | Users, groups, Stores, clients, matters, folders and uploads |

| Type 1001 created, or type changed to or from 1001 | inside `SEARCH_FOLDER` or `MATTER_CREATE` | "Search folders can only be created with New search folder." |

A copy already can't carry one outside `SEARCH_FOLDER` or `MATTER_CREATE` | the parent is inside a matter (`isInsideMatter()`) or below a template (`IN_TEMPLATES`), never directly in the Templates Store, where it would be a template; admins included (Task 17) | "A search folder can only be inside a {label} or a workspace template." |
