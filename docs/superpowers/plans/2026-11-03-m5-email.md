# M5 "Email" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner files email from new Outlook for Mac into a matter's folders, the message being read or several selected, through a Healdan pane and the Healdan Helper's Save window, with attachments optionally filed as linked documents and a matter holding each message once, as the approved spec describes.

**Architecture:**
- **`healdan-core`** (`com.logicaldoc.healdan.email`) holds the domain:
  - the Message-ID as a new email field, read on every route, and `hd_email`, Healdan's own index of it, with a background worker that fills both for emails already in Healdan;
  - the once-per-matter rule, in a document listener of its own and in `HealdanHooks`, on every route;
  - `MessageParts`, Healdan's own walk of an `.eml`'s parts: attachments, inline parts and attached messages.
- **`healdan-api`** gains `Filer`, the filing of one document taken out of `DocumentResource.create`, and `EmailResource`: `POST /v1/emails/inspect`, `POST /v1/emails` (the email, its ticked attachments and their links, all or nothing) and `GET /v1/emails`, in `openapi.yaml`. `AddinResource` serves a second manifest, `outlook-manifest.xml`.
- **The add-in** (`clients/office/`) gains Outlook's manifest template and a pane, `mail.html`, with its logic in `mail.js` (Node-testable) and its Office.js calls in `mail-glue.js`. It holds no token and talks only to the helper.
- **The helper** pairs Outlook as one more app on M3.5's port, and gains `mail/status`, `mail/file`, `mail/file-many` and `mail/file-one`, the Save window's email mode, and the several-message summary.

**Tech Stack:**
- **Server:** JDK 25, CXF 4.0 JAX-RS, Spring 6.2, Hibernate 7, Flyway 13.10.3, Jakarta Mail through CE's `MailUtil`, msgparser 1.1.15 (already a dependency of `logicaldoc-core`), JUnit 4 with Spring's servlet mocks, as M2 and M4. No new libraries.
- **Helper:** .NET 10 and Avalonia 12.1.4, as M3. No new NuGet packages.
- **Add-in:** classic scripts with no dependencies, Office.js from Microsoft's CDN, Node 22's test runner, as M3.5.
- **Icons:** one new Tabler 3.50.0 icon, `mail`.

**Spec:** [`docs/superpowers/specs/2026-11-03-m5-email-design.md`](../specs/2026-11-03-m5-email-design.md). Read it with this plan: tasks cite its sections.

- **A Message-ID** is the header's value without angle brackets or surrounding whitespace, compared exactly, at most 998 characters (longer counts as none). Its hash is SHA-256 of its UTF-8 bytes, in lower-case hex.

## Review Focus

These are the inputs most likely to hurt someone that a task's main tests could miss. Each has a test in the task named.

1. **A refusal or a lookup revealing a document the caller can't read:** the rule, `inspect`'s copies, `GET /v1/emails`, the suggestions (Tasks 4, 7, 11).
2. **A matter getting a second copy of a message** by some route: an upload, the API, a copy, a restore, a document or folder move, a folder merge or restore, or two filings at once (Task 4).

5. **The wrong message filed, or a category on one that wasn't:** several selected, a reused or expired ticket, an outcome lost on the way (Tasks 13, 14).

## Spec corrections and calls this plan makes

The owner hears about these when this plan is handed over. Task 15 folds them into the spec, each marked "changed in the build".

1. **Filing needs WRITE on the folder, not ADD** (spec §6.5, §6.7). `POST /v1/documents` checks `Permission.WRITE` (`DocumentResource`, via `AccessChecks.allowed`), and emails file the same way, so a suggestion is a folder the caller may file into by that test, `FolderView.canFile`.
2. **`hd_email` holds no matter** (spec §6.2, §12, §16). A message has few copies, so the rule and the lookup find each copy's matter afresh with `MatterLocator.locate(folderId)`. No column to keep right on moves of documents or folders.
3. **Filing an email and its attachments lives in `healdan-api`** (spec §13). Filing one document (the doc #'s reservation, the stamp, properties, `confirmStored`) is `DocumentResource.create`'s, in `healdan-api`. Task 6 takes it out into a `Filer` there, and `EmailFiling` uses it.
4. **Attachments take the email's sent properties** (spec §6.5), other than its email fields, so a required property the person filled applies to them too. Otherwise they inherit from the folder, as any upload does.
5. **The rule is a listener of its own,** `OncePerMatterListener` at position 135, after the email fields (130) and before the doc # (140) (spec §6.4, §16).
6. **An `.msg`'s Message-ID comes from msgparser's `Message.getMessageId()`** (spec §6.1, §16). CE's `EMail` has no such field, and `MailUtil` never fills its headers.
7. **`AlreadyFiledException` is a `HealdanRuleException`,** so `Vetoes.check` evicts on rollback as for the filing rule, and `ProblemMapper` maps it, ahead of the general veto, to `409 already-filed` with the copy as `document` (spec §6.4, §6.8).
8. **The backfill is a worker,** on `PreviewWorker`'s pattern, with a cursor in `hd_setting` (spec §6.3).
9. **Outlook pairs by name,** not as an `OfficeProgram`, as it isn't in the copy cycle (spec §7.1).
10. **The name isn't editable in the Save window's email mode** (spec §7.3). M1 names every email after its subject on every route (`EmailDocumentListener`), so a name sent would be replaced. It can be renamed afterwards in the web page, as today.
11. **Each copy in `GET /v1/emails` carries `address`,** the web page's address for it (`/frontend.jsp?docId=<id>`, which `MainPanel` opens), so the pane's doc # link needs no internal id (spec §8.2).
12. **Rows for documents deleted for good stay,** and every lookup joins `ld_document` and skips them (spec §6.2).

```java
public Optional<Document> copyIn(String messageId, long folderId, long except, User actor) {
	if (messageId == null)
		return Optional.empty();
	Matter matter = MatterLocator.get().locate(folderId).matter();
	if (matter == null)
		return Optional.empty();
	for (long id : EmailIndex.get().copies(messageId)) {
		if (id == except)
			continue;
		Document copy = DocumentDAO.get().findById(id);
		if (copy == null || !matter.equals(MatterLocator.get().locate(copy.getFolder().getId()).matter()))
			continue;
		if (actor == null || AccessChecks.readableDocument(copy, actor).isPresent())
			return Optional.of(copy);
	}
	return Optional.empty();
}
```

## Decision log

Every ruling made while building that the plan or the spec didn't settle, in task order, with what it costs if it was wrong. The ledger's rulings and the controller's, as the build made them. The plan's own corrections are under "Spec corrections and calls this plan makes".

**Task 1**

- **The Message-ID stays out of the full-text index** (`EmailParser.appendHeaders` unchanged), so spec §6.1's "searched like the other email fields" became "shown in Properties; Healdan finds copies by it". Copies are found through `hd_email`, and an ID's fragments would add noise to every email's text for a lookup nobody types. If wrong, one line in `EmailParser` and a re-index.

**Task 3**

- **The worker runs from its cursor on every start,** also once `email.index` is `done`, which now records only that the first full pass ended. The plan's Task 3 comment ("returns at once once `email.index` is done") describes the old rule. So an email filed since the last start whose row was missed gets one; the Developer Guide says how to run it again from the start (delete `email.index` and `email.index.cursor`, restart). If wrong, a short scan at each start (one query).
- **Warnings log the exception's class and the document id,** never `toString()` (`EmailFields`, `EmailDocumentListener`, the worker). A MIME parse message can carry addresses, which the global constraint keeps out of warnings. If wrong, less detail in a warning.

**Task 4**

- **No `hd_matter` row lock; the rule serialises on `DocumentManager`'s monitor** (supersedes the first reading of the Task 8 ruling below, and changes spec §6.4's lock sentence). Every create and move holds the monitor across its listeners and store, and commits inside it when no outer transaction is open, so the rule's check (also for stores that move a document) sees every earlier filing. **Accepted**
